# Adapter Architecture

## Purpose

Every document that precedes this one treats the Adapter as a boundary rather than a subject. The Domain Model establishes that an Adapter exists and that it is versioned independently of the Agent it serves. The Backend Architecture places the Adapter Layer in the dependency graph and states, categorically, what it may and may not depend on. The Execution Engine Architecture goes further — it describes, from the orchestrating side of the boundary, what an Adapter may and may not do, and treats everything on the other side of that boundary as a black box it invokes but does not inspect. That treatment was correct for the Execution Engine Architecture's purpose: an orchestration document should not need to understand the internals of every component it coordinates in order to define how it coordinates them. But a black box invoked correctly by one document still needs, somewhere in the corpus, a document that opens it — that explains why it exists, what it is architecturally responsible for, and what rules govern its own internal shape. This is that document.

The Adapter Layer is the single mechanism by which EvalForge remains agent-agnostic — capable of evaluating Claude Code, Cursor, Gemini CLI, Codex, and every coding agent not yet built, through the identical orchestration, execution, event, and grading architecture already established by every prior document, without any of those documents needing to know or care which agent a given Run happens to involve. That is a strong claim, and it is only true because of how narrowly and precisely this document is about to define the Adapter's responsibility. If the Adapter's boundary were drawn loosely — if it were permitted to leak vendor-specific concepts into the platform's orchestration, its persistence layer, or its grading logic — agent-agnosticism would be an aspiration the documentation asserts rather than a property the architecture actually delivers. This document exists to make sure that does not happen: to draw the Adapter's boundary with enough precision that every other document in this corpus can continue to treat "an Agent" as an interchangeable abstraction, forever, regardless of how many wildly different vendor implementations the platform eventually supports.

This document refines, and does not redefine, everything the corpus has already established about Adapters. Where the Domain Model already states that an Adapter is connected to exactly one Agent and is independently versioned, this document does not restate that fact — it explains the architectural consequences of it. Where the Backend Architecture already states the dependency rules governing the Adapter Layer package, this document does not relitigate those rules — it explains why they are drawn exactly where they are and what would break if they were drawn anywhere else. Where the Execution Engine Architecture already describes, from its own side, how it invokes an Adapter and what it expects back, this document takes that same invocation and describes it from the Adapter's side, filling in exactly the internal architecture that document deliberately left as a black box. Everywhere this document uses a term the corpus has already defined — Agent, Adapter Version, Normalized Domain Model, Execution Event, Artifact, Sandbox — it means precisely what that earlier document said it means, and nothing more.

## Adapter Philosophy

**Agent-agnosticism as the platform's central promise, and the Adapter as its sole mechanism.** Every document in this corpus, from the System Overview onward, has taken for granted that EvalForge evaluates multiple, heterogeneous coding agents through one uniform pipeline. That uniformity is not a coincidence of good design elsewhere in the platform — it is a direct, load-bearing consequence of the Adapter Layer's existence. Remove the Adapter, and every other document's agent-agnostic language collapses into fiction: the Execution Engine would need to branch on which Agent it was invoking, the Domain Model's Normalized Domain Model would have no producer, and onboarding a new Agent would mean touching orchestration, persistence, and grading code simultaneously. The Adapter is not one convenience among several that make multi-agent evaluation easier; it is the single point in the architecture where agent-specific reality is absorbed so that nothing else in the platform ever has to be agent-aware.

**Translation as the Adapter's entire purpose, and nothing more.** An Adapter has exactly one job: convert one Agent's native behavior — its tool-call format, its file-editing mechanism, its way of signaling completion or failure — into the platform's Normalized Domain Model, faithfully and in real time. This document treats "faithfully" as a specific, demanding standard, not a vague aspiration: a translation is faithful when a human or a Grader reading the resulting Execution Events can reconstruct exactly what the Agent did, in the order it did it, without needing to have watched the Agent operate directly. An Adapter that translates loosely — dropping detail, reordering events for its own convenience, or summarizing rather than recording — has failed at the one thing it exists to do, regardless of how well it otherwise integrates with a given Agent's API.

**The Adapter as a pure boundary, never a store of record.** This principle is already stated in the Backend Architecture, and this document treats it as one of the two or three most consequential facts about the Adapter's design, worth dwelling on rather than merely citing. An Adapter holds no durable state of its own between Runs, and, more subtly, holds no durable state of its own even within a single Run beyond what it needs transiently to perform the translation currently in progress. Everything an Adapter produces flows immediately back across the boundary to the Execution Engine, to be durably recorded through the platform's own persistence path. An Adapter that accumulated its own record — even temporarily, even as an optimization — would be creating a second, uncontrolled copy of facts the platform's entire architecture depends on having exactly one authoritative copy of, which Database Design's Normalization Philosophy already treats as a defect wherever it occurs, and which is especially dangerous here, at the one boundary where untrusted, non-deterministic behavior first enters the system.

**Isolation as a consequence of narrow scope, not a separately engineered property.** An Adapter for one Agent knows nothing about any other Adapter, any other Agent, or any of the platform's own concerns beyond the translation boundary this document defines. This is not an isolation mechanism bolted onto the Adapter Layer after the fact — it is what falls out naturally from an Adapter having exactly one job, narrowly scoped, with no legitimate reason to reach beyond it. A well-drawn boundary does not need a separate isolation enforcement mechanism nearly as much as a poorly-drawn one does, and this document's later sections on Adapter boundaries and dependency rules are, in large part, an explanation of how that narrow scope is drawn precisely enough to make isolation close to automatic.

**Determinism of translation, not of the thing being translated.** The Execution Engine Architecture already distinguishes the Agent's permitted unpredictability from the orchestration's required determinism. This document draws an analogous, but distinct, line specifically for the Adapter: given the identical sequence of Agent actions, an Adapter's translation of those actions into Normalized Domain Model events must be the same every time. The Adapter does not get to introduce its own unpredictability into the pipeline — if the same tool call, observed twice, ever produced two different Execution Event shapes from the same Adapter Version, the platform's entire reproducibility guarantee (Database Design's Versioning Model, restated at the execution level by the Execution Engine Architecture) would be undermined not by the Agent's legitimate unpredictability but by a defect in the one component that is supposed to be faithfully, deterministically recording it.

**Extensibility as the philosophy's practical payoff.** Every principle above compounds into the same outcome: because an Adapter's responsibility is narrow, its behavior deterministic, and its boundary strictly one-directional (translate and hand off, never reach back), adding a new Agent to the platform is additive by construction — a new Adapter satisfying the same contract, changing nothing else. This document's later Extensibility section makes this concrete, but it is worth stating here, as philosophy, because every other section in this document is, in one way or another, in service of keeping that additive property true no matter how many Agents the platform eventually supports.

## Responsibilities

An Adapter is responsible for observing an Agent's behavior inside a Sandbox and translating that behavior, continuously and in real time, into the Normalized Domain Model shape the rest of the platform consumes. It is responsible for that translation being complete — nothing the Agent does that is meaningful to the Run's record may be silently dropped — and for that translation being ordered correctly, since the sequence in which actions occurred is itself part of what the platform's record must faithfully preserve. It is responsible for recognizing the vendor-specific signals that indicate an Agent has finished its work, succeeded, or failed on its own terms, and translating those signals into the platform's own vocabulary for execution outcomes. And it is responsible for doing all of this using only vendor-specific knowledge — nothing about an Adapter's internal translation logic is shared with, or should be informed by, anything about how any other Agent behaves.

An Adapter is not responsible for deciding when a Run should be considered complete, when a timeout should be enforced, or when a Sandbox should be provisioned or torn down — those are Execution Engine decisions, informed by what the Adapter reports, never delegated to it, exactly as the Execution Engine Architecture already states from its own side of this same boundary. An Adapter is not responsible for persisting anything — every fact it produces is handed back across the boundary for the Execution Engine to record durably, through the platform's own persistence path, never written directly by the Adapter to any store. An Adapter is not responsible for grading — nothing about whether an Agent's behavior was good, correct, or successful in any evaluative sense is the Adapter's concern; it records what happened, faithfully and without judgment, and leaves every evaluative question to the Grader Layer, which the Adapter has no relationship to whatsoever. And an Adapter is not responsible for anything resembling authorization, API concerns, or business logic belonging to any other bounded context this corpus has established — by the time an Adapter is invoked, every one of those concerns has already been resolved by layers the Adapter never sees.

This division is not incidental to the Adapter's design — it is the design. An Adapter that also made orchestration decisions, or persisted its own state, or passed judgment on the quality of what it observed, would no longer be a narrow translation boundary; it would be a second orchestration authority, a second store of record, or a second grading mechanism, each of which this corpus has already established belongs exactly once, elsewhere in the platform. The Adapter's responsibility is deliberately, precisely everything between "observing the Sandbox" and "producing Normalized Domain Model facts," and nothing on either side of that narrow span.

## Position in the Architecture

The Backend Architecture already places the Adapter Layer in the platform's dependency graph with a rule this document treats as inviolable: Adapters depend on the Domain Layer and shared, framework-level concerns only, and are never depended upon by anything other than the Execution Engine that invokes them. This document's contribution is explaining why that specific position — and no other — is the correct one for a component whose entire job is translating untrusted, vendor-specific behavior into a form the rest of the platform can trust.

An Adapter sits at the exact point in the architecture where the platform's control extends to its furthest, most tenuous reach: inside a Sandbox, observing code the platform did not write and cannot fully predict. Every layer upstream of the Adapter — the Execution Engine, the Application Layer, the API — operates on data the platform itself produced or validated. The Adapter is the one component whose primary input is not the platform's own data at all, but a third party's live, real-time behavior. This is precisely why its dependency footprint is drawn so narrowly: a component operating this close to untrusted behavior should have as little surface area as possible for that behavior's unpredictability to reach into, and depending on nothing beyond the Domain Layer's shape definitions is what keeps that surface area minimal.

The Adapter's position relative to the Execution Engine, per the Execution Engine Architecture's own topology, is that of an invoked boundary, never a peer. The Execution Engine calls into an Adapter and consumes what it produces; the Adapter never calls back into the Execution Engine's own orchestration logic, never asks it a question, and never waits on it for anything beyond receiving the Sandbox and the pinned inputs (Agent Version, Prompt Version) it needs to begin. This one-directional relationship — invoked, never invoking — is what makes the Adapter's failure modes containable in exactly the way the Execution Engine Architecture's Failure Model already assumes: an Adapter that misbehaves can be observed misbehaving and handled, but it can never itself reach further into the platform than the narrow channel through which it reports translated events.

The Adapter's position relative to the Agent Integration bounded context, established by the Domain Model and given code-level shape by the Backend Architecture's package organization, places one Adapter submodule per supported Agent, each independently deployable in the logical sense (though not independently versioned from the platform's own release process, a distinction Versioning below addresses directly) and each entirely ignorant of every sibling Adapter's existence. This is the Backend Architecture's dependency rule — "Adapters never depend on any other Adapter" — restated here as a positional fact: an Adapter's neighbors, in the codebase's actual directory structure, are Adapters for other Agents, but its architectural relationships extend only downward, to the Domain Layer, and upward, to the one Execution Engine invocation that calls it. It has no lateral relationships at all.

## Adapter Topology

Within this position, the Adapter itself is not architecturally monolithic — it is useful to distinguish three internal concerns every Adapter implementation must address, even though this document, consistent with its Non-Goals, does not specify how any of them are implemented.

The first is **observation**: the mechanism by which an Adapter perceives what the Agent is doing inside the Sandbox. This might mean intercepting the Agent's tool-call invocations, watching filesystem changes the Agent makes, or consuming a structured event stream the Agent's own runtime exposes — the specific mechanism varies entirely by Agent, which is exactly why this document does not prescribe one. What every Adapter's observation concern shares, architecturally, is that it is the only place vendor-specific knowledge is permitted to live at all.

The second is **translation**: the mapping from whatever the observation concern perceives into the Normalized Domain Model shape this document's Translation Model and Normalization Model sections define in full. Translation is where an Adapter's determinism obligation, established in Adapter Philosophy, is actually discharged — the same observed action must always produce the same translated shape.

The third is **reporting**: the mechanism by which translated events and artifacts are handed back across the boundary to the Execution Engine, in the streaming, ordered fashion this document's Streaming Architecture section describes. Reporting is deliberately kept as thin as possible — it is not itself a place where translation logic lives, only the channel through which already-translated facts leave the Adapter's boundary.

These three concerns are described separately here because they are useful to reason about independently — a bug in observation (missing an Agent action entirely) is a categorically different failure from a bug in translation (observing correctly but mapping incorrectly) or a bug in reporting (translating correctly but failing to durably hand off the result) — and this document's later Failure Model section treats them as distinguishable failure classes precisely because an engineer diagnosing a specific Adapter problem needs to know which of the three actually failed. They are not, however, three separately versioned or separately invokable components — an Adapter Version, per the Domain Model and Schema Design, is a single, atomic unit encompassing all three concerns together, and this document's topology is a reasoning aid, not a suggestion that these concerns should be split into independently deployable pieces.

## Adapter Lifecycle

An Adapter's lifecycle, from the Execution Engine's perspective, is fully described by the Adapter Invocation section of the Execution Engine Architecture: initialization, observation and translation throughout Agent execution, and an implicit conclusion once the Sandbox's work ends. This document describes the identical lifecycle from the Adapter's own side of the boundary, filling in what happens inside each of those phases.

**Initialization** begins the moment the Execution Engine invokes the pinned Adapter Version against a freshly prepared Sandbox and the Run's other pinned inputs. What an Adapter does during initialization is establish whatever internal state it needs to begin observing this specific Agent's behavior — recognizing the Agent's expected interface, establishing whatever connection or hook the observation concern requires, and confirming that the Sandbox is in the state the Adapter expects before Agent execution formally begins. Initialization is the one phase in which an Adapter is permitted to fail cleanly and immediately, before any Agent behavior has occurred at all — an Adapter that cannot establish observation of its Agent has nothing further to contribute to the Run, and the Execution Engine treats that failure, per the Execution Engine Architecture's Failure Model, as an Adapter failure distinct from anything the Agent itself might later have done.

**Active translation** is the lifecycle's longest phase, running for the full duration of Agent execution, and is where the three concerns Adapter Topology describes — observation, translation, reporting — operate continuously and concurrently with whatever the Agent is doing. There is no meaningful sub-phase structure to active translation from the platform's perspective; it is simply the period during which the Adapter is doing the entirety of its job, producing a continuous stream of Normalized Domain Model events for as long as the Agent continues to act.

**Conclusion** is reached when the Agent signals it is finished, when the Sandbox's execution otherwise ends (a timeout, a resource-limit violation per the Execution Engine Architecture's Resource Accounting), or when the Adapter itself detects that no further meaningful translation is possible. The Adapter's responsibility at conclusion is narrow: report whatever final signal the Agent gave (successful completion, an Agent-reported failure, or an Agent-reported inability to proceed) in the platform's own vocabulary, and then stop — an Adapter does not itself tear down the Sandbox, does not itself decide the Run's terminal status, and does not continue attempting to observe an Agent that has already indicated it is done.

An Adapter's own lifecycle is deliberately this simple — three phases, no branching complexity of its own — because the branching complexity that does exist in a Run's overall journey (timeouts, cancellation, resource-limit violations, worker crashes) is Execution Engine complexity, per that document's own Run Lifecycle and Failure Model, not Adapter complexity. The Adapter's job is to behave predictably within whichever of these Execution-Engine-determined circumstances it finds itself in, not to independently reason about which circumstance currently applies.

## Adapter Contract

Every Adapter Version, regardless of which Agent it serves, satisfies the identical contract — the same shape of invocation, the same shape of output, the same behavioral guarantees — and this uniform contract is what the Backend Architecture's Testing Strategy already anticipates when it describes contract tests verifying that an Adapter's output satisfies the Normalized Domain Model's shape without needing a live Agent or Grader. This document defines what that contract actually consists of.

**On invocation**, an Adapter receives a prepared Sandbox (already checked out to the Case Version's reference repository state, per the Execution Engine Architecture's Run Lifecycle), the pinned Agent Version and Adapter Version it is itself operating as, and the pinned Prompt Version whose content it is responsible for delivering to the Agent. This is the entirety of what an Adapter receives — it does not receive the Run's identifier in any form that would let it reach into persistence directly, it does not receive Grader information, and it does not receive anything about the Case beyond what the prepared Sandbox and Prompt Version already carry, consistent with an Adapter having no legitimate reason to know about Runs, Grades, or Cases as platform concepts, only about the Sandbox and the content it has been asked to deliver.

**On output**, an Adapter produces a stream of Normalized Domain Model events, in strict chronological order, terminating in exactly one concluding signal indicating how the Agent's execution ended. Every event in this stream conforms to the shape the Domain Model already establishes for the Normalized Domain Model, and this document's Normalization Model section below describes precisely how an Adapter is expected to map arbitrarily varied vendor-specific behavior onto that one, fixed shape.

**On behavioral guarantees**, every Adapter commits to the determinism property Adapter Philosophy already establishes, to producing no output through any channel other than the reporting mechanism this document's Streaming Architecture describes, and to never blocking indefinitely without eventually reporting either further translated activity or its own inability to continue — an Adapter that simply stops producing any signal, with no eventual timeout or failure report of its own, is relying entirely on the Execution Engine's own timeout enforcement to notice, which this document treats as acceptable only as a last resort, not as an Adapter's primary means of handling its own internal failure.

**On what the contract does not require**, an Adapter is not required to understand or reason about anything upstream of its own invocation (why this Run was created, what Suite it belongs to, who requested it) or anything downstream of its own conclusion (how it will be graded, what Score it will receive). The contract is deliberately narrow enough that an engineer implementing a new Adapter needs to understand only the Agent they are integrating and the fixed shape they must translate into — nothing about the rest of the platform's architecture is a prerequisite for correctly satisfying this contract.

## Translation Model

Translation is the process by which an Adapter converts something it observed — a tool invocation, a file write, a shell command, a piece of output — into one or more Normalized Domain Model events. This document treats translation as having three properties every Adapter must uphold, regardless of how different the underlying Agent's native format is from any other Agent's.

**Completeness** means every action the Agent takes that has any bearing on the Run's outcome is translated into some corresponding event — an Adapter does not selectively omit actions it considers unimportant, because the judgment of what is or is not important belongs to whoever later reads the Run's record (a human debugging it, a Grader scoring it), not to the Adapter performing the translation. An incomplete translation is not a smaller, more efficient record — it is a record that has silently diverged from what actually happened, which this corpus's Execution Philosophy already treats as one of the most serious failure modes the platform can produce.

**Fidelity** means a translated event preserves the actual content and meaning of what was observed, not a lossy or approximated version of it. Where an Agent's native tool call carries specific arguments, a file edit carries a specific diff, or an output stream carries specific text, the Adapter's translation carries that same content forward into the Normalized Domain Model event, subject only to the Artifact Translation section's rules about what belongs inline versus in object storage — fidelity is about preserving content, not about where that content is physically stored.

**Timeliness** means translation happens as observation occurs, not in a batch after the fact. An Adapter that buffered its observations and translated them in bulk once Agent execution concluded would violate this document's Streaming Architecture requirements below, and would also mean the platform's SSE stream — which the Execution Engine Architecture already establishes as a live projection of durably recorded Execution Events — has nothing live to project, defeating the purpose of live progress visibility entirely.

Translation is explicitly not summarization, interpretation, or evaluation. An Adapter does not decide that a sequence of Agent actions "amounts to" some higher-level action and record only the summary; it records what actually happened, at the granularity the Agent actually operated at. An Adapter does not interpret whether an action was a good or bad choice by the Agent; that judgment belongs entirely to the Grader Layer, operating on the Adapter's faithful record after the fact, never to the Adapter itself.

## Normalization Model

Normalization is the specific discipline of mapping an arbitrarily varied set of vendor-specific action types onto the one, fixed Normalized Domain Model shape the Domain Model already defines. This is the single hardest architectural problem an Adapter solves, because the entire value of having a Normalized Domain Model at all — that every downstream consumer (Execution Event persistence, the SSE stream, Graders) can operate on one shape regardless of which Agent produced it — depends on every Adapter solving this problem correctly and consistently.

The Normalized Domain Model's shape is defined once, by the Domain Model, and is not something this document redefines or extends per Agent. An Adapter's job is to find, for every distinct kind of action a specific Agent can take, the correct mapping onto that one fixed shape — never to propose an Agent-specific extension to the shape itself, because an extension used by only one Adapter would immediately reintroduce exactly the agent-specific leakage into downstream consumers that the Normalized Domain Model exists to prevent. Where an Agent's native behavior genuinely does not map cleanly onto any existing Normalized Domain Model concept, that is a signal the Domain Model itself may need to evolve — through the ordinary, deliberate evolution process any shared domain concept undergoes — not a signal that an individual Adapter should invent its own extension unilaterally.

Normalization is necessarily lossy in one specific, bounded sense that this document is explicit about: an Agent's own internal representation of its actions — whatever data structures or formats it uses natively — is not preserved verbatim, only its meaning, translated into the Normalized Domain Model's vocabulary. This is a deliberate choice, not an unfortunate limitation: preserving every Agent's native representation verbatim, alongside the normalized translation, would mean every downstream consumer needs to understand every Agent's native format after all, exactly undoing the value normalization provides. Where an Agent's native representation carries detail the Normalized Domain Model's shape has no place for, that detail is either mapped into the closest fitting normalized concept or, where genuinely too large or too Agent-specific to normalize meaningfully, carried forward as an Artifact per this document's Artifact Translation section — but it is never carried forward as an unnormalized escape hatch that lets an Adapter sidestep the shape it is contractually required to produce.

Every Adapter Version's normalization mapping is itself an immutable fact about that specific version, exactly as the Domain Model's versioning philosophy already requires: if an Agent's native output format changes, or if the platform discovers a more accurate way to normalize some existing action type, that change is expressed as a new Adapter Version, never as a silent change to how an existing, already-referenced Adapter Version behaves — a Run that pinned a specific Adapter Version must, per Database Design's Reproducibility guarantee, be reconstructable using that exact version's normalization behavior, forever.

## Event Translation

Every discrete, meaningful action an Adapter observes becomes exactly one Execution Event, or, where a single observed action genuinely decomposes into multiple independently meaningful facts, a small number of closely related Execution Events — never a single event representing several genuinely distinct actions collapsed together, since collapsing would violate the completeness property Translation Model establishes.

**Granularity** is chosen, by each Adapter, at the level the underlying Agent actually operates at — a single tool invocation becomes a single translated event (or an event pair, where the Adapter meaningfully distinguishes a tool call's invocation from its result), a single file edit becomes a single translated event, and so on. This document does not prescribe a universal granularity finer or coarser than what the Agent itself naturally produces, because imposing an artificial granularity — either splitting a single atomic Agent action into multiple events or merging several distinct actions into one — would itself be a fidelity violation in either direction.

**Sequencing**, per the Execution Engine Architecture's Event Production section, is assigned by the Execution Engine as it consumes the Adapter's stream, not by the Adapter itself — an Adapter's own responsibility is only to report events to the Execution Engine in the correct relative order it observed them, and the Execution Engine's own sequence-position assignment is what turns that relative ordering into the durable, absolute ordering Schema Design's Execution Event table requires. This division matters architecturally: it means an Adapter never needs to coordinate sequence numbering with anything outside itself, even under concurrent internal activity (an Agent that issues several tool calls whose results resolve out of strict issuance order, for instance) — the Adapter reports in the order it can confidently establish, and the Execution Engine's own recording discipline is what makes that order durable and authoritative.

**Content shape** for a translated event follows the Normalized Domain Model's event structure exactly, carrying whatever type, timestamp, and payload fields that structure defines, populated from the specific Agent action being translated. An Adapter does not add fields to this structure that only its own Agent's events would ever populate — any field an Adapter's translated events carry is a field every other Adapter's translated events are equally capable of carrying, even if a specific Agent never happens to populate it, because a field only one Adapter ever uses is, again, exactly the kind of agent-specific leakage the Normalized Domain Model exists to prevent.

## Artifact Translation

Where a translated event's payload would be large enough to warrant separate storage rather than inline event metadata, per the Execution Engine Architecture's Artifact Handling and Database Design's Storage Strategy, the Adapter is the component that recognizes this at the moment of translation and produces an Artifact rather than embedding the content inline. This decision — inline versus Artifact — is made using the identical, Agent-agnostic size-based criterion the Execution Engine Architecture already establishes, applied consistently by every Adapter regardless of how naturally verbose or terse a given Agent's native output tends to be, which is precisely what keeps Execution Event rows uniformly sized across every Agent the platform supports.

An Adapter that produces an Artifact hands the underlying content across the boundary to the Execution Engine for durable persistence to object storage, exactly as it hands translated events across the same boundary — the Adapter does not write to object storage directly, consistent with this document's Adapter Philosophy stance that an Adapter is never a store of record, and consistent with the Backend Architecture's dependency rules, which never grant the Adapter Layer a dependency on Infrastructure. What the Adapter does own is recognizing that a given piece of content belongs in an Artifact rather than inline, and streaming that content across the boundary in a form the Execution Engine can persist without needing to understand or reinterpret it — the Adapter's Artifact-worthy content is opaque payload from the Execution Engine's perspective, exactly as Database Design's metadata-versus-artifact separation already requires.

Every Artifact an Adapter produces is referenced from the specific translated Execution Event it belongs to, following the identical relationship Schema Design already establishes between Execution Event and Artifact — an Adapter never produces an orphaned Artifact with no referencing event, because an Artifact with no event context has lost the one piece of information (what action produced it, and when, relative to everything else) that makes it meaningful within the Run's record.

## Streaming Architecture

An Adapter's relationship to the Execution Engine is fundamentally a streaming relationship, not a request-response one — the Adapter does not wait until Agent execution has entirely concluded and then hand back a single, complete bundle of everything that happened. It reports translated events and artifacts continuously, as they are produced, for the full duration of Agent execution, and the Execution Engine consumes that stream incrementally, durably recording each item as it arrives, exactly as the Execution Engine Architecture's Event Production section already describes from the consuming side.

This streaming relationship exists for reasons that compound across several parts of this corpus. It is what makes live SSE progress possible at all, since the REST API Design's SSE stream is a projection of Execution Events as they are durably recorded, and events cannot be durably recorded before they are reported. It is what bounds the cost of a worker crash mid-execution to only the narrow window between an event's translation and its durable recording, per the Execution Engine Architecture's Durable Checkpoints discussion — a batch-reporting Adapter would mean an entire Run's worth of translated activity is lost on a crash, rather than only the small amount that had not yet crossed the boundary. And it is what keeps memory pressure bounded on both sides of the boundary — an Adapter holding an entire Run's worth of untranslated or untransmitted state in memory, for a Run that can run for many minutes, is a resource risk this architecture avoids by design, per streaming's natural tendency to keep only the currently-in-flight item's state resident at any given moment.

The streaming relationship is one-directional in the sense that matters architecturally: the Adapter produces, the Execution Engine consumes, and there is no meaningful flow of information in the opposite direction beyond the Execution Engine's initial invocation parameters. The Execution Engine does not send the Adapter mid-stream instructions, does not query the Adapter for its current state, and does not negotiate with it about what should happen next — the entirety of the Execution Engine's influence over a given Run's translation is exercised once, at invocation, through the Sandbox, Agent Version, Adapter Version, and Prompt Version it hands the Adapter to begin with, and, separately, through whatever cancellation or timeout signal the Execution Engine Architecture's Cancellation section already establishes as the platform's means of ending a Run's execution cooperatively.

## Interaction with the Execution Engine

The relationship this document has described piecewise throughout — invocation, streaming, conclusion — is worth stating once, holistically, as the complete interaction between these two components, because it is the single most important boundary this document defines.

The Execution Engine invokes exactly one Adapter per Run, for that Run's entire execution, and treats it as a contract-satisfying boundary rather than a specific implementation, per the Execution Engine Architecture's own Adapter Invocation section. Everything the Execution Engine does with what the Adapter produces — durable recording, sequence assignment, SSE publication — happens entirely on the Execution Engine's own side of the boundary, using mechanisms this document does not redefine and the Adapter has no visibility into. Everything the Adapter does with what the Execution Engine provides at invocation — the prepared Sandbox, the pinned versions — happens entirely on the Adapter's own side, using mechanisms the Execution Engine has no visibility into and, per this document's Position in the Architecture, is architecturally forbidden from depending on.

This mutual opacity is deliberate and symmetric. The Execution Engine does not know how a given Adapter accomplishes its translation, and the Adapter does not know how the Execution Engine accomplishes durable recording, sequence assignment, or orchestration. Each side of this boundary trusts the other to fulfill its half of the contract this document and the Execution Engine Architecture jointly define, and neither side reaches past that contract to inspect or influence the other's internals. This is what the Backend Architecture's dependency rules are, at root, protecting: a boundary this opaque in both directions is what makes it possible to change either side — a new Adapter, or a revised Execution Engine implementation — without the other needing to change in response, as long as the contract between them holds.

The one place this mutual opacity is deliberately incomplete is failure: the Execution Engine does need to know, in the classified sense the Execution Engine Architecture's Failure Model already establishes, that an Adapter has failed, distinct from the Sandbox failing or the Agent itself failing on its own terms. This document's Failure Model section below defines exactly what an Adapter is responsible for reporting when this happens, and how that report crosses the boundary without requiring the Execution Engine to understand anything about why the Adapter failed internally — only that it did, and at what point in the lifecycle.

## Interaction with the Sandbox

An Adapter's relationship to the Sandbox is the one relationship in this document that is inherently agent-specific in its mechanics, even though the platform's own guarantees about that relationship are not. The Execution Engine Architecture's Sandbox Lifecycle already establishes what every Sandbox guarantees regardless of which Adapter is operating within it: isolation from every other Run's Sandbox, ephemerality, and enforced resource limits. This document's contribution is describing what an Adapter is permitted to do with those guarantees, and what it is not.

An Adapter observes the Sandbox's state and the Agent's behavior within it, and, where the Agent's own mechanism requires it, participates in delivering the Prompt Version's content into the Sandbox and relaying the Agent's resulting actions back out. What an Adapter does not do is treat the Sandbox as a place to store its own translation state durably, or as a resource it manages the lifecycle of — Sandbox provisioning and teardown remain entirely the Execution Engine's decision, per that document's Run Lifecycle, and an Adapter's relationship to the Sandbox begins only once it has already been provisioned and prepared, and ends, functionally, once Agent execution concludes, well before the Sandbox is actually torn down.

This document reinforces, from the Adapter's side, the Execution Engine Architecture's insistence that Sandbox state is never trusted as persistent state: an Adapter that held some piece of translation-relevant information only inside the Sandbox's own filesystem or process memory, without ever reporting it across the boundary, would be creating exactly the kind of unrecoverable, untranslated state that document's Cleanup discussion already warns against. Every observation an Adapter makes inside the Sandbox is expected to be translated and reported promptly, per this document's Streaming Architecture, precisely so that nothing meaningful is still sitting only inside the Sandbox at the moment it is destroyed.

## Interaction with the Domain Model

An Adapter's only substantive relationship to the Domain Model is producing data that conforms to the Normalized Domain Model shape that document defines. This is a narrower relationship than it might first appear: an Adapter does not read from the Domain Model in any interactive sense — it does not query for a Case's details, does not look up a Run's history, and does not consult any other domain entity's current state. Everything an Adapter needs to do its job is handed to it once, at invocation, by the Execution Engine, per this document's Adapter Contract; the Domain Model's role in an Adapter's operation is purely as the specification of the shape its output must satisfy, never as a live data source it consults.

This narrowness is what the Backend Architecture's dependency rule — "Adapters depend on Domain Layer only" — actually means in practice: the dependency is on the Domain Layer's *type definitions*, the Normalized Domain Model's shape, not on any behavior, query capability, or mutable state the Domain Layer might otherwise expose. An Adapter imports what it needs to know what shape to produce; it does not import anything that would let it act as a second, informal consumer of domain data alongside the Application Layer's own, authorized access patterns.

## Versioning

Every Adapter Version is immutable once created, exactly as Schema Design and Database Design's Versioning Model already require for every versioned entity in the platform, and this document treats that immutability as specifically protecting the translation mapping this document's Normalization Model describes: once a given Adapter Version exists and has been referenced by any Run, its normalization behavior — which Agent action types map to which Normalized Domain Model shapes, and how — is permanently fixed, never adjustable after the fact even to fix a discovered translation bug.

This has a consequence worth stating explicitly, because it is easy to underestimate: a bug in how an Adapter Version translates some specific Agent behavior is not corrected by patching that Adapter Version. It is corrected by publishing a new Adapter Version with the fix, and every Run that already referenced the buggy version keeps its original, possibly-imperfect translation permanently, exactly as it was recorded. This might seem, at first, like an argument against strict immutability — surely a known translation bug should be fixed retroactively — but this document, consistent with Database Design's deletion and mutation philosophy, treats the alternative as strictly worse: a platform that silently reinterprets historical Execution Events because the Adapter Version that produced them was later revised is a platform whose historical record is no longer trustworthy, which is precisely the property every other document in this corpus has organized itself around protecting. A discovered Adapter bug is a real cost, paid honestly, once, by the Runs that happened to use the buggy version — not a cost quietly erased by rewriting history.

**Independence from Agent Version** is the second pillar of this document's versioning treatment, already established by the Domain Model and worth restating here from the Adapter's own perspective: an Adapter Version's identity, and its normalization behavior, are entirely independent of which Agent Version a given Run happens to pin alongside it. The same Adapter Version can be, and routinely is, paired with many different Agent Versions across many Runs, and a single Agent Version can, across the platform's history, be paired with several different Adapter Versions as the mapping logic is refined. This independence is what makes it possible to answer questions like "did this behavior change because the Agent's vendor shipped a new release, or because the platform's translation logic changed" — a question that would be unanswerable if Adapter and Agent were versioned as a single, coupled unit.

**What triggers a new Adapter Version** is, architecturally, any change to the translation mapping this document's Normalization Model describes — a new Agent action type recognized and translated, a corrected mapping for an existing action type, or a change in how the Adapter interprets the Agent's own completion or failure signals. It is deliberately not triggered by changes that do not affect translation behavior at all — a purely internal refactor of how the Adapter's observation mechanism is implemented, with no change to what gets translated or how, does not, by this document's reasoning, require a new Adapter Version, because Adapter Version identity exists to track behaviorally meaningful changes, not implementation churn that produces identical output.

## Compatibility

An Adapter's compatibility obligation runs in two directions this document treats as distinct concerns, worth separating explicitly.

**Compatibility with the Agent** means an Adapter Version correctly translates the specific range of Agent behavior it was built against — and, critically, this document does not assume that range is static. Agent vendors evolve their products, sometimes in ways that change the native interface an Adapter observes, independent of anything the platform controls. When a vendor's change breaks an existing Adapter Version's ability to correctly translate that Agent's behavior, this is not treated as an Adapter defect in the sense Failure Model below discusses — it is treated as a signal that a new Adapter Version, compatible with the Agent's new behavior, is needed, following the identical versioning discipline this document's Versioning section already establishes. The platform does not expect Agent vendors to preserve backward compatibility on the platform's behalf; it expects its own Adapter Versions to be revised in response when they do not.

**Compatibility with the Normalized Domain Model** means every Adapter Version, regardless of which Agent it serves or when it was created, produces output conforming to the same Normalized Domain Model shape every other Adapter Version — past, present, and future — also conforms to. This is the compatibility obligation this document's Adapter Contract already establishes as absolute, and it is what allows the Domain Model's own shape to evolve deliberately over time (through whatever process governs domain concept evolution generally) without every existing Adapter Version needing simultaneous revision — an Adapter Version conforms to the Normalized Domain Model shape as it existed at the time that Adapter Version was authored, and a shape evolution that is itself backward compatible (an added, optional field, following the same additive-evolution discipline the REST API Design already establishes for its own surface) requires no revision to existing Adapter Versions at all.

## Failure Model

**Initialization failure** occurs when an Adapter cannot establish observation of its Agent at all — a connection that cannot be made, an expected interface that is not present. This is reported to the Execution Engine immediately and unambiguously, before any Agent execution has meaningfully begun, and the Execution Engine Architecture's Failure Model already classifies this as an Adapter failure distinct from a Sandbox or Agent failure, precisely because this document's Adapter Topology identifies initialization as entirely the Adapter's own concern.

**Translation failure** occurs mid-execution, when an Adapter observes something it cannot correctly map onto the Normalized Domain Model — an Agent action type the Adapter Version does not recognize, or an internal error in the Adapter's own translation logic. This document treats translation failure as more delicate than initialization failure, because it occurs after real, meaningful Agent behavior has already been faithfully translated and reported — discarding that already-reported partial history would violate this document's Translation Model completeness property retroactively. An Adapter encountering a translation failure reports the failure explicitly, as its own distinct signal, rather than silently dropping the unrecognized action and continuing as though nothing happened; what the Execution Engine does with that report — whether the Run's already-recorded partial history stands as the Run's terminal record, per the Execution Engine Architecture's own handling of this exact scenario — is the Execution Engine's decision, not the Adapter's, consistent with this document's repeated insistence that Adapters report, and Execution Engines decide.

**Agent-signaled failure** is not, in this document's vocabulary, an Adapter failure at all — it is the Agent's own legitimate outcome, translated faithfully by a fully functioning Adapter into the platform's vocabulary for "the Agent reported it could not complete this task." This distinction matters enormously, because conflating an Agent failing to solve a Case with an Adapter failing to do its job would corrupt exactly the classification the Backend Architecture's Error Handling Philosophy insists on preserving: a Run where the Agent tried and failed is a valid, gradable outcome; a Run where the Adapter itself broke is a platform-caused failure with no legitimate signal about the Agent's actual capability.

**Reporting failure** — a translated event or artifact that the Adapter attempted to hand across the boundary but which the Execution Engine could not durably record, for reasons entirely on the Execution Engine's own side (an infrastructure failure, per that document's Failure Model) — is not, symmetrically, an Adapter failure either. The Adapter's obligation is to attempt reporting faithfully and promptly; what happens to that report once it crosses the boundary is governed entirely by the Execution Engine Architecture's own durability and retry discipline, and this document does not ask an Adapter to independently verify or retry a report the Execution Engine has already accepted for durable recording.

## Retry Philosophy

An Adapter does not retry anything on its own initiative — every retry decision this platform makes is owned by the Execution Engine, per that document's own Retry Philosophy, and an Adapter's role in any retry is passive: if a Run is retried (a fresh Sandbox provisioned, a new attempt at execution begun), that retry invokes the Adapter fresh, exactly as any new invocation would, with no memory of, or relationship to, whatever the previous attempt's Adapter invocation did or reported.

This is a deliberate consequence of the statelessness this document's Adapter Philosophy already establishes: an Adapter holds no durable state between invocations, which means there is architecturally nothing for an Adapter-level retry mechanism to resume from even if this document wanted to introduce one. A retried Run's Adapter invocation is, from the Adapter's own perspective, indistinguishable from a first attempt — it observes a fresh Sandbox, translates what it observes, and reports it, with no notion that this might be the second or third time this specific Run has reached this point.

Where an Adapter's own initialization or translation failure is the reason a Run needs to be retried at all, this document does not ask the Adapter itself to decide whether that retry should happen — that decision belongs entirely to the Execution Engine, informed by the classified failure report this document's Failure Model establishes, following the exact retry-versus-terminal-failure policy the Execution Engine Architecture's own Retry Philosophy already lays out. An Adapter's only obligation in this entire process is to report its failure clearly enough that the Execution Engine can make that decision correctly.

## Resource Ownership

An Adapter does not own or provision compute, memory, or storage resources of its own — every resource an Adapter's execution consumes is consumed within the Sandbox's own resource envelope, enforced by the Sandbox itself, per the Execution Engine Architecture's Resource Accounting. This document draws this line deliberately: an Adapter that maintained its own, separate resource allocation, outside the Sandbox's enforced limits, would be a second, unaccounted-for consumption surface the platform's resource-accounting architecture has no visibility into, undermining the very guarantee Resource Accounting exists to provide.

What an Adapter does own, in a narrower sense, is the transient, in-memory state it needs to perform translation currently in flight — buffering a partially observed action until enough of it has arrived to translate confidently, for instance. This document treats this kind of transient state as fundamentally different from durable state: it is expected to be small, bounded, and short-lived, discarded immediately once the corresponding translation is reported across the boundary, never accumulated across the Run's full duration in a way that would make an Adapter's own memory footprint grow unboundedly as execution proceeds. An Adapter whose transient state grows without bound over a long-running Run's execution has, in effect, violated the streaming discipline this document's Streaming Architecture section already establishes, even if no single translation step was individually at fault.

## Security

An Adapter operates at the platform's most sensitive trust boundary: it is the one component whose correct behavior determines whether untrusted, Sandbox-contained code can influence anything outside that Sandbox. This document treats an Adapter's own code as trusted platform code — unlike the Agent it observes, an Adapter is written and reviewed by the platform's own engineers, not supplied by a third party — but treats everything an Adapter *observes* as untrusted, and every translation decision as an opportunity for that untrusted content to attempt to influence something it should not.

**Input from the Sandbox is never trusted implicitly.** An Adapter translating an Agent's tool-call arguments, file contents, or output does not assume that content is well-formed, bounded in size, or free of anything an Agent might have deliberately or accidentally produced to disrupt the platform's own processing — malformed data, unexpectedly large payloads, or content crafted to exploit a parsing weakness in the Adapter's own translation logic. An Adapter's translation logic is written defensively against exactly this possibility, treating the Sandbox as an adversarial input source even when a given Agent is, in practice, well-behaved.

**Translation never grants the Sandbox reach beyond its boundary.** The one-directional reporting relationship this document's Streaming Architecture establishes is itself a security property, not merely an architectural convenience: because an Adapter only ever sends data outward, in the fixed, platform-defined Normalized Domain Model shape, there is no mechanism by which something the Agent does inside the Sandbox can cause the Adapter to execute arbitrary platform-side behavior on the Agent's behalf. The Adapter interprets and translates; it never executes, on the platform's own infrastructure, anything the Agent itself directed it to do.

**An Adapter's own credentials and secrets, where an Agent integration requires them (an API key for a hosted Agent, for instance), are scoped as narrowly as the specific Agent integration requires, and never exposed to the Sandbox or, therefore, to the Agent itself.** This document treats this as an absolute boundary: whatever an Adapter needs to authenticate with an Agent's own service is a platform-held credential the Adapter uses on the platform's behalf, never something the Agent, operating inside the Sandbox, is permitted to observe or extract.

## Observability

Every Adapter invocation is correlated, per the Execution Engine Architecture's Observability section, to the same correlation identifier established at Run creation and threaded through every component this document's Adapter Topology and Position in the Architecture describe — an Adapter's own logging, wherever it exists, carries that identifier so that an engineer reconstructing a Run's operational history can see the Adapter's contribution alongside everything the Execution Engine, Sandbox, and Grading Pipeline separately produced.

**Translation-specific observability** is worth calling out as its own category, distinct from the general execution-timing metrics the Execution Engine Architecture already establishes: how many events a given Adapter Version produces per Run, how large its Artifacts tend to be, and how often it encounters an unrecognized action type (a leading indicator, often, of an Agent vendor's behavior having changed in a way this document's Compatibility section anticipates) are all signals specific to an Adapter's own behavior, worth measuring per Adapter Version rather than only in aggregate, since a translation-quality regression in one specific Adapter Version should be visible and attributable to that version specifically, not blended into a platform-wide average that could mask it.

**Failure-classification observability**, tracking how often each of this document's Failure Model categories (initialization, translation, Agent-signaled) actually occurs, per Adapter Version, is what lets the platform's operators distinguish a genuinely unreliable Adapter Version from an Agent whose own task success rate happens to be low — exactly the distinction this document's Failure Model exists to make possible in the first place, made concrete here as something worth actually measuring rather than only architecturally correct in principle.

This document does not specify the mechanisms — logging framework, metrics backend, tracing system — through which any of this observability is delivered, consistent with the Execution Engine Architecture's own restraint on this exact question; it establishes only what is worth observing about an Adapter's behavior specifically, leaving how to a future, dedicated Observability Architecture document.

## Scalability

An Adapter's scalability story is, architecturally, almost entirely inherited from the Execution Engine Architecture's own: because an Adapter holds no durable state and consumes resources only within its Sandbox's already-accounted-for envelope, per this document's Resource Ownership section, there is no separate scaling dimension an Adapter introduces beyond however many Runs, and therefore however many concurrent Sandboxes and Adapter invocations, the platform's worker pool is already provisioned to support.

The one scalability-relevant property specific to this document is that an Adapter Version's translation logic must perform its work within whatever time budget the Run's overall execution timeout allows, per the Execution Engine Architecture's Resource Accounting — an Adapter that translates slowly, relative to the pace at which the Agent it serves actually produces observable actions, risks becoming the limiting factor in a Run's own execution timing, distinct from and attributable separately from however long the Agent itself took to act. This is precisely why this document's Observability section calls out execution-duration attribution as something worth measuring per Adapter Version specifically: a platform running many concurrent Adapters across many concurrent Runs needs to be able to tell, at scale, whether a slowdown originates in a specific Adapter's own translation performance or somewhere else in the pipeline entirely.

## Extensibility

Every principle in this document converges on the same extensibility claim Adapter Philosophy opened with: onboarding a new Agent means authoring a new Adapter that satisfies this document's Adapter Contract, and nothing else in the platform changes as a result. This section makes that claim concrete against the specific extensibility scenarios this corpus has already anticipated.

**A future Adapter SDK**, anticipated by Schema Design's Future Extensions and the Domain Model's Extensibility Model, formalizes this document's Adapter Contract into a versioned, externally documented interface — but it does not change the contract's shape, only its degree of formality and, potentially, who is capable of authoring a conforming Adapter. Everything this document establishes about translation, normalization, streaming, versioning, and failure classification remains exactly as true of an SDK-authored Adapter as of a platform-team-authored one, because the SDK's entire purpose is to make satisfying this document's existing contract easier, not to introduce a different one.

**New Agents entirely unlike anything the platform currently supports** — an Agent with a fundamentally different interaction model than any Adapter has yet had to translate — are accommodated by this document's Normalization Model discussion of what happens when an Agent's native behavior does not map cleanly onto the existing Normalized Domain Model shape: the Domain Model evolves deliberately, through its own established process, and every existing Adapter Version remains valid against the shape as it existed when that Adapter Version was authored, per this document's Compatibility section, while new Adapters take advantage of whatever the Domain Model's evolution newly makes expressible.

**Multiple Adapters per Agent**, should some future need arise (distinct integration strategies for the same underlying Agent product, for instance), is compatible with this document's architecture without modification: the Domain Model's one-to-one connection between an Agent and its Adapter, established elsewhere in this corpus, is the current relationship this document assumes, and nothing in this document's own translation, versioning, or invocation architecture would need to change if that cardinality were ever revisited — this document's contract is defined per Adapter, not per Agent, and remains equally valid regardless of how many Adapters ultimately connect to a given Agent.

## Non-Goals

This document defines the architecture governing the Adapter Layer; it does not define how any specific Adapter is actually implemented. It does not specify the observation mechanism any Adapter uses to perceive Agent behavior inside a Sandbox — whether that means intercepting API calls, watching filesystem events, or consuming a vendor-provided event stream is an implementation decision made per Agent, against this document's contract, not part of it. It does not provide interfaces, type signatures, or any code-level specification of the Normalized Domain Model's shape, which remains entirely the Domain Model's own responsibility, referenced here by name and never redefined. It does not specify SDK design for a future Adapter SDK beyond the Extensibility section's architectural anticipation of one. It does not specify how any given vendor's API is actually invoked, authenticated against, or rate-limited — those are per-Agent implementation concerns entirely outside this document's scope. It does not specify logging, metrics, or tracing implementation, beyond naming what is worth observing in this document's Observability section. It does not define Execution Engine internals, Sandbox provisioning mechanics, or persistence mechanics, all of which remain exactly as the Execution Engine Architecture, Database Design, and Schema Design already establish them, referenced here only at the boundary where an Adapter touches them. And it does not include diagrams, pseudocode, or implementation examples of any kind, consistent with every architecture document in this corpus treating those as artifacts of a later, separate implementation effort, not of the architecture itself.
