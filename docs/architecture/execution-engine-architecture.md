# Execution Engine Architecture

## Purpose

Every prior document treats the Execution Engine as a name — a standing capability, invoked by Background Workers, that turns a queued Run into a graded one. The Backend Architecture defines its place in the dependency graph. The Domain Model defines what it is responsible for producing. The Database and Schema Design documents define what its output looks like once persisted. None of them define how it actually does its work: how a Run's lifecycle actually advances from creation to a terminal state, what guarantees hold at each step, what happens when a step fails partway through, and why the pipeline is shaped the way it is rather than some simpler alternative. That is the gap this document closes.

The Execution Engine deserves this treatment because it is architecturally unlike every other part of the platform this corpus has described so far. The API surface, the Application Layer's use cases, and the relational schema are all, in their different ways, dealing with well-behaved, deterministic operations against a database — validate, authorize, persist, respond. The Execution Engine is dealing with the opposite: a multi-minute, multi-step process that hands control to untrusted, non-deterministic third-party software running inside a sandbox, over a network, with no guarantee that any given step will succeed, complete promptly, or behave the same way twice. A subsystem with that risk profile needs its own explicit architecture, because the failure modes it has to survive are qualitatively different from anything a CRUD-shaped API or a normalized schema has to reason about on its own.

This document sits directly beneath the Backend Architecture's Background Execution Flow, which already sketched the high-level sequence — queue submission, worker execution, status updates, grading, persistence — at the granularity appropriate to a codebase-organization document. This document takes that sketch and gives it the architectural depth a team actually building the Execution Engine needs: what orchestration means here, what a worker is and is not trusted to do on its own, how the Sandbox's ephemeral nature is enforced rather than merely assumed, how Execution Events and Artifacts are produced durably under concurrent and unreliable conditions, how grading is scheduled and isolated, and how every failure mode this subsystem will encounter in production is handled by design rather than discovered by incident. Everything here is a refinement of what the prior documents already established, never a redefinition of it — where this document uses a term the Domain Model or Schema Design already defined, it means exactly what those documents said it means.

## Execution Philosophy

**Deterministic orchestration over non-deterministic execution.** The Agent under evaluation is permitted to behave unpredictably — that unpredictability is, in fact, exactly what the platform exists to measure. The orchestration that wraps that Agent's execution is not permitted the same latitude. Given the same Run, the same pinned versions, and the same sequence of external outcomes (the Adapter's translated actions, the Sandbox's responses), the Execution Engine's own control flow — which state comes next, what gets persisted when, what triggers a transition — must be the same every time. This separation is what makes it possible to reason about the platform's reliability at all: if orchestration itself were as unpredictable as the Agents it evaluates, no failure could ever be attributed with confidence to the Agent rather than to the platform, which would corrupt the very comparisons the platform exists to produce.

**Stateless workers, stateful Runs.** A worker process holds no durable state of its own between tasks — everything it needs to resume or reason about a Run's progress is either passed to it when it picks up a task or is already recorded, durably, against the Run itself. This is the same statelessness principle the REST API Design applies to API requests, applied here to the execution side of the platform for an identical reason: a worker that depended on in-memory state accumulated since it started would be a worker that could not crash and be replaced without losing information, and a worker that cannot safely crash is a worker this platform cannot tolerate, given how long a single Run's execution can run and how many independent workers must be able to pick up where another left off.

**Append-only execution history as the mechanism of truth, not merely a storage convention.** Schema Design already establishes that Execution Events are insert-only rows. This document treats that as more than a storage rule — it is the architectural reason the Execution Engine does not need a separate "what actually happened" ledger distinct from what it persists. Every meaningful thing that occurs during a Run's execution becomes an Execution Event, in strict order, and nothing about the platform's understanding of a Run's history is ever derived from anything other than that sequence. This is what makes a Run's execution reconstructable after the fact without needing to have observed it live.

**The immutable execution record as the platform's actual deliverable.** The Agent's output — a diff, a passing or failing test suite — matters, but the record of how that output was produced matters just as much, because the platform's value is comparative and longitudinal, not just outcome-reporting. The Execution Engine is, in a real sense, building a permanent record with every Run it drives, and every other property in this section exists in service of that record being trustworthy: complete, correctly ordered, and never retroactively alterable.

**Separation between orchestration and execution.** The component that decides what should happen next (provision a Sandbox, invoke the Adapter, persist an event, transition a status) is architecturally distinct from the components that actually do those things (the Sandbox itself, the Adapter, the persistence layer). This mirrors the Backend Architecture's own dependency-direction discipline: the Execution Engine orchestrates, but it does not itself contain sandbox-provisioning logic, agent-translation logic, or persistence logic — those live in the components it invokes. This separation is what keeps a change to how Sandboxes are provisioned from having any effect on how a Run's lifecycle is orchestrated, and vice versa.

**Reliability over throughput, as a default posture, not an excuse.** Given a choice between an execution path that is marginally faster but introduces a new way for a Run's record to end up incomplete or ambiguous, and one that is slower but keeps that record unambiguous under every failure this document's Failure Model anticipates, this architecture chooses the latter, every time, without needing case-by-case justification. This is not a statement that throughput does not matter — Scalability, later in this document, takes it seriously — it is a statement about which property yields when the two are genuinely in tension, and it is stated up front because it is the tiebreaker nearly every subsequent design decision in this document actually rests on.

**Reproducibility, bounded honestly.** The Execution Engine reproduces every input to a Run exactly — the pinned Case Version, Prompt Version, Agent Version, and Adapter Version are, by construction, identical every time a Run referencing them is inspected. It does not, and architecturally cannot, guarantee that re-running the same inputs against a live Agent produces the same output, because the Agent itself is the one component in this pipeline whose determinism the platform does not control and is explicitly not trying to control — controlling it would defeat the purpose of evaluating a real agent's real behavior. Reproducibility, in this architecture, means the inputs and the record of what happened are permanently fixed and fully knowable, not that the Agent's behavior is guaranteed to repeat.

**Observable execution as a first-class design constraint, not an add-on.** Every state the Execution Engine passes through, and every event it produces along the way, exists partly because someone — an engineer debugging a failure, a user waiting on a Run, a Grader consuming the record afterward — needs to be able to see it. A pipeline that worked but produced no legible trace of how it worked would fail this architecture's actual purpose just as surely as a pipeline that failed outright, because an unobservable success in a platform whose entire value is trustworthy comparison is not meaningfully different from an untrustworthy one.

**Isolation, at every boundary that matters.** A Run's execution is isolated from every other Run's execution (no shared Sandbox, no shared mutable state), a Grader's execution is isolated from every other Grader's execution during the grading phase, and the platform's own orchestration is isolated from the untrusted code running inside a Sandbox. Isolation is treated here as a graded property applied deliberately at each of these boundaries, rather than a single blanket guarantee, because the risk and consequence of a failure differs at each one, and the isolation mechanism appropriate to containing a misbehaving Agent is not automatically the right one for containing one Grader's bug from affecting another's Score.

**Resumability wherever the underlying step allows it, honesty wherever it does not.** A worker crash between two already-completed steps should never require redoing work that already succeeded and was already durably recorded — the orchestration resumes from the last durably-recorded state, not from the beginning. But not every step is resumable in a meaningful sense: a Sandbox that was mid-execution when its host worker crashed cannot be resumed, because the Sandbox itself is gone and its in-progress work was never durable in the first place. This architecture is explicit about which of these two situations applies at every step, rather than pretending resumability is uniform across a pipeline where it structurally cannot be.

**Failure containment as the organizing principle beneath every other one in this list.** A failure at any single point in this pipeline — a Sandbox crash, an Adapter bug, a single Grader's exception — is designed to be contained to the smallest scope that failure actually affects, never allowed to cascade into corrupting or blocking work that failure had nothing to do with. This principle recurs throughout this document because it is, more than any other, what keeps a platform running thousands of concurrent, long-running, third-party-code-executing pipelines operable in practice rather than only in theory.

**Execution is authoritative; presentation is derived.** Everything a human or client ever sees about a Run — a dashboard's summary, a live SSE progress indicator, a status badge, a rendered log view, a report, a trend chart — is a derived projection of the execution record this pipeline produces, never an input to it and never a system this pipeline depends on to function correctly. The execution pipeline does not query a dashboard to decide what to do next, does not wait on a progress indicator's state, and does not shape what it records based on how that record will later be displayed. This ordering is not incidental: it is what keeps the Execution Engine's correctness independent of the availability, correctness, or even the existence of any specific presentation surface. A dashboard can be redesigned, an SSE stream can be dropped, a reporting pipeline can be entirely rebuilt, and none of it touches what this document's execution pipeline does or how reliably it does it — because presentation reads from the execution record, strictly downstream, and the execution record has no reciprocal dependency on anything that reads it.

## Responsibilities

The Execution Engine owns the orchestration of a single Run's journey from queued to terminal: deciding what step comes next, invoking the components each step requires, and ensuring that every fact worth recording along the way is recorded durably before the step is considered complete. It owns the decision of when a Sandbox is provisioned and when it is torn down. It owns the invocation of exactly one Adapter per Run, and the translation of that Adapter's output into the sequence of Execution Events and Artifacts that become the Run's permanent record. It owns the transition of a Run's status through the states this document's Run Lifecycle and State Transitions sections define, and it owns detecting and classifying the failure modes this document's Failure Model enumerates, so that a Run's terminal state correctly reflects what actually happened.

The Execution Engine deliberately does not own vendor-specific translation logic — that lives entirely inside the Adapter Layer, which the Execution Engine invokes as a boundary it does not look behind, per the Backend Architecture's dependency rules. It does not own grading logic — the Grader Layer determines how a completed Run is scored, and the Execution Engine's role in grading, detailed later in this document, is scheduling and isolation, not judgment. It does not own persistence mechanics — it calls through the same Application-Layer-mediated, Infrastructure-implemented contracts every other part of the backend uses, never talking to PostgreSQL, object storage, or the queue directly, consistent with the Backend Architecture's dependency direction. It does not own authorization or API-facing concerns of any kind — by the time a task reaches the Execution Engine, the Application Layer has already authorized the Run's creation, and the Execution Engine's job begins after that authorization has already happened. And it does not own the underlying compute substrate a Sandbox runs on — provisioning a Sandbox is a capability the Execution Engine invokes through its own boundary, exactly as it invokes an Adapter, without itself containing the mechanics of how that compute is actually supplied.

This division exists for the same reason the Backend Architecture draws every other module boundary the way it does: a component with a narrow, clearly bounded responsibility can be reasoned about, tested, and evolved independently of the components around it. An Execution Engine that also contained adapter logic, or grading logic, or sandbox-provisioning mechanics, would be a component nothing could safely change in isolation — exactly the kind of coupling the platform's modular-monolith architecture exists to prevent.

## Execution Topology

The Responsibilities above describe what the Execution Engine owns in isolation; this section describes how it sits among the six other components a Run's execution actually touches, and why each of those components occupies the position in the topology that it does rather than some other arrangement.

The **Queue** is the durable handoff point between a Run's creation and the start of its execution, and its architectural role is scheduling *delivery*, not scheduling *execution*: it decides which worker receives which task and when that task becomes visible for claiming, but it has no awareness of what a Run actually is, what it will take to execute, or what should happen once a worker has claimed it. The Queue's entire relationship to the rest of this topology is upstream of the Worker — it hands off a task and is otherwise uninvolved until that task either completes or, on a crash, becomes eligible for redelivery.

The **Worker** is the execution context that hosts orchestration for whichever Run's task it currently holds. A Worker does not itself decide what a Run should do next — it does not contain workflow logic of its own — it exists to give the Execution Engine's orchestration a running process to execute inside, and its defining property, per the Worker Model, is that it is disposable: any Worker can host any Run's orchestration, and no Worker is architecturally distinguished from any other. In this topology, the Worker is best understood as a chassis, not a decision-maker.

The **Execution Engine** is the orchestration authority that actually runs inside a Worker once a task is claimed, and it occupies the center of this topology for exactly one reason: it is the one component that knows the full sequence a Run must pass through and coordinates every other component accordingly. Where the Queue only knows about task delivery and the Worker only knows about hosting, the Execution Engine knows that Sandbox provisioning must precede Agent execution, that Agent execution must precede grading, and that every step in between must be durably recorded before the next one begins. Every other component in this topology is, from the Execution Engine's perspective, a boundary it invokes and waits on — never a peer it coordinates with as an equal, and never a component it delegates its own sequencing authority to.

The **Sandbox** is the one component in this topology that executes untrusted code, and its position — invoked by the Execution Engine, never invoking anything back into the platform on its own initiative — is what keeps that untrusted execution contained. The Sandbox does not talk to Persistence, does not talk to the Queue, and does not talk to Graders; everything it produces leaves it through exactly one channel, the Adapter, which is the only component positioned to observe what happens inside it.

The **Adapter** sits directly between the Sandbox and the Execution Engine, and its position in this topology is what makes the rest of the pipeline agent-agnostic: it is the only component that understands the Sandbox's Agent-specific reality on one side, while presenting the Execution Engine with the platform's Normalized Domain Model on the other. Nothing downstream of the Adapter — the Execution Engine's orchestration, Persistence, the Graders — ever needs to know which Agent produced what it is looking at; the Adapter's position in the topology is precisely what absorbs that distinction before it can propagate any further.

**Persistence** is the component that records the authoritative history the rest of this topology exists to produce, and its position is deliberately passive: it never initiates anything, never decides when a Run should advance, and is invoked exclusively by the Execution Engine, through the Application-Layer-mediated contracts the Backend Architecture already establishes. Every other component in this topology is, in a real sense, working to feed Persistence a correct and complete record — the Queue by ensuring a task is not lost before a Worker claims it, the Sandbox and Adapter by producing an accurate translation of what occurred, the Execution Engine by sequencing all of it correctly — but Persistence itself does no work beyond durably recording exactly what it is given.

**Graders** are the topology's downstream consumers, positioned to read from Persistence only after the Execution Engine has determined a Run's execution is complete. A Grader never observes the Sandbox, the Adapter, or the Queue directly, and never participates in execution itself — its entire relationship to this topology is reading the completed, immutable record Persistence now holds and writing back a Score through the identical Execution-Engine-mediated path every other write in this topology uses. This positioning is what makes a Grader's view of a Run always complete and never partial: by the time any Grader is invoked, everything upstream of Persistence has already finished its work for that Run.

Read together, this topology has a single directional shape: the Queue hands a task to a Worker, the Worker hosts the Execution Engine, the Execution Engine coordinates the Sandbox and Adapter to produce a record, that record flows into Persistence, and Graders read from Persistence once the Execution Engine has closed execution out. No component in this topology reaches backward past the one that invoked it, and no component skips the Execution Engine to coordinate directly with another — which is the topological expression of the centralized-orchestration principle the Orchestration Model section below establishes in more detail.

## Run Lifecycle

**Run creation** happens entirely outside the Execution Engine's scope, at the Application Layer, per the Backend Architecture's Request Flow — a Run is created with all five of its pinned version references fixed, in a queued state, and the Execution Engine's involvement begins only once that Run has already been durably persisted and enqueued. This ordering matters architecturally: the Execution Engine never operates on a Run whose identity or pinned inputs are not yet fully and durably established, which is what allows every subsequent step to trust that the Run it is working on is fully specified from the moment it first encounters it.

**Queueing** places a task, referencing the Run's identifier, onto the broker described in the Backend Architecture's Background Execution Flow. The Execution Engine treats this queue as a durable handoff point, not a transient one — a task sitting in the queue represents a Run whose execution has not yet started, and the queue's own durability (rather than any in-memory state on the API process that created the Run) is what guarantees that Run will eventually be picked up even if every process that existed at creation time has since restarted.

**Scheduling**, in the narrow sense of which worker picks up which task and in what raw order, is the queue's own concern, not the Execution Engine's — governed by the broker and the worker pool's own consumption behavior, discussed further in Scalability. The policy that shapes *how* that delivery behaves — concurrency limits, fairness, prioritization, and the other platform-owned concerns detailed in Scheduling Philosophy below — is a separate, platform-owned layer sitting above the broker's raw delivery mechanism, not a property of the queue itself. The Execution Engine's lifecycle, from this point forward, is described from the perspective of a single Run once some worker has claimed it, not from the perspective of how that claim was arbitrated among competing workers or shaped by platform policy.

**Worker pickup** is the moment a Background Worker claims the task and hands control to the Execution Engine for that specific Run. The Execution Engine's first responsibility at this point is to transition the Run's status from queued to running, durably, before doing anything else — this ordering is deliberate: a Run must never be observably "being worked on" from the Sandbox's perspective while still reporting a queued status to anyone watching it, since that would be exactly the kind of discrepancy between the live and the authoritative record this document's Execution Philosophy rules out.

**Sandbox provisioning** follows immediately, and is treated as its own explicit, observable step rather than an implicit precondition folded into Agent execution — provisioning can itself fail (resource exhaustion, a provisioning-layer outage), and treating it as a named step means that failure is attributable to provisioning specifically, not conflated with a failure that occurred once the Agent was already running. The full architectural treatment of what provisioning guarantees is given in Sandbox Lifecycle below.

**Repository preparation** checks out the Case Version's reference repository state into the freshly provisioned Sandbox, establishing the exact starting point the Agent will work from. This step's completion is what makes the Run's eventual diff meaningful — everything the Agent changes is measured relative to this specific, version-pinned starting state, and getting this step wrong (an incomplete checkout, a mismatched reference) would silently corrupt every downstream measurement of what the Agent actually did.

**Adapter initialization** hands control, for the first time, to the one Adapter Version this Run pinned — the Execution Engine invokes it against the now-prepared Sandbox and the Run's other pinned inputs (Agent Version, Prompt Version), establishing whatever the Adapter needs internally to begin translating the Agent's native behavior into the Normalized Domain Model. What happens inside this initialization is entirely the Adapter's concern, per Adapter Invocation below; the Execution Engine's responsibility here is limited to invoking it correctly and observing whether initialization itself succeeded.

**Prompt delivery** is the point at which the Prompt Version's content is actually handed to the Agent, through the Adapter, inside the Sandbox — the first moment the Agent under evaluation receives the instruction it will act on. This is a named, observable step for the same reason repository preparation is: prompt delivery can itself be where a failure originates (a delivery mechanism that times out, an Agent that rejects malformed input), and naming it lets that failure be attributed precisely.

**Agent execution** is the longest and least predictable step in the entire lifecycle — the Agent acts, inside the Sandbox, for as long as it takes (bounded by the timeout policy this document's Failure Model discusses), producing the tool calls, file edits, and output that the Adapter continuously translates. This step is where the platform's core measurement actually happens, and it is also, correctly, the step over which the Execution Engine exercises the least direct control, because exercising more control than "observe and record" here would mean interfering with the very behavior the platform exists to measure.

**Execution Event recording** happens continuously throughout Agent execution, not as a single step after the fact — every translated action the Adapter produces becomes an Execution Event, persisted in strict sequence, as detailed in Event Production below. This is deliberately interleaved with Agent execution in the lifecycle's description, rather than listed as a separate later step, because that is architecturally what it is: a continuous side effect of execution, not a discrete phase that follows it.

**Artifact persistence** occurs alongside Execution Event recording, whenever a translated action's payload is large enough to warrant Artifact storage rather than inline event metadata, per Database Design's Storage Strategy. Like event recording, this is continuous during execution, not a separate terminal phase.

**Execution completion** is reached when the Agent signals it is finished, or when the Execution Engine's own timeout or cancellation policy ends execution first — either way, this is the step where the Sandbox's work concludes and the Execution Engine transitions the Run out of active execution. What "completion" means at this step is deliberately broad: it covers an Agent that finished normally, one that was terminated by timeout, and one that failed outright, because all three converge on the same next step — the Sandbox's work is over, and what happens next is determined by classification, not by which of these three paths led here.

**Grading** begins once execution has concluded, transitioning the Run's status accordingly, and invokes every Grader the Run's Case Version declared applicable (per Schema Design's Case Grader Declaration), each independently, as detailed in the Grading Pipeline section below.

**Score persistence** happens as each Grader completes, written durably through the same Application-Layer-mediated path every other write in this pipeline uses, never through a shortcut the Execution Engine invents for itself.

**Terminal completion** is the Run's final status transition — to a completed, failed, or cancelled state, per the Domain Model's lifecycle and this document's State Transitions section — after which the Run is permanently closed, per Schema Design's immutability rules, to any further Execution Event, Artifact, or Score.

## Orchestration Model

Orchestration in this architecture is centralized in the sense that exactly one logical authority — the Execution Engine, invoked by whichever worker claimed a given Run — decides what step that Run takes next at any given moment. This is a deliberate rejection of a choreographed alternative, where each component (Sandbox, Adapter, persistence layer) might independently decide when to hand off to the next based on events it observes. Choreography can look attractive for its apparent decoupling, but for a pipeline whose entire purpose is producing a trustworthy, ordered record of what happened, it trades that decoupling for something this architecture is not willing to give up: a single place where "what should happen next for this Run" is decided, and therefore a single place where the correctness of that decision can be reasoned about and tested. Centralized orchestration is what makes Run Lifecycle's thirteen steps a genuine sequence rather than an emergent, harder-to-verify property of several components' independent behavior.

Workers remain stateless specifically so that this centralization does not become a scalability or reliability bottleneck. Orchestration is centralized *per Run*, not centralized onto a single always-running process for the whole platform — any worker, picking up any Run's task, becomes that Run's orchestration authority for as long as it holds the task, and hands that authority to whichever worker next picks up the Run (after a crash, or at a natural step boundary) without needing to coordinate with any other worker about it. This is what reconciles "centralized decision-making for a given Run" with "horizontally scalable across many concurrent Runs" — the two are not in tension, because centralization is scoped to the individual Run, and there are, at any given moment, as many independent orchestration authorities active as there are Runs currently executing.

Orchestration coordinates multiple subsystems — the Sandbox, the Adapter, the persistence layer, eventually the Grader Layer — without absorbing any of their internal logic into itself. It knows, for a given step, which subsystem to invoke and what durable fact must be recorded before advancing, but it does not know, and architecturally must not know, how the Sandbox provisions compute, how the Adapter translates a specific vendor's tool-call format, or how a Grader evaluates a rubric. This is the practical meaning of "orchestration contains workflow rather than business logic": the Execution Engine's own code should read as a sequence of steps and the durability guarantees between them, not as a place where any subsystem's actual logic has been inlined for convenience. A change to how a Grader scores something should never require touching the Execution Engine's orchestration code, and a change to the Execution Engine's step sequence should never require touching a Grader's internal logic — if either becomes necessary, it is a sign the boundary between orchestration and the subsystem it invokes has eroded.

## Scheduling Philosophy

Run Lifecycle already establishes that *which worker* picks up *which task*, and in what raw order, is the queue's own concern — a mechanical, delivery-level decision the broker is well suited to make. It does not follow that the queue owns *execution policy*, and this distinction matters enough to this architecture that it deserves separating explicitly: a broker knows how to hand a task to an available worker; it has no notion of a Project's fairness entitlement, a Run's relative priority, or the platform's current willingness to spend Sandbox capacity on a given kind of workload. Those are business and operational concerns the platform itself owns, expressed as policy the scheduling layer enforces, never left to whatever behavior a broker happens to exhibit by default.

**Concurrency limits** — how many Runs may execute simultaneously, platform-wide or within some narrower scope — are a platform-owned policy for the same reason Sandbox resource limits are platform-owned: unconstrained concurrency would let the execution subsystem's demand for Sandbox and grading capacity grow without bound, and the platform, not the broker, is the party positioned to know what that capacity actually is at a given time.

**Project fairness** ensures that one Project's burst of Run creation does not starve every other Project's Runs of worker attention indefinitely — this is a policy decision about how the platform wants to allocate a shared, finite resource across tenants, and a broker operating purely on delivery order (first queued, first claimed) has no notion of "tenant" at all, let alone a fairness policy governing them. Enforcing fairness is therefore a scheduling policy layered on top of the queue's raw delivery mechanism, not a property the queue provides on its own.

**Workload prioritization** — allowing some Runs (a time-sensitive comparison a user is actively waiting on, for instance) to be picked up ahead of others in the same queue — is likewise a platform policy, informed by business context the broker does not and should not need to understand. The queue's delivery mechanism is the enforcement point such a policy is applied through, but the policy itself — what counts as higher priority, and how much a higher-priority Run is allowed to preempt lower-priority ones — is decided by the platform.

**Execution quotas** — bounding how much execution a given Project, Agent, or caller is entitled to consume over a window of time — are an extension of the same principle: a quota is a statement about acceptable resource consumption at the business level, and enforcing it requires the scheduling layer to know something about a Run's origin and history that a generic broker has no visibility into on its own.

**Resource-aware scheduling** — routing a Run to a worker or worker pool that actually has the Sandbox or grading capacity that Run's requirements demand, rather than treating every worker as interchangeable regardless of current load — is a platform-owned refinement on top of the queue's basic claim mechanism, informed by the platform's own visibility into current resource pressure across its worker pools.

**GPU routing**, anticipated as a future extension per Extensibility below, is a specific instance of resource-aware scheduling: routing a Run whose Agent or Grader requires GPU-backed compute to a worker pool or Sandbox provisioning path capable of supplying it. This document does not specify how that routing decision is made, only that it is, architecturally, the platform's scheduling policy to own, exactly like every other resource-aware routing decision described above.

**Worker pool selection**, where multiple worker pools exist (per the Backend Architecture's anticipated segmentation by resource class), is the scheduling-policy decision of which pool a given task belongs in — a decision made once, based on the Run's known characteristics, before the task is ever handed to the queue's own delivery mechanism for that pool. The queue, once a pool has been selected, still owns only delivery within that pool; pool selection itself remains upstream, platform-owned policy.

Across every item above, the pattern is the same: the queue is a mechanism, not a policymaker, and every question that requires knowing something about the business — which Project this is, how urgent this Run is, how much capacity the platform currently has to spare, what kind of compute a Run actually needs — is answered by the platform before or alongside the queue's own delivery decision, never left for the broker to infer or default into on its own.

## Worker Model

A worker's responsibility, from the Execution Engine's perspective, is to claim a task, instantiate the Execution Engine's orchestration for the Run that task references, and drive that orchestration forward until either the Run reaches a step boundary durable enough to safely release the worker (in practice, most commonly, the Run reaching a terminal state, though intermediate durable checkpoints are possible) or the worker itself is no longer able to continue, at which point the task's visibility timeout expires and another worker becomes eligible to claim it. A worker does not decide business logic beyond invoking the orchestration correctly — it is a thin, disposable execution context for whatever Run it currently holds, not an independent decision-maker.

Worker independence is what makes horizontal scalability possible without coordination overhead: any worker in the pool is, at any moment, equally capable of claiming any queued task, and no worker needs to know anything about any other worker's current state, workload, or identity to do its job correctly. This is a direct consequence of the statelessness principle in Execution Philosophy, applied to the worker pool as a whole rather than to a single worker in isolation — a pool of independent, stateless workers scales by adding more of them, with no coordination protocol required beyond the queue's own natural claim-and-visibility-timeout mechanism.

**Worker crashes** are treated as an expected, routine occurrence, not an exceptional one, given how long a single Run's orchestration can run and how many workers are active at any given time across the platform's full Run volume. When a worker crashes mid-orchestration, the task it was holding becomes eligible for another worker to claim once its visibility timeout expires, and that new worker resumes orchestration from the Run's last durably recorded state — not from wherever the crashed worker happened to be in memory, since nothing in memory was ever the source of truth. This is precisely what Execution Philosophy's resumability principle is describing at the worker-pool level: a crash loses only the work that had not yet been durably recorded, never more.

**Retries** at the worker level are a consequence of this same crash-and-reclaim mechanism, not a separately implemented feature — a Run whose worker crashed is retried simply by another worker claiming the same task and resuming orchestration, using the exact mechanism that handles ordinary task pickup. This is elaborated fully in Retry Philosophy below, but it is worth noting here that the worker model does not distinguish, architecturally, between "a fresh worker picking up a newly queued Run" and "a fresh worker picking up a Run whose previous worker crashed" — both are the identical operation from the queue's and the Execution Engine's perspective, which is a deliberate simplification this architecture relies on rather than treats as a coincidence.

**Idempotency** at the worker level is what makes this retry mechanism safe rather than merely convenient — a worker resuming a Run's orchestration must not, by resuming, duplicate any Execution Event, Artifact, or Score that a prior worker had already durably recorded before crashing. This is enforced through the same uniqueness constraints Schema Design already establishes (a Score's uniqueness per Run-and-Grader-Version pairing, an Execution Event's uniqueness per sequence position within its Run), which means a resuming worker's re-attempt at a step whose result was already durably recorded either produces no observable change or is cleanly rejected by the constraint, never a silent duplicate.

**Durable checkpoints are the concept that makes crash-and-resume actually work, and this architecture defines the term precisely rather than leaving it implicit.** A durable checkpoint exists at any point in a Run's orchestration where enough execution state has been successfully and durably persisted that another worker — with no memory of what the crashed worker was doing, and no access to anything that only ever existed in that worker's memory — can correctly determine what has already happened and what remains to be done, without ambiguity. A checkpoint is not a special mechanism the Execution Engine invokes separately from its ordinary work; it is a natural consequence of the durable writes this document already requires at every step: a Run status transition, once persisted, is a checkpoint, because a resuming worker can trust it completely. An Execution Event, once persisted, is a checkpoint, because a resuming worker can trust that everything up to and including that sequence position genuinely happened and was recorded. An Artifact, once persisted, is a checkpoint for the same reason, and so is a Score.

What makes these writes checkpoints, specifically, rather than merely durable facts, is that each one narrows the range of ambiguity a resuming worker has to resolve. Before the first Execution Event of a Run's Agent execution step is durably recorded, a resuming worker's only reliable checkpoint is the Run's own status (running, meaning execution has begun but nothing about its content is yet guaranteed) — it must assume nothing about what the Sandbox may have been doing and, consistent with Sandbox Lifecycle's treatment of Sandbox state as untrustworthy, it provisions fresh rather than attempting to inspect or resume the prior Sandbox's state directly. Once several Execution Events have been durably recorded, a resuming worker's checkpoint narrows considerably: it knows, with certainty, everything up to the last recorded sequence position, and its only genuine uncertainty is bounded to whatever occurred in the narrow window between that last durable write and the crash — precisely the bounded, named gap Event Production's Durability discussion already describes.

This is why this document treats durable checkpoints as architectural recovery boundaries rather than as an implementation detail of any specific persistence call: every checkpoint is a point this architecture guarantees a resuming worker can trust completely, and the frequency and placement of checkpoints throughout Run Lifecycle — one at every status transition, one at every Execution Event, one at every Artifact and Score — is what keeps the cost of any single crash bounded to the smallest possible unit of not-yet-durable work, never to an entire step or an entire Run.

**Fault isolation** at the worker level means one worker's crash, hang, or misbehavior has no effect on any other worker's ability to continue processing its own Run — workers share no in-memory state, and the only shared resource between them is the queue and the persistence layer, both of which are designed (per Database Design's Concurrency section) to handle concurrent access from many independent workers correctly. A worker stuck in a pathological state (an Adapter invocation that hangs indefinitely, for instance) is contained to the one Run it happens to be holding, bounded eventually by whatever timeout policy applies to that step, and never propagates its own dysfunction to any other Run's execution.

## Sandbox Lifecycle

A Sandbox is created fresh for exactly one Run, at the Sandbox provisioning step in Run Lifecycle, and its creation is the Execution Engine's explicit request to whatever provisioning capability the platform has available — a request the Execution Engine makes without knowing or needing to know the underlying compute mechanism that fulfills it, consistent with this document's Non-Goals. What the Execution Engine does need to know, and what this architecture commits to regardless of the underlying implementation, is that a Sandbox, once provisioned, is isolated from every other Run's Sandbox — no shared filesystem, no shared process space, no shared network namespace that would let one Run's execution observe or influence another's.

**Ownership** of a Sandbox belongs entirely to the Run it was provisioned for, for the Sandbox's entire lifetime — no Sandbox is ever shared across Runs, and no Sandbox outlives the Run it was created for. This one-to-one, non-reusable relationship is what the Domain Model already establishes and this document treats as an inviolable architectural constraint: reusing a Sandbox across Runs, even as a performance optimization, would risk exactly the kind of cross-Run contamination (residual filesystem state, cached process behavior) that would undermine the platform's ability to attribute a Run's outcome purely to its own pinned inputs.

**The ephemeral nature of a Sandbox is enforced, not merely assumed.** A Sandbox is torn down deterministically at the conclusion of the Run it belongs to — whether that conclusion was normal completion, a timeout, a failure, or a cancellation — and this teardown is treated as a mandatory step in the Execution Engine's orchestration, not an optional cleanup that might be skipped under failure conditions. A Sandbox that is not torn down is both a resource leak and, more importantly for this architecture, a violation of the isolation guarantee this section opened with: an orphaned, still-running Sandbox from a previous Run is exactly the shared, uncontrolled state this document's isolation principle exists to prevent.

**Resource limits** are applied to every Sandbox uniformly — bounds on compute, memory, execution time, and network access — because the Sandbox is, by design, running untrusted third-party code, and the platform's own stability cannot be allowed to depend on that code behaving well. These limits are what make a misbehaving or runaway Agent a contained, single-Run failure (handled per this document's Failure Model) rather than a platform-wide incident.

**Cleanup** extends beyond the Sandbox's own compute teardown to include ensuring nothing the Sandbox produced escapes as an uncontrolled side effect — every observable output of a Sandbox's execution is intended to leave the Sandbox boundary through exactly one path, translated by the Adapter into Execution Events and Artifacts, before the Sandbox itself is destroyed. Anything the Sandbox produced that was never translated through that path does not become part of the Run's record, and is not recoverable after teardown — which is precisely why Event Production and Artifact Handling, below, treat durable recording as something that must complete *before* the corresponding step is considered finished, not something eligible to be caught up on after the fact.

**Why Sandbox state is never trusted as persistent state.** Nothing about a Run's authoritative record — its status, its Execution Events, its Artifacts — is ever read back from a live or previously-torn-down Sandbox. The Sandbox is a means of producing that record, translated and persisted as it happens, never a place the record itself is considered to reside. This is what allows a Sandbox to be destroyed immediately and unconditionally once a Run concludes, without any concern that some piece of the Run's history still only exists inside it — if that were ever true of any fact, this architecture would already have failed to durably record that fact at the moment it happened, which Event Production and Artifact Handling are specifically designed to prevent.

## Resource Accounting

Every Run this platform executes consumes finite resources — compute time inside its Sandbox, memory, storage for its Artifacts, and, more subtly, sheer volume of Execution Events — and this architecture is deliberate about which component owns enforcing a limit on each of those resources versus which component owns deciding what happens once a limit is reached, because those are two distinct responsibilities that this document is careful not to blur together.

**Sandboxes enforce resource limits.** Consistent with Sandbox Lifecycle's treatment of resource limits as applied uniformly to every Sandbox, the actual enforcement of an execution timeout, a CPU budget, or a memory budget happens at the Sandbox boundary itself — the Sandbox is what stops an Agent from consuming more compute or memory than it has been allocated, in exactly the same way it is what isolates one Run's execution from another's. This document does not specify the numerical values of any of these budgets, because the correct values are an operational tuning question, not an architectural one; what this document commits to is that some bound exists on every one of these dimensions, and that the Sandbox — not the Execution Engine, and not the Agent itself — is the component responsible for actually enforcing it.

**Storage budgets and artifact size limits** apply to what a Run's execution is permitted to durably persist rather than to what happens inside the Sandbox, and they are enforced at the point of recording, per Artifact Handling — an Artifact whose payload would exceed whatever size the platform considers reasonable for a single stored object, or a Run whose accumulated Artifact volume would exceed a reasonable total, is a condition the Execution Engine detects at the moment it is about to persist, not a condition discovered later by inspecting the schema for an oversized row after the fact.

**Event volume limits** exist for an analogous reason at the other end of Schema Design's highest-volume table: an Agent that produces an unbounded, runaway stream of tool calls or output would, left unchecked, threaten the same operational health this document's Partitioning and Scalability concerns depend on the platform being able to reason about. A bound on how many Execution Events a single Run may produce is therefore treated as a legitimate resource dimension in its own right, alongside compute, memory, and storage — not an afterthought, and not conflated with a storage-size limit, since a Run can in principle produce a very large number of small events well within any individual size budget while still representing a resource-consumption problem this architecture needs a name for.

**The Execution Engine owns lifecycle decisions resulting from limit violations.** A Sandbox enforcing a CPU or memory budget, or the Execution Engine's own detection of an oversized Artifact or an excessive Execution Event volume, does not itself decide what becomes of the Run — it surfaces the violation as a signal, and the Execution Engine is the sole authority that decides what that signal means for the Run's lifecycle: whether execution is terminated outright, whether the Run is marked failed, or, where the platform's policy allows it, whether execution is permitted to conclude with whatever partial record has already been durably captured. This mirrors the same division of labor Grading Pipeline already establishes between a Grader detecting its own failure and the Execution Engine classifying what that failure means for the Run overall — detection and classification are kept as distinct responsibilities throughout this document, and resource-limit violations are no exception.

**Resource exhaustion is a classified execution outcome, not an ambiguous one.** Consistent with the Backend Architecture's Error Handling Philosophy insistence that a platform-caused failure and an Agent's ordinary failure to solve a Case are never conflated, a Run terminated for exceeding its execution timeout, its memory budget, or its event volume limit is recorded with that specific cause, distinguishable from every other reason a Run might reach a failed terminal state. This distinction matters for the exact reason every other classification in this document matters: a client or engineer looking at a failed Run needs to be able to tell, without guessing, whether the Agent ran out of ideas or the platform ran out of patience, and this architecture treats that distinction as owed to every Run's record, not as a nicety.

## Adapter Invocation

Adapters exist, per the Backend Architecture, because every Agent under evaluation has a different native interface, and the Execution Engine's orchestration must remain identical regardless of which Agent a given Run pins. Without an Adapter boundary, every step in Run Lifecycle that touches the Agent's behavior — prompt delivery, execution observation, event translation — would need to branch on which Agent is involved, which would mean the orchestration itself grows more complex, and more fragile, with every new Agent the platform onboards. The Adapter is what absorbs that variability entirely, so that from the Execution Engine's perspective, invoking Claude Code and invoking a future, still-unknown Agent are the identical operation: initialize the pinned Adapter Version against the prepared Sandbox and pinned Prompt Version, and consume whatever stream of Normalized Domain Model events it produces.

The Adapter's architectural role, from the Execution Engine's side of the boundary, is narrow and specific: translate one Agent's native actions into the platform's normalized shape, in real time, as those actions occur, and do nothing else. It may observe the Sandbox's state as the Agent interacts with it. It may translate the Agent's tool calls, file edits, and output into Execution Events and, where a payload is large, Artifacts. It may not persist anything itself, bypassing the Execution Engine — every fact an Adapter produces flows back through the Execution Engine's own durable-recording path, never directly to Infrastructure, consistent with the Backend Architecture's rule that an Adapter never depends on anything outside the Domain Layer and the Sandbox it is translating. It may not make orchestration decisions — an Adapter does not decide when a Run should be considered complete, when a timeout should be enforced, or when a Sandbox should be torn down; those remain the Execution Engine's decisions, informed by what the Adapter reports but never delegated to it.

The Execution Engine interacts with exactly one Adapter per Run, for that Run's entire execution, and treats the Adapter as a boundary it invokes but does not inspect internally — the Execution Engine knows how to call an Adapter and how to consume the stream of translated events it produces, and nothing about how a specific Adapter accomplishes that translation is visible to, or a concern of, the orchestration invoking it. This is what the Backend Architecture's dependency rule ("Adapters never depend on API") looks like from the other direction: the Execution Engine depends on the Adapter's translation contract, never on any specific Adapter's implementation, which is exactly what makes onboarding a new Agent an additive change — a new Adapter satisfying the same contract — rather than a change to the Execution Engine itself.

## Event Production

Every Execution Event this platform will ever have originates from exactly one place: an Adapter's translation of something that happened inside a Sandbox, during Agent execution, consumed and persisted by the Execution Engine as it occurs. Nothing bypasses this path — there is no mechanism by which an Execution Event is written except as the direct result of the Execution Engine recording what an Adapter reported, in the order the Adapter reported it.

**Ordering** is established by an explicit sequence position, assigned by the Execution Engine as it consumes the Adapter's stream, rather than inferred from timestamps or insertion order at the storage layer — this is the same architectural stance Schema Design already takes on this exact question, restated here from the producing side: the Execution Engine is the one authority that assigns sequence, and it does so synchronously, as part of recording each event, so that two events from the same Run's stream can never be assigned the same or an out-of-order position regardless of how closely together they occurred.

**Durability** means an Execution Event is not considered "produced" by this architecture's own accounting until it has been persisted through the Application-Layer-mediated path to Infrastructure — an event the Adapter has translated but the Execution Engine has not yet durably recorded does not yet exist from the platform's perspective, and if a worker crashes in the narrow window between translation and durable persistence, that specific event is lost, not corrupted or duplicated, and the resuming worker's orchestration (per Worker Model) proceeds from the Sandbox's actual current state rather than attempting to reconstruct a gap in the record. This is a deliberate, bounded honesty about resumability's limits, consistent with Execution Philosophy: the architecture does not pretend every possible crash window is invisible, it minimizes that window and is explicit about what falls inside it.

**Append-only behavior** at the point of production means the Execution Engine never revisits or corrects an already-recorded Execution Event — if an Adapter's translation of a specific action turns out, in hindsight, to have been wrong (a bug in a specific Adapter Version, discovered later), the correction is a new Adapter Version and, going forward, new Runs recorded through it — never a retroactive edit to Execution Events a prior, buggy Adapter Version already produced, because Schema Design's immutability guarantee has to hold even when the reason a past record looks wrong is a bug in the platform's own translation layer, not just an intentional design choice by whoever authored the Case.

**Relationship with persistence** is direct and synchronous at the point of production: an Execution Event's durable write is not a background, eventually-consistent side effect of some other operation — it is the operation, the specific, awaited step the Execution Engine performs before considering that portion of Agent execution "recorded" at all.

**Relationship with SSE** is the one place this document diverges from strict synchronicity, by design, matching the REST API Design's treatment of the SSE stream as a live projection layered on top of the durable record, never a replacement for it. Once an Execution Event has been durably persisted, its publication to any connected SSE stream for that Run is a best-effort, subsequent step — the Execution Engine does not block a Run's progress, or block the durable-recording path, waiting for a live subscriber (who may not even be connected) to acknowledge receipt. This is what allows the durable path to remain fast and unconditionally reliable while the live path remains genuinely optional infrastructure that can degrade — a slow consumer, a dropped connection — without ever being permitted to slow down or endanger the Run's actual execution.

## Artifact Handling

Large outputs — a full tool-call payload, an extensive diff, a long stdout capture — are handled by the identical production path Event Production describes, diverging only in where the content ultimately lives: rather than being carried inline as part of an Execution Event's own metadata, a large payload is written to object storage, and the Execution Event that references it carries only the reference (and the minimal descriptive metadata Schema Design's Artifact table specifies), consistent with Database Design's Storage Strategy.

**The decision of what counts as "large enough" to warrant Artifact storage rather than inline event metadata** is made by the Execution Engine at the moment of recording, based on payload size, and is applied consistently regardless of which Adapter produced the payload or which Agent generated it — this consistency matters because it keeps Execution Event rows uniformly small and fast to query regardless of how verbose any particular Agent's native output tends to be, which is exactly the property Database Design's Indexing Philosophy depends on holding for the platform's highest-volume table.

**Streaming**, where the underlying payload is large enough that holding it entirely in memory before writing it would itself be a resource concern, is the Execution Engine's mechanism for moving content from the Sandbox boundary to object storage without requiring the full payload to be buffered anywhere but transiently — this is treated as an architectural expectation of the Artifact-handling path (large content moves through the pipeline incrementally, not as a single, memory-bound blob) rather than a specific streaming implementation this document prescribes.

**Metadata and checksums** are recorded alongside every Artifact at the moment its content is durably written to object storage — a checksum specifically, so that the platform can later verify a fetched Artifact's content matches what was originally written, catching corruption or an incomplete write rather than silently trusting whatever object storage happens to return. This is not a defensive measure against object storage being generally unreliable; it is a deliberate architectural stance that a write-once, long-retained artifact deserves an integrity check that a normal metadata row does not, given how consequential a silently corrupted diff or transcript would be for a downstream Grader or a human debugging a Run years later.

**Ownership** of every Artifact belongs to the Run it was produced for, exactly as Schema Design establishes — the Execution Engine never produces an Artifact that is not immediately and permanently associated with the Run currently executing, and an Artifact's row is written as part of the same durable-recording discipline Event Production describes, never left in a state where the object storage write succeeded but the referencing metadata did not, or vice versa; where the underlying persistence mechanism cannot guarantee both halves atomically, the Execution Engine's own step-completion logic treats the operation as incomplete, and therefore unrecorded, until both halves are confirmed, rather than exposing a partially-written Artifact as if it were whole.

**Immutability** for Artifacts, once written, is absolute and permanent in the identical sense Event Production establishes for Execution Events — an Artifact's content is never edited or replaced in place, and a corrected or superseding version of some content is a new Artifact, referenced going forward, never a mutation of the original.

## Grading Pipeline

Grading begins only once a Run's execution has fully concluded — the Execution Engine does not invoke any Grader against a Run that is still actively executing, because a Grader consuming a partial, still-growing Execution Event history would be reasoning about an incomplete record, and any Score produced from an incomplete record would be meaningless at best and misleading at worst. This ordering — execution completes, then and only then does grading begin — is treated as an absolute sequencing rule, not a default that could be relaxed for a Grader that only needs a subset of a Run's history.

**Grader scheduling** is the Execution Engine's responsibility: given a completed Run and the set of Graders its Case Version declared applicable (per Schema Design's Case Grader Declaration), the Execution Engine invokes each one, tracks which have completed, and determines when the Run's overall grading phase is finished. Scheduling here means orchestration — deciding when and how each Grader is invoked — not grading itself, which remains entirely the Grader Layer's own concern, invoked as a boundary the same way the Adapter is, per the Backend Architecture's dependency rules.

**Parallel grading** is the default posture: because each declared Grader is architecturally independent of every other one — reading the same completed, immutable Run record, producing its own Score, per the Domain Model's explicit statement that a Grader's failure never affects another Grader's output — there is no correctness reason to serialize them, and serializing them would only add latency to a phase whose total duration directly affects how quickly a Run reaches a terminal, actionable state. The Execution Engine invokes applicable Graders concurrently, bounded by whatever resource limits the platform's grading capacity imposes at a given time (a Scalability concern, not a correctness one).

**Isolation** between Graders during this phase mirrors the isolation principle established for Sandboxes: one Grader's execution — its own resource consumption, its own failure, its own runtime behavior — has no observable effect on any other Grader evaluating the same Run. This is what makes the Domain Model's guarantee (a Grader's failure never affects another Grader's Score) an architectural property of the grading pipeline's isolation, not merely a hoped-for outcome of graders happening to be well-written.

**Score persistence** occurs as each Grader completes, independently, through the same durable, Application-Layer-mediated path every other write in this pipeline uses — a Grader that finishes early does not wait for slower Graders before its Score is recorded, because there is no correctness reason for one Grader's completion to be gated on another's, and gating it would introduce exactly the kind of unnecessary coupling this document's isolation principle exists to prevent.

**Partial grading failures** are an expected outcome this architecture handles explicitly rather than treats as an edge case: if one declared Grader fails — a timeout, an internal error, an infrastructure failure specific to that Grader's invocation — the Execution Engine records that failure against that Grader specifically and continues collecting results from the others, exactly as the Backend Architecture's Background Execution Flow already establishes. The Run's eventual terminal state reflects this honestly: a Run can reach a terminal, gradable-complete state with some Graders having succeeded and others having failed, and this is a legitimate, permanent outcome for the affected Run — not a state the Execution Engine attempts to indefinitely retry into full completion, because a grading window that never closes would mean the platform could never present a Run's results with any confidence about when "complete enough to compare" has actually been reached.

**Completion** of the grading phase, and with it the Run's transition to its overall terminal state, is reached once every declared Grader has either produced a Score or been conclusively marked as failed for this Run, or once whatever grading-window policy the platform applies has elapsed with some Graders still outstanding — whichever comes first, per the Domain Model's partial-grading treatment. This is the final step in Run Lifecycle, and it is the point at which the Run becomes, permanently, the object every downstream comparison and trend analysis will read.

## Failure Model

**Worker crash.** A worker process terminates, for any reason, while holding a Run's orchestration. Architecturally, this is handled entirely by the mechanism Worker Model already describes: the task's visibility timeout expires, another worker claims it, and orchestration resumes from the Run's last durably recorded state. No special-case handling exists for this failure beyond the ordinary claim-and-resume path, because treating worker crashes as ordinary rather than exceptional is precisely what this architecture's statelessness and resumability principles are designed to make possible.

**Sandbox failure.** The Sandbox itself fails to provision, or fails unexpectedly during execution — a resource-exhaustion condition, an underlying infrastructure fault unrelated to anything the Agent did. This is classified, by the Execution Engine, as an infrastructure-caused failure of the Run, distinct from the Agent simply failing to solve the Case, per the Backend Architecture's Error Handling Philosophy insistence that these two categories are never conflated. A Sandbox failure typically results in the Run being retried (a fresh Sandbox provisioned, execution attempted again) up to whatever retry policy this document's Retry Philosophy establishes, and only becomes a terminal failure of the Run itself once that policy is exhausted.

**Adapter failure.** The Adapter itself — not the Agent it is translating — raises an error: a translation bug, an unhandled shape in the Agent's native output. Because the Adapter is platform code, not untrusted third-party behavior, this is treated as a defect to be surfaced clearly and attributed to the specific Adapter Version involved, rather than silently absorbed or misattributed to the Agent's own behavior. Depending on where in execution the failure occurred, this may still allow a partial Execution Event history to be preserved (whatever was successfully translated and durably recorded before the failure) while the Run itself is marked failed, since a failure at this point means the Execution Engine can no longer trust that further Agent behavior is being faithfully translated.

**Network interruption.** Connectivity between the orchestrating worker and the Sandbox, or between the worker and the platform's own Infrastructure, is disrupted transiently. This is treated, by default, as a transient, retryable condition — consistent with the Backend Architecture's stance that infrastructure errors are classified separately from domain errors and are often safely retried — with the specific retry behavior governed by Retry Philosophy below, distinguishing a brief interruption (retried transparently) from a sustained one (eventually surfaced as a Run-level failure once retry budget is exhausted).

**Storage failure.** A write to PostgreSQL or object storage fails at the moment the Execution Engine is attempting to durably record an Execution Event, an Artifact, or a Score. Because this architecture treats durable recording as the operation that defines whether something "happened" from the platform's perspective (per Event Production), a storage failure at this point means the corresponding fact is not yet recorded, and the Execution Engine's step-completion logic reflects that honestly — it does not proceed as though the write succeeded, and it does not silently drop the fact either; it retries the write according to policy, or, if retries are exhausted, surfaces the failure at the Run level rather than allowing an ambiguous, partially-recorded state to stand.

**Grader failure.** Addressed fully in Grading Pipeline's Partial grading failures above — contained to the specific Grader involved, never allowed to affect other Graders' Scores or the Run's own execution record, which by the time grading begins is already complete and immutable regardless of what happens during grading itself.

**Queue redelivery.** The broker redelivers a task the Execution Engine, or the worker holding it, had already processed — a normal consequence of an at-least-once delivery guarantee, discussed further in Retry Philosophy, and handled by the same idempotency mechanisms (uniqueness constraints on Execution Events, Artifacts, and Scores) that make worker-crash resumption safe. A redelivered task for a Run that has already reached a terminal state is recognized as such immediately — the Execution Engine checks the Run's current status before attempting any further orchestration, and a Run already in a terminal state is never re-executed, its status is simply confirmed and the redelivered task is acknowledged without further action.

## Retry Philosophy

**Safe retries** are the default assumption this architecture makes about most of the failure modes in the section above, because most of this pipeline's steps are either naturally idempotent (checking a repository out again produces the same starting state) or are made safe through the explicit uniqueness constraints Schema Design establishes (a retried Execution Event write, Artifact write, or Score write either succeeds once or is cleanly rejected as a duplicate, never silently duplicated). This is what allows the Execution Engine to retry aggressively and by default, rather than treating every retry decision as a bespoke judgment call.

**Idempotency**, as established throughout this document, is not a property retries merely benefit from — it is the precondition that makes retrying safe in the first place, and it is engineered into every write this pipeline performs before that write's retry behavior is ever exercised in production, never bolted on afterward once a duplicate-data incident reveals the gap.

**Duplicate prevention** is therefore not a separate mechanism this document introduces — it is the direct consequence of the uniqueness constraints already discussed, applied consistently: an Execution Event's sequence position, a Score's Run-and-Grader-Version pairing, and an Artifact's own identity are each the specific fact that makes a retried write of that specific kind of record either a no-op or a clean rejection, never a silent duplicate.

**At-least-once execution** is the guarantee this architecture actually provides, and it is stated explicitly rather than left implicit, because it is the honest characterization of what a queue-based, crash-tolerant pipeline can promise: a Run's task may, under failure conditions, be picked up and partially processed more than once (by different workers, across a crash), but the idempotency guarantees above ensure that "processed more than once" never means "recorded more than once." Exactly-once semantics at the level of the underlying queue delivery is not attempted, because achieving it would add substantial complexity for a guarantee this architecture does not actually need, given that idempotent recording already delivers the property that matters — a Run's final record is correct regardless of how many times any individual step was attempted.

**Where retries happen** is scoped specifically to the failure modes this document's Failure Model classifies as infrastructure or transient in nature — Sandbox provisioning failures, network interruptions, storage write failures — because retrying these is both safe (per idempotency) and likely to succeed, since the underlying cause is typically not something intrinsic to the specific Run.

**Where retries deliberately do NOT happen** is just as architecturally important: a domain-level rejection (a Run created against a Case Version that turns out to have been deprecated between creation and execution, for instance) is never retried, because retrying a domain error does not make it valid — this mirrors the Backend Architecture's Error Handling Philosophy exactly, applied here to the execution pipeline specifically. Agent execution itself, once genuinely underway and producing real Execution Events, is not silently retried from scratch on a failure partway through — a partial, real execution history has already been durably recorded and represents something that actually happened; discarding it and re-running the Agent from the beginning would mean the platform's record no longer reflects what happened on the attempt that produced those events, which this architecture treats as unacceptable. Where a Run's execution genuinely needs to be attempted again after a failure of this kind, that is architecturally a new Run, not a silent retry of the old one, preserving the principle that a Run's history is what actually happened during that Run, not an idealized version of what would have happened if nothing had gone wrong.

## Cancellation

Run cancellation is a deliberate, caller-initiated action — a Project member decides a Run is no longer needed and requests its cancellation through the API, per the REST API Design's treatment of cancellation as an explicit state transition rather than a generic field update. The Execution Engine's responsibility, once a cancellation request reaches it, is to honor that request as promptly and as cleanly as the Run's current step allows.

**Cooperative cancellation** is the mechanism by which this happens: the Execution Engine does not forcibly terminate a Sandbox or an in-flight operation the instant a cancellation request arrives, because doing so at an arbitrary point could leave a step's durable-recording work half-completed in a way this document's other sections have specifically designed against. Instead, cancellation is checked at well-defined points in the orchestration — between steps, and periodically during long-running steps like Agent execution — and honored at the next such point, allowing whatever step is currently in progress to reach a clean, recordable boundary before the Run's execution is actually halted.

**Cleanup** on cancellation follows the identical discipline Sandbox Lifecycle already establishes for every other path to a Run's conclusion: the Sandbox is torn down deterministically, and cleanup is never skipped or made conditional on how the Run reached its conclusion. A cancelled Run's Sandbox is reclaimed exactly as promptly and exactly as reliably as a normally completed Run's Sandbox.

**Terminal guarantees** for a cancelled Run are the same as for any other terminal Run: once cancellation has been fully processed, the Run is permanently closed to any further Execution Event, Artifact, or Score, and its record — whatever Execution Events had already been durably recorded up to the point cancellation was honored — is preserved exactly as it stood, never retroactively cleared or hidden just because the Run did not run to natural completion. A cancelled Run's partial history remains a legitimate, permanent, and inspectable fact, consistent with this document's Execution Philosophy insistence that the record is the platform's actual deliverable.

**Resource reclamation** — the Sandbox's compute, and any grading capacity that would otherwise have been allocated to a Run that will now never reach the grading phase — is a direct benefit of processing cancellation promptly rather than an afterthought: a Run that sits in a queued or provisioning state at the moment cancellation is requested should never proceed to consume Sandbox or Adapter resources at all, and the Execution Engine's cooperative-cancellation checks are placed specifically so that a cancellation requested early is honored before any resource this platform cares about conserving is actually spent.

## State Transitions

A Run's status field, per Schema Design, is the one legitimate mutation across an otherwise immutable execution record, and this document treats that status as authoritative in a specific, narrow sense: at any given moment, a Run's persisted status is the single source of truth for what phase of Run Lifecycle it is in, and every component in this architecture — the Execution Engine itself, any worker resuming after a crash, the API surfacing status to a client — defers to that persisted value rather than to any inference drawn from other signals (whether a Sandbox happens to still be running, whether an SSE connection is still open).

**Allowed transitions** follow the finite state machine the Domain Model already defines: queued to running, running to grading, grading to one of the terminal outcomes, with cancellation able to intervene from queued or running (and, in the bounded sense Grading Pipeline already describes for partial failures, potentially from grading as well, depending on the platform's cancellation policy for a Run already mid-grading). This document does not redefine that state machine — it defines how the Execution Engine enforces it: every status transition the Execution Engine performs is checked against the Run's current persisted status before being applied, and a transition that does not correspond to a legal edge in this state machine is rejected as a constraint violation, not silently applied.

**Terminal states** — completed, failed, cancelled — are permanent, and the Execution Engine treats a Run already in a terminal state as fully closed to any further orchestration, per Queue redelivery's handling above: encountering a terminal Run, whether through a redelivered task or a resumed worker's stale view, results in no further action, only confirmation.

**Illegal transitions** — an attempt to move a Run from a terminal state back to running, for instance, or from queued directly to grading, skipping execution — are treated as a defect to be prevented structurally wherever possible (the Execution Engine's own orchestration logic never constructs such a transition under normal operation) and as a hard rejection wherever they might otherwise occur (a duplicate or out-of-order task delivery attempting to apply a transition the Run's current status does not permit).

**Relationship to the Domain Model** is direct: this document does not introduce any state or transition the Domain Model does not already define. Everything in this section is the Execution Engine's enforcement of a state machine that document already owns, applied consistently at the one place in the codebase — the Execution Engine's orchestration — where every legitimate status transition in the platform actually originates.

## Run Status and Execution History

State Transitions establishes Run status as authoritative for what phase of Run Lifecycle a Run is currently in; this section clarifies precisely how that authority relates to the Execution Event stream Event Production describes, because the two are easy to conflate and this architecture depends on them being understood as fundamentally different kinds of fact.

Execution Events are the complete, append-only, historical record — every meaningful thing that happened during a Run's execution, in strict order, permanently retained. Nothing about a Run's actual behavior is knowable from anywhere else; the Execution Event stream is not a log of the truth, it is the truth, in the specific sense that Execution Philosophy's append-only-history principle already establishes.

Run status, by contrast, is not a historical record at all — it is the platform's current projection of lifecycle progress, a single, present-tense summary answering exactly one question: which phase of Run Lifecycle is this Run in right now. A status value carries no information about what happened during any given phase, only that the Run has reached it. This is a deliberate, narrow scope, not an oversight: status is designed to be cheap to read, cheap to poll, and immediately meaningful without requiring any interpretation of the underlying event stream, precisely because so many parts of this platform (a client polling for completion, a dashboard summarizing many Runs at once) need exactly that narrow, present-tense answer and nothing more.

The relationship between the two is therefore one of derivation, not parity. The authoritative history is the Execution Event stream; the status is a summary computed over that history's progress, not an independent source of truth running alongside it. This is why the Execution Engine treats a status transition and the Execution Events that precede it as connected but distinct durable checkpoints, per Worker Model's Durable checkpoints discussion — a status transition tells a resuming worker or an observing client *where* a Run stands, while the event stream tells anyone who needs it *what actually happened* to bring it there. A client that only ever reads status can correctly track a Run's progress through its lifecycle without ever needing to interpret a single Execution Event; a Grader, or an engineer debugging a specific outcome, reads the event stream because status alone was never designed to answer "why," only "where."

This separation is also what protects the event stream's integrity from the pressures a live-updating summary field would otherwise introduce. Because status is a narrow projection rather than an accumulating record, it can be the one field this document permits to be updated in place (per Schema Design and State Transitions) without that update ever threatening the append-only guarantee the event stream depends on — the two facts are stored, reasoned about, and mutated under entirely different rules, and this architecture is explicit that conflating them, or treating status as if it were itself part of the historical record, would be a category error with real consequences for how confidently either one can be trusted.

## Observability

Every step in Run Lifecycle produces signal worth capturing beyond the Execution Events that make up a Run's own record — structured logs correlating a given log line to the Run, worker, and step it originated from, using the same correlation identifiers the Backend Architecture's Cross-Cutting Concerns section already establishes as threaded from the point of origin through every layer a request or task passes through. This document does not redesign that correlation mechanism; it notes that the Execution Engine is one of the two primary origination points (alongside the API Layer) where a correlation identifier is first attached, and every subsequent step's logging inherits it.

**Correlation identifiers**, specifically for the execution pipeline, must survive every hand-off this document's Execution Topology describes — from the Queue's task, to the Worker that claims it, to the Execution Engine's orchestration, to the Sandbox and Adapter it invokes, and on into the Grading Pipeline. A correlation identifier that was dropped or regenerated at any one of these hand-offs would sever the ability to reconstruct a Run's operational story end to end, which is precisely the failure this discipline exists to prevent; this architecture treats the identifier established at Run creation as the one that must appear on every subsequent log line, metric, and trace span this pipeline produces, regardless of how many components or worker crashes intervene between origination and any given piece of signal.

**Metrics** — how long each named step in Run Lifecycle typically takes, how often each failure mode in this document's Failure Model actually occurs, how deep the queue typically runs — are what turn this architecture's failure and retry handling from a set of rules that are merely believed to work into a set of behaviors that are actually observed to work at the volumes this platform runs at. This document does not specify which metrics are collected or how they are aggregated; it establishes that every named step and every named failure mode in this document is, by design, the kind of thing metrics should be attached to, because a step or failure this document bothered to name explicitly is one this platform's operators will eventually need to ask "how often does this happen, and how long does it take" about.

**Worker execution timing** — how long a given worker actually holds a Run's orchestration, from claim to release — is a distinct measurement from the Run's own overall duration, because a worker's hold time reflects the platform's own processing behavior (including any time spent blocked on a slow Sandbox or Adapter call), while a Run's total duration reflects the full span from creation through terminal state, including time spent simply waiting in the queue. Keeping these two measurements distinct is what makes it possible to tell, for a Run that took an unusually long time, whether the delay originated in queue wait, in worker processing, or in the Agent's own execution — three genuinely different explanations that a single, undifferentiated duration figure would obscure.

**Orchestration latency** — the time between one durable checkpoint and the next, per Worker Model's Durable checkpoints discussion — is the measurement most directly tied to this architecture's reliability posture: a growing gap between successive checkpoints for a given step is the earliest operational signal that something in the orchestration itself, rather than in the Agent's own behavior, has started to slow down, and it is worth measuring separately from execution duration precisely because it isolates the platform's own overhead from the Agent's.

**Execution duration**, broken out step by step per Run Lifecycle (Sandbox provisioning, repository preparation, Agent execution, grading), is what lets the platform distinguish a genuinely slow Agent from a genuinely slow platform — and, at aggregate scale, what lets trend analysis of execution duration itself become one more dimension this platform can report on, alongside score, since how long an Agent takes is frequently as meaningful a comparison point as whether it succeeded.

**Sandbox lifecycle metrics** — provisioning time, teardown time, and the rate at which provisioning itself fails — are measured as their own category distinct from Agent execution time, because Sandbox Lifecycle already treats provisioning and teardown as their own named, observable steps specifically so that a provisioning-layer problem is attributable to provisioning, not misread as an Agent-caused slowdown; the same reasoning that justifies naming these steps explicitly in Run Lifecycle justifies measuring them explicitly here.

**Tracing** a single Run's execution across the worker that picked it up, the Sandbox it was provisioned into, the Adapter it invoked, and the Graders that eventually scored it is a natural extension of the same correlation-identifier discipline, applied end to end, and is the mechanism by which the timing measurements above are stitched into a single, navigable picture of one Run's operational path through this topology — a distributed trace spanning the Queue hand-off, the Worker's hold, and every subsequent boundary crossing this document's Execution Topology describes. It is worth noting that this platform has an advantage most systems do not when it comes to tracing: the Execution Events a Run produces already are, in effect, a detailed, durable, ordered trace of everything that happened, since Execution Philosophy's observable-execution principle was designed with exactly this dual purpose in mind. A conventional distributed trace and this platform's own persisted Execution Event history serve overlapping purposes, and this document notes that overlap without conflating the two: a trace is an operational tool for engineers debugging the platform's own behavior across a request or task's lifetime; the Execution Event history is the platform's product, describing the Agent's behavior, not the platform's internal mechanics.

**Auditability** for the Execution Engine specifically means that every status transition a Run undergoes, and every fact recorded along the way, is attributable — which worker performed it, and when — even though the Execution Engine's own step-by-step orchestration is not itself an Audit Log entry in Schema Design's specific sense (that table is reserved for administrative and definitional actions, not execution-time facts). The Execution Event history already serves this purpose for what happened during a Run; this document's point is only that the Execution Engine's own operational behavior — which worker, which retries, which timing — should be reconstructable after the fact with the same rigor, through logging and metrics, even though it lives outside the platform's core Domain Model.

**Debuggability**, ultimately, is what every principle in this section serves: an engineer investigating why a specific Run behaved the way it did should be able to reconstruct, after the fact, exactly what the Execution Engine did, when, on which worker, and why — without needing to have been watching live when it happened. This document does not attempt to fully specify the mechanisms that deliver this — that is the proper scope of a future, dedicated Observability Architecture document — but it establishes that the Execution Engine's design, throughout every section above, treats debuggability as a design input, not a capability added after the fact once the pipeline is already built.

## Scalability

**Horizontal workers** are the primary lever this architecture relies on to scale execution throughput, and the Worker Model's statelessness is what makes this lever effective without introducing coordination cost: adding more workers to the pool increases the platform's capacity to pick up and orchestrate concurrently executing Runs linearly, with no change required to the Execution Engine's own logic and no coordination protocol between workers beyond the queue's native claim mechanism.

**Queue depth** — how many Runs are waiting to be picked up at any given moment — is the natural signal this architecture uses to reason about whether the current worker pool is sufficient for the platform's current load, and a growing queue depth under sustained load is the expected, correct indicator that more workers (or more Sandbox provisioning capacity, which Sandbox Lifecycle keeps as an independent concern) are needed, rather than a sign of a design flaw in the orchestration itself.

**Backpressure** is exercised, in this architecture, primarily by allowing queue depth to grow rather than by degrading correctness under load — a Run that must wait longer in a queued state before a worker becomes available to pick it up is a acceptable, honestly-communicated cost of high load (the Run's status remains accurately "queued" for as long as that is true), which is preferable to attempting to force throughput past what the platform's Sandbox and grading capacity can actually sustain at the cost of the reliability guarantees this document establishes elsewhere. This is a direct expression of Execution Philosophy's "reliability over throughput" tiebreaker, applied specifically to how this architecture behaves under load rather than only to how it behaves under isolated failure.

**Parallel grading**, already established in the Grading Pipeline section, is also a scalability property in its own right: because Graders are architecturally independent, grading capacity scales the same way execution capacity does, by adding more concurrent grading capability, without any correctness concern about Graders interfering with each other regardless of how many run concurrently, bounded only by whatever resource limits the platform chooses to impose at a given time.

**High-volume execution**, at the scale Database Design and Schema Design anticipate (millions of Runs, hundreds of millions of Execution Events), is handled by this architecture primarily through the combination of stateless horizontal workers and the append-only, idempotent write discipline established throughout this document — nothing in this document's design depends on execution volume staying below any particular threshold, because every mechanism described here (crash-and-resume, idempotent writes, per-Grader isolation) is designed to behave identically whether the platform is running ten concurrent Runs or ten thousand. This document deliberately does not discuss the underlying deployment infrastructure that provisions worker capacity or Sandbox compute at whatever scale the platform actually needs — that is explicitly out of scope, per Non-Goals below, and is a separate concern from the architectural design that makes scaling that infrastructure a matter of adding capacity, not a matter of redesigning this pipeline.

## Extensibility

**New sandbox implementations** — a different underlying provisioning mechanism, chosen for cost, performance, or platform-specific reasons — fit into this architecture as a new implementation of the same Sandbox-provisioning boundary the Execution Engine already invokes without inspecting internally, per Sandbox Lifecycle. Nothing about Run Lifecycle, Orchestration Model, or any other section of this document changes because the Sandbox is provisioned differently underneath; the Execution Engine's relationship to "a Sandbox" is defined entirely by the guarantees Sandbox Lifecycle establishes (isolation, ephemerality, resource limits), not by any specific mechanism that delivers them.

**Distributed execution** — spreading a single Run's orchestration, or the platform's overall execution workload, across a more elaborate distributed topology than a straightforward worker pool — is compatible with this architecture specifically because centralized-per-Run orchestration with stateless workers, per the Orchestration Model, already does not assume any single always-running process; it assumes only that some worker, at any given moment, holds a given Run's orchestration authority. A more distributed underlying topology is a deployment and infrastructure evolution layered on top of that same model, not a change to it.

**GPU execution**, should some future Agent or Grader require it, is accommodated the same way any other Sandbox or Grader resource requirement would be — as a property of the specific Sandbox provisioning request or Grader invocation for that Run, routed through the resource-aware scheduling and GPU-routing policy Scheduling Philosophy already anticipates, not as a structural change to the pipeline. The Execution Engine's orchestration does not need to know or care what kind of compute a given Sandbox or Grader actually runs on, only that the boundary it invokes fulfills the contract this document establishes.

**Multiple worker pools**, segmented by resource class or workload characteristics as the Backend Architecture's Future Evolution section already anticipates, fit naturally because nothing in this document assumes a single, undifferentiated pool — task routing to an appropriate pool is the worker-pool-selection policy Scheduling Philosophy already scopes outside the Execution Engine's own responsibility, and multiple pools simply means that scheduling decision has more than one destination to choose from, with the Execution Engine's own orchestration, once a task is claimed by any worker in any pool, behaving identically regardless of which pool claimed it.

**Additional grading engines** — new kinds of Graders, or an entirely new grading execution mechanism distinct from how Graders run today — are accommodated by the same isolation and scheduling boundary the Grading Pipeline already establishes: a new Grader is simply one more independent, isolated participant the Execution Engine schedules and collects a Score from, following the identical contract every existing Grader already follows.

**New adapters** are, as established throughout this document, the platform's primary and expected extensibility mechanism — every new Agent the platform ever supports arrives as a new Adapter satisfying the existing translation boundary, with zero change required to Run Lifecycle, Orchestration Model, Event Production, or any other section of this document. This is, in a real sense, the extensibility case this entire architecture was designed around first, and every other item in this section inherits the same underlying discipline: the Execution Engine's stability comes from depending on contracts and boundaries, never on the specific implementations that satisfy them at any given moment.

## Non-Goals

This document defines the architecture governing execution orchestration; it does not define how any of the components that architecture invokes are actually implemented. It does not specify the numerical values of any resource limit discussed in Resource Accounting — execution timeouts, CPU or memory budgets, storage or Artifact size limits, and event volume limits are named here as dimensions this architecture accounts for, never as specific figures, which are an operational tuning decision made separately. It does not specify the numerical values behind any Scheduling Philosophy policy either — concurrency limits, fairness allocations, and execution quotas are named as platform-owned policy categories, not as configured thresholds. It does not specify worker implementation — the specific process model, language-level concurrency mechanism, or task-consumption library a worker uses internally is an implementation decision made against this document, not part of it. It does not specify Sandbox implementation, nor does it name or assume any particular containerization or virtualization technology, including Docker or Kubernetes — this document's Sandbox Lifecycle section establishes the guarantees a Sandbox implementation must provide, deliberately without naming the mechanism that provides them. It does not specify queue technology — Retry Philosophy's at-least-once guarantee and Worker Model's crash-and-resume mechanism are written to hold against any broker that provides the properties this document assumes (durable enqueue, visibility-timeout-based redelivery), not against any specific product. It does not specify object storage implementation, beyond the metadata and checksum obligations Artifact Handling establishes. It does not specify SDK implementation for Adapters or Graders, beyond the invocation boundary Adapter Invocation and Grading Pipeline already describe. It does not define API endpoints — Run creation, cancellation, and status retrieval are referenced throughout this document exactly as the REST API Design already specifies them, and this document adds nothing to that surface. It does not define database schema — every persisted fact this document discusses is exactly the table Schema Design already specifies, referenced here by name, never redefined. And it does not discuss deployment — how many workers run, in what environment, on what infrastructure, and how that infrastructure is provisioned or scaled operationally are concerns this document deliberately leaves to the teams and documents responsible for the platform's operational deployment, informed by this document's Scalability section but not specified by it.
