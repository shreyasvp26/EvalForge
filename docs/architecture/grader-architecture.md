# Grader Architecture

## Purpose

Every document that precedes this one treats the Grader as a boundary rather than a subject. The Domain Model establishes that a Grader exists, that it consumes a completed Run's Execution Events and Artifacts, and that it produces Scores. The Backend Architecture places the Grader Layer in the dependency graph and states, categorically, what it may and may not depend on. The Execution Engine Architecture goes further — it describes, from the orchestrating side of the boundary, how a Run's grading phase is scheduled, parallelized, and isolated, and treats everything on the other side of that boundary as a black box it invokes but does not inspect. That treatment was correct for the Execution Engine Architecture's purpose: an orchestration document should not need to understand how a rubric is interpreted or how an objective check is evaluated in order to define how it schedules the component that does either. But a black box invoked correctly by one document still needs, somewhere in the corpus, a document that opens it — that explains why it exists, what it is architecturally responsible for, and what rules govern its own internal shape. This is that document.

The Grader Layer is the single mechanism by which EvalForge turns a faithfully recorded execution history into a comparable, trustworthy measurement — capable of judging a Run's correctness objectively, its quality subjectively, or both, through the identical orchestration, versioning, and persistence architecture already established by every prior document, without any of those documents needing to know or care what any individual Grader actually measures or how. That is a strong claim, and it is only true because of how narrowly and precisely this document is about to define the Grader's boundary. If that boundary were drawn loosely — if a Grader were permitted to reach back into a Run's execution, to observe another Grader's behavior, or to introduce its own unaccounted-for variability into what is supposed to be a comparable measurement — the platform's core value proposition of trustworthy longitudinal comparison would be an aspiration the documentation asserts rather than a property the architecture actually delivers. This document exists to make sure that does not happen: to draw the Grader's boundary with enough precision that every other document in this corpus can continue to treat "a Grader" as an interchangeable, independently reasoned-about abstraction, forever, regardless of how many wildly different grading strategies the platform eventually supports.

This document refines, and does not redefine, everything the corpus has already established about Graders. Where the Domain Model already states that a Grader never modifies the Run it grades and that a Grader's failure is isolated from every other Grader's output, this document does not restate those facts as new claims — it explains their architectural consequences. Where the Backend Architecture already states the dependency rules governing the Grader Layer package, this document does not relitigate those rules — it explains why they are drawn exactly where they are and what would break if they were drawn anywhere else. Where the Execution Engine Architecture already describes, from its own side, how it schedules, parallelizes, and isolates Grader invocations, this document takes that same invocation and describes it from the Grader's side, filling in exactly the internal architecture that document deliberately left as a black box. Everywhere this document uses a term the corpus has already defined — Run, Execution Event, Artifact, Score, Grader Version, Case Grader Declaration — it means precisely what that earlier document said it means, and nothing more.

## Grading Philosophy

**Grading as measurement of a completed fact, never participation in producing one.** By the time any Grader is invoked, the Run it is grading is already finished, in the strict sense the Execution Engine Architecture's Grading Pipeline establishes: execution has concluded, every Execution Event and Artifact that will ever exist for this Run has already been durably recorded, and nothing a Grader does can add to, alter, or retroactively reinterpret that record. A Grader's entire relationship to a Run is that of an observer reading a closed book, never an author still writing one. This is not a convenience of scheduling — it is the property that makes a Score meaningful at all: a measurement taken against a record that could still change out from under it would not be a measurement of anything stable, and every downstream comparison this platform exists to support depends on the thing being compared having already stopped moving.

**Two families, one contract.** Objective Graders (test pass/fail, lint, build success, diff correctness) and rubric-based Graders (structured, criteria-driven judgment, typically LLM-as-judge) solve categorically different problems — one asks "did a mechanically checkable condition hold," the other asks "how good was this, against a stated standard" — and this document does not pretend those are the same question. But the Domain Model deliberately models both identically: something that reads a Run's record and emits a Score. This document honors that unification precisely because it is what lets the Execution Engine, the Score schema, and every consumer of a Score treat "a Grader ran" as one uniform fact regardless of which family produced it. Where the two families genuinely diverge — in determinism, in resource profile, in failure surface — this document calls that divergence out explicitly rather than papering over it with false symmetry; where they do not diverge, this document treats them identically, because inventing a distinction the Domain Model does not draw would fracture the one contract every Grader, present and future, is expected to satisfy.

**Independence as the property that makes modular grading possible at all.** A Run is not graded once, by one authority reaching a single verdict — it is graded by however many Graders its Case Version declared applicable, each producing its own independent Score, decomposing "how did this Run do" into as many separate measurements as there are applicable Graders. This is a deliberate rejection of a single, monolithic grading function that would need to understand every possible dimension of quality at once. A platform whose entire purpose is evaluating a growing, unpredictable set of coding agents against a growing, unpredictable set of task types cannot afford a grading architecture that requires touching existing grading logic every time a new dimension of measurement is wanted — it needs one where a new way of judging a Run is simply one more independent participant, added without touching anything that already exists.

**Reproducibility as an obligation this document takes more seriously for Graders than for almost any other component in the corpus.** The Execution Engine Architecture is explicit that the platform does not, and cannot, guarantee an Agent's behavior will repeat — that unpredictability is what the platform exists to measure. A Grader occupies the opposite position: it is not the thing being measured, it is the instrument doing the measuring, and an instrument whose own readings drift for reasons unrelated to what it is reading undermines the platform's reproducibility guarantee just as surely as a bug in the Execution Engine's orchestration would. This document's Determinism Requirements section below treats this obligation as real but calibrated differently for each Grader family, rather than either ignoring it for rubric-based Graders or holding them to a standard they cannot structurally meet.

**Isolation as a graded property applied deliberately, not a single blanket guarantee.** The Execution Engine Architecture already states that a Grader's execution is isolated from every other Grader's execution during the grading phase, mirroring the isolation principle established for Sandboxes. This document treats that isolation as load-bearing in a specific, narrow sense: a bug, a timeout, or an unexpected exception in one Grader must never be observable in another Grader's Score, in the Run's own execution record (already closed and immutable by the time grading begins), or in the Run's ability to reach a terminal state. Isolation here is not about hiding Graders from each other for its own sake — it is what allows the platform to add, remove, or reauthor a Grader without ever needing to reason about what that change might do to any other Grader evaluating the same Run.

## Responsibilities

A Grader is responsible for reading a completed Run's Execution Events and Artifacts, in full, through the Domain-defined read contracts this document's Interaction with the Domain Model section describes, and producing one or more Scores that represent its own, independent judgment of that Run. It is responsible for interpreting whatever standard it was authored against — an objective check's pass/fail condition, or a rubric's stated criteria — consistently, such that the same standard applied to the same record yields the same judgment, to the degree this document's Determinism Requirements section establishes is achievable for that Grader's family. It is responsible for classifying and surfacing its own failures clearly, so that the Execution Engine can distinguish a Grader that could not reach a judgment from one that reached a judgment the platform simply has not yet seen. And it is responsible for doing all of this using only the Run's own recorded history — nothing about a Grader's judgment may depend on information the platform's own architecture did not durably capture as part of that Run's Execution Events or Artifacts.

A Grader is not responsible for executing anything. It does not run tests, invoke a linter against a live checkout, or otherwise reproduce any part of what the Agent did — whatever objective signal a Grader reports (a test suite's exit code, a lint tool's findings) was itself captured as an Execution Event or Artifact during the Run's own execution, by the Adapter, and the Grader's job is to interpret that already-captured record, never to regenerate it. A Grader that re-executed code to determine its own verdict would be reaching back across a boundary the Execution Engine Architecture's topology already closes once execution concludes, and would be measuring a second, potentially different execution rather than the one the Run's record actually describes. A Grader is not responsible for deciding when it is invoked, how many other Graders run alongside it, or what happens to the Run once its own Score is produced — those are Execution Engine decisions, exactly as the Execution Engine Architecture already states from its own side of this same boundary. A Grader is not responsible for persisting its own Score durably — it produces a Score value and hands it back across the boundary for the Execution Engine to record through the platform's own persistence path, never writing directly to any store itself. And a Grader is not responsible for anything resembling the outcome of any other Grader evaluating the same Run — it has no legitimate reason to know another Grader exists, let alone what that other Grader concluded.

This division is not incidental to the Grader's design — it is the design. A Grader that also executed code, or made scheduling decisions, or persisted its own state, or reasoned about other Graders' outputs, would no longer be a narrow measurement boundary; it would be a second execution authority, a second orchestration authority, or a second store of record, each of which this corpus has already established belongs exactly once, elsewhere in the platform. A Grader's responsibility is deliberately, precisely everything between "reading a completed Run's record" and "producing a Score," and nothing on either side of that narrow span.

## Position in the Architecture

The Backend Architecture already places the Grader Layer in the platform's dependency graph with a rule this document treats as inviolable: the Grader Layer depends on the Domain Layer only, and is never depended upon by anything other than the Execution Engine that invokes it. It cannot depend on the Adapter Layer, the API Layer, or the Application Layer — a restriction the Backend Architecture calls out specifically because it is the dependency most tempting to add by accident, when a Grader author reaches for "which Agent produced this Run" and is tempted to import the Adapter that ran it rather than reading that fact as ordinary data on the Run itself, through the Domain Layer, the way every other Run fact is read. This document's contribution is explaining why that specific position — and no other — is the correct one for a component whose entire job is producing a comparable, trustworthy measurement from an already-closed record.

A Grader sits at the exact point in the architecture where the platform's execution-time concerns have already fully concluded and its analytical concerns begin. Every layer upstream of grading — the Sandbox, the Adapter, the Execution Engine's own orchestration — is dealing with a Run still in motion, subject to timeouts, retries, and the genuine unpredictability of untrusted third-party behavior. A Grader never touches any of that; it receives, exclusively, a Run whose execution has already reached a terminal step, per the Execution Engine Architecture's Grading Pipeline absolute sequencing rule. This is precisely why a Grader's dependency footprint is drawn so narrowly: a component that only ever reasons about a finished, immutable record has no legitimate need for anything upstream of that record's existence, and depending on nothing beyond the Domain Layer's read contracts is what keeps a Grader's reach confined to exactly what it needs.

A Grader's position relative to the Execution Engine, per the Execution Engine Architecture's own topology, is that of an invoked boundary, never a peer, symmetric with the Adapter's position on the other side of a Run's lifecycle. The Execution Engine calls into a Grader and consumes what it produces; a Grader never calls back into the Execution Engine's own orchestration logic, never asks it a question, and never waits on it for anything beyond receiving the completed Run's identity and the read access this document's Grader Contract section defines. This one-directional relationship — invoked, never invoking — is what makes a Grader's failure modes containable in exactly the way the Execution Engine Architecture's Failure Model already assumes: a Grader that misbehaves can be observed misbehaving and handled, but it can never itself reach further into the platform than the narrow channel through which it reports a Score or a failure.

A Grader's position relative to the Sandbox and the Adapter is one of strict topological separation, not merely a rule about which packages may import which. The Execution Engine Architecture states this plainly: a Grader never observes the Sandbox, the Adapter, or the Queue directly, and never participates in execution itself. This document treats that separation as the specific architectural fact that makes a Grader's view of a Run always complete and never partial — by the time any Grader is invoked, everything upstream of Persistence has already finished its work for that Run, which means a Grader reading a Run's Execution Events is reading the entire history that will ever exist for it, not a snapshot that might still grow.

A Grader's position relative to the Grader Layer's own internal organization, given code-level shape by the Backend Architecture's package structure, places one submodule per Grader family or per individual grading capability, each entirely ignorant of every sibling Grader's existence. An objective Grader checking build success and a rubric-based Grader judging code quality against the same Run are, architecturally, unrelated components that happen to be invoked against the same Run's record — neither has any relationship to the other, neither is aware the other exists, and nothing about one's implementation constrains or informs the other's.

## Grader Lifecycle

A Grader's lifecycle, from the Execution Engine's perspective, is fully described by the Grading Pipeline section of the Execution Engine Architecture: invocation begins only once a Run's execution has concluded, proceeds concurrently and independently of every other declared Grader, and ends when the Grader either produces a Score or is conclusively classified as having failed. This document describes the identical lifecycle from the Grader's own side of the boundary, filling in what happens inside each of those phases.

**Applicability resolution** happens before any Grader is invoked at all, and is not itself a Grader's own responsibility — it is the Execution Engine, consulting the Run's Case Version's declared applicable Graders (per Schema Design's Case Grader Declaration) and the specific Grader Version each resolved to at the moment the Run was created (per this document's Versioning section), that determines the full set of Graders a given Run's grading phase will invoke. A Grader has no visibility into, and no influence over, whether it was selected to grade a given Run — that decision was made entirely upstream, at Run creation, by a declaration the Grader itself is not a party to.

**Invocation** hands a Grader exactly two things: read access to the completed Run's Execution Events and Artifacts, through the Domain-defined read contracts this document's Grader Contract section specifies, and nothing else. A Grader does not receive the Run's identifier in any form that would let it reach into persistence beyond those contracts, does not receive information about which other Graders are also being invoked against this Run, and does not receive anything about the Agent, Adapter, or Sandbox that produced the Run beyond what the Execution Event and Artifact record itself already carries as ordinary domain data.

**Reading** is the phase in which a Grader consumes as much of the Run's Execution Event sequence and Artifact set as its own judgment requires — an objective Grader checking a single exit-code signal may read a narrow slice; a rubric-based Grader assessing overall code quality may read the Run's full diff and transcript. This document does not prescribe how much of the record any given Grader reads, only that whatever it reads is read exactly as durably recorded, never partially, never reordered, and never supplemented with anything from outside the Run's own record.

**Judgment** is the phase in which a Grader's own logic — an objective check's evaluation, a rubric's interpretation — is actually applied to what was read, producing the value or values that will become one or more Scores. This is the one phase of a Grader's lifecycle this document deliberately does not specify further, consistent with this document's Non-Goals: what happens inside judgment is exactly the grading capability a Grader's author is contributing, and the entire point of this document's contract is that the platform never needs to know how that judgment is reached in order to invoke it correctly.

**Reporting** hands the produced Score, or a classified failure if judgment could not be reached, back across the boundary to the Execution Engine, exactly as the Grading Pipeline's Score persistence discussion describes — a Grader's own lifecycle ends the moment this handoff completes, and it holds no further relationship to the Run, the Score, or anything that happens to either of them afterward.

## Grader Contract

Every Grader, regardless of family, satisfies the identical contract — the same shape of invocation, the same shape of output, the same behavioral guarantees — and this uniform contract is what lets the Execution Engine's Grading Pipeline schedule, parallelize, and collect results from an arbitrary number of Graders without ever branching on which specific grading capability it happens to be invoking. This document defines what that contract actually consists of.

**On invocation**, a Grader receives read access to exactly one completed Run's Execution Events and Artifacts, scoped to that Run alone, through the Domain-defined read contracts this document's Interaction with the Domain Model section specifies. This is the entirety of what a Grader receives — it does not receive write access to anything, it does not receive information about other Graders, and it does not receive anything about the Run's Agent, Adapter, Case authoring history, or Project beyond what is already expressed as ordinary, readable domain data on the Run itself.

**On completion**, a Grader returns one or more Score values, each carrying whatever measurement content that Score family produces (a pass/fail outcome and supporting detail for an objective Grader; a numeric or categorical judgment and supporting rationale for a rubric-based Grader) and implicitly attributed to the specific Grader Version that produced it, per Schema Design's Score specification. A Grader that produces more than one Score in a single invocation — an objective Grader that reports both a build-success signal and a separately meaningful test-pass signal, for instance — does so as multiple independent Score-producing measurements, not as one composite Score whose internal structure the platform's schema does not itself define.

**Completeness** means a Grader's judgment reflects the entirety of the Run record relevant to what it measures — a Grader does not silently ignore part of the Execution Event sequence or Artifact set that its own stated grading criteria would otherwise consider, because the judgment of what is or is not relevant to a specific Grader's own criteria belongs to that Grader's authored logic, not to an accidental gap in what it happened to read. An incomplete read is not a faster, more efficient grading pass — it is a Score that has silently diverged from what the Grader's own contract claims to measure.

**Non-mutation** is the contract's most absolute term: a Grader never modifies a Run, an Execution Event, or an Artifact, under any circumstance, per the Domain Model's sixth invariant. This is not merely a convention this document recommends — it is enforced structurally, by the Domain-defined read contracts a Grader is given never exposing any mutating operation against a Run's owned data in the first place, per this document's Interaction with the Domain Model section. A Grader's only legitimate domain effect is producing a Score, and, where its own explanatory output warrants it, a durably-owned Artifact of its own — per the Domain Model's treatment of Artifacts the grading process itself creates — never anything that alters the Run being graded.

**Independence from invocation order** is the final contract term: a Grader's judgment does not depend on which other Graders have or have not yet run against the same Run, because a Grader has no visibility into that fact at all. The Execution Engine's Parallel grading default posture, per the Execution Engine Architecture, depends on this term holding absolutely — an architecture that scheduled Graders concurrently while some Grader's correctness secretly depended on a specific ordering would be violating its own contract silently, in a way no amount of correct scheduling logic could compensate for.

## Score Production

A Score is the sole durable output a Grader is permitted to produce that becomes part of the platform's authoritative comparative record, and this document treats its production as the specific moment a Grader's entire purpose is discharged. Producing a Score is not merely returning a value — it is asserting, on behalf of the specific Grader Version that produced it, a judgment the platform will treat as permanent and comparable the instant it is durably recorded, per the Domain Model's statement that a Score is written once, atomically, and immutable thereafter.

**One Score per applicable Grader Version, per Run**, is the cardinality this document assumes throughout, matching Schema Design's uniqueness constraint on the Run-and-Grader-Version pairing. A Grader that internally decomposes its own judgment into several independently meaningful measurements produces several Scores, each satisfying this same one-per-pairing constraint under a conceptually distinct Grader identity, rather than one Grader silently overloading a single Score with several unrelated judgments a downstream consumer would need to unpack.

**A Score is a Grader's judgment, not a description of the Run.** This distinction matters architecturally: the Run's own record — its Execution Events, its Artifacts — describes what happened, faithfully and without evaluation, per the Adapter Architecture's treatment of translation as strictly non-evaluative. A Score is the one place in the platform's entire data model where evaluation actually happens, and it happens exactly once per Grader Version, cleanly separated from the record it was produced from. This separation is what makes it possible to re-author a Grader's judgment (a new Grader Version, with revised rubric wording or thresholds) without touching, in any way, the underlying record every past and future Grader Version will read identically.

**Supporting detail accompanies a Score without diluting its authority.** An objective Grader's Score may carry the specific check that failed; a rubric-based Grader's Score may carry the rationale a judge model produced for its verdict, potentially durably stored as a Grader-produced Artifact per the Domain Model's ownership treatment. This document treats such detail as valuable but strictly secondary to the Score's own judgment value — a human or downstream system consuming a Score can always find explanation for it, but the Score's judgment value itself is the fact every comparison, trend, and regression analysis this platform exists to support actually operates on.

**Some Grader families may produce additional explanatory metadata, such as a confidence estimate, alongside a Score.** A rubric-based Grader's judgment mechanism may naturally surface how confident it was in a given verdict, and this document does not prohibit a Grader Version from reporting that alongside its Score. It treats confidence, and metadata like it, exactly as it treats the rationale discussed above: supporting information a downstream consumer may find useful, never a mandatory part of the Grader Contract, and never authoritative in the way the Score itself is. A Grader Version is not required to produce a confidence estimate, and this document does not specify a shape for one — a Score's own judgment value remains the one fact every comparison, trend, and regression analysis actually operates on, regardless of what supporting metadata happens to accompany it.

**A Score's production is unconditional on the Run's overall outcome.** A Grader produces a Score whether the Agent succeeded, failed, or timed out, because a Grader's job is to measure what happened, not to gate its own participation on the Run having gone well — an Agent that produced no usable diff at all is still a legitimate subject for an objective Grader to score as a failure, and for a rubric-based Grader to characterize, rather than a case a Grader is permitted to skip.

**Composite or aggregate scores are not produced by Graders.** A Grader produces only its own independent measurement, exactly as this document's Grading Philosophy establishes for the "one Score per applicable Grader Version" posture that makes modular grading possible in the first place. An overall quality score, an overall pass/fail verdict, a weighted benchmark score, or a leaderboard ranking are all downstream concerns, built by reading many already-persisted Scores across one or more Runs and combining them under whatever weighting or ranking logic a separate, later concern defines — never produced by a Grader itself, and never fed back into a Run's grading phase as though they were one more Grader's own judgment. This document draws this line for the same reason it draws every other boundary in this document as narrowly as it does: a Grader that aggregated other Graders' Scores would need visibility into those Scores, which this document's Isolation Between Graders section and Grader Contract both already rule out, and would collapse the very independence that makes it possible to add, remove, or reauthor one Grader without touching any other.

## Rubric Interpretation

Rubric-based Graders occupy a specific, harder position within this document's uniform contract, and this section exists because that position deserves its own treatment rather than being folded silently into Score Production above. A rubric is a stated standard — structured criteria against which a Run's outcome is judged — and interpreting it correctly is a categorically different problem from evaluating an objective check's binary condition.

**A rubric's wording is content the Grader Version owns, not content this document specifies.** Exactly as this document's Non-Goals section states plainly, this document does not author rubrics, does not define a rubric authoring format, and does not specify how a rubric's criteria map onto a scoring scale. What this document does establish is that a rubric, once authored into a specific Grader Version, is immutable exactly as that Grader Version is — a rubric's wording cannot drift silently between two invocations of the "same" Grader without that drift being a new Grader Version, per this document's Versioning section, because an un-versioned drift in rubric wording would be indistinguishable, from a downstream comparison's perspective, from an actual change in Agent behavior.

**Interpretation happens against the Run's record alone, never against external context a rubric-based Grader was not given.** A rubric-based Grader's judgment — however sophisticated the mechanism producing it, typically an LLM-as-judge invocation — is scoped to the same Execution Events and Artifacts any other Grader receives, per this document's Grader Contract. A rubric-based Grader does not fetch outside information, does not consult other Runs for comparison, and does not have access to anything beyond the single completed Run it was invoked against, because introducing any of that would make its judgment depend on a wider, less controlled set of inputs than this platform's reproducibility architecture is designed to account for.

**Rubric-based judgment is judgment, not measurement, and this document does not pretend otherwise.** Where an objective Grader's Score is a direct, mechanical function of the record it reads, a rubric-based Grader's Score is the product of an interpretive act this platform does not attempt to make perfectly repeatable, for reasons this document's Determinism Requirements section addresses directly. This document's stance is that this is an honest limitation of the grading family itself, not a defect to be engineered away, and that the platform's correct response is to be explicit about it — through Grader Versioning, through observability of scoring variance, and through the failure and retry treatment below — rather than to overstate a rubric-based Grader's reliability to make it look more like an objective one than it actually is.

## Determinism Requirements

**Determinism of judgment given a fixed record, calibrated by Grader family, not a single uniform standard.** The Execution Engine Architecture already distinguishes the Agent's permitted unpredictability from the orchestration's required determinism, and the Adapter Architecture draws an analogous line for translation. This document draws a third, distinct line, specific to grading, and it is deliberately not the same line for both Grader families this document has already distinguished.

**Objective Graders are held to strict determinism, without exception.** Given the identical completed Run record, an objective Grader's Score must be the same every time that Grader Version is invoked against it. An objective check is, by definition, a mechanical evaluation of a mechanically checkable condition, and a Grader Version that produced two different verdicts for the identical input would not be exhibiting acceptable variance — it would be exhibiting a defect, exactly as an Adapter that translated the identical Agent action into two different Execution Event shapes would be exhibiting a defect per the Adapter Architecture's own determinism treatment. This standard is non-negotiable for this Grader family because nothing about the problem an objective Grader solves has any legitimate source of variance once its input is fixed.

**Rubric-based Graders are held to a calibrated, honestly weaker standard: bounded variance, not bit-identical reproduction.** A rubric-based Grader, particularly one implemented as an LLM-as-judge invocation, may not produce the identical Score on every invocation against the identical Run record, even holding the Grader Version's rubric wording and thresholds fixed, because the underlying judgment mechanism is not architecturally guaranteed to be deterministic. This document does not require what the mechanism cannot structurally deliver. What it does require is that a rubric-based Grader Version minimize this variance to whatever degree its own implementation allows — fixed prompts, controlled sampling parameters, a pinned judge-model version where the Grader Version's own authoring controls that choice — and that whatever variance remains is attributable entirely to the Grader Version's own judgment mechanism, never conflated with a change in the Agent's behavior or the Run's record. This is the same discipline the Versioning Model applies to every other axis: variance is acceptable only when it is attributable, and a rubric-based Grader Version's residual non-determinism is attributable precisely because the Grader Version identity that produced a given Score is permanently recorded alongside it, per Schema Design's Score specification.

**A Score, once produced, is authoritative regardless of whether re-invoking the same Grader Version would reproduce it exactly.** This document is explicit that a Score's immutability, established by the Domain Model, is not contingent on the underlying Grader having been deterministic — a rubric-based Grader's Score is exactly as permanent and exactly as comparable as an objective Grader's, once written, even though the objective Grader's Score carries a stronger guarantee that re-running it would produce the identical value. The platform's comparability guarantee rests on Grader Version pinning, not on grading determinism, and this document treats that distinction as the correct resolution of a tension that would otherwise be irreconcilable for any platform that wants to support LLM-as-judge grading at all.

## Isolation Between Graders

**No shared state, no shared failure surface, no shared timing dependency.** The Execution Engine Architecture already establishes that a Grader's execution — its own resource consumption, its own failure, its own runtime behavior — has no observable effect on any other Grader evaluating the same Run. This document treats that as an architectural property this document's own Grader Contract makes close to automatic, rather than a separately engineered enforcement mechanism: because a Grader receives only read access to a Run's record and no visibility into any other Grader's existence, invocation, or output, there is structurally nothing through which one Grader's misbehavior could reach another.

**Isolation extends to resource contention, not only to correctness.** A rubric-based Grader waiting on a slow external judge-model invocation must never cause an objective Grader evaluating the same Run to wait alongside it — the Execution Engine Architecture's Parallel grading default posture depends on this holding, and this document's own contract supports it by giving each Grader invocation an entirely independent execution context, with no synchronization point between Graders of any kind, not even an implicit one such as a shared connection pool whose exhaustion by one Grader could starve another.

**One Grader's failure never blocks, delays, or degrades another Grader's ability to produce its own Score.** This is the Domain Model's explicit guarantee, restated here as the specific design consequence this document's contract is built to deliver: the Execution Engine collects each Grader's result as it completes, independently, per the Grading Pipeline's Score persistence discussion, which means a Grader that raises an exception on its very first read of the Run's Execution Events has no bearing whatsoever on a sibling Grader that completes cleanly moments later.

**Isolation does not mean identical treatment of every Grader's resource needs.** A Grader that requires substantially more compute, memory, or external-call budget than another (a rubric-based Grader invoking a large judge model, against an objective Grader performing a near-instant pattern match) is isolated in the correctness sense this section establishes, but is not thereby entitled to identical scheduling priority or resource allocation — that is a Scalability concern this document addresses separately below, and isolation as a correctness property should not be conflated with fairness as a resource-allocation property, which the Execution Engine's own Scheduling Philosophy governs, not this document.

## Interaction with the Execution Engine

The relationship this section describes is the same one the Execution Engine Architecture already describes from its own side, in its Grading Pipeline section — this document restates it from the Grader's perspective specifically to make explicit what the Grader Layer may assume about that relationship and what it must never assume.

**The Execution Engine is the sole invoker of every Grader, and a Grader has no legitimate path to being invoked any other way.** A Grader is never triggered directly by an API request, a user action, or any component other than the Execution Engine's own Grading Pipeline logic, consistent with the Backend Architecture's dependency rules placing the Grader Layer beneath Background Workers and Application, never reachable from the API Layer directly. This is what keeps grading a strictly post-execution phase of a Run's lifecycle rather than something a caller could trigger prematurely, against a Run whose execution has not yet concluded.

**The Execution Engine owns scheduling; the Grader owns judgment; neither leaks into the other.** The Execution Engine decides which Graders to invoke (per Applicability resolution in this document's Grader Lifecycle), when to invoke them (only after execution concludes, per the absolute sequencing rule the Execution Engine Architecture establishes), how many to run concurrently (bounded by whatever grading-capacity limits the platform imposes, a Scalability concern this document addresses below), and what a partial or failed grading phase means for the Run's terminal state. A Grader owns none of that — its own responsibility begins the moment it is invoked and ends the moment it reports a Score or a classified failure, and this document's Responsibilities section already establishes that a Grader has no visibility into, and exerts no influence over, any of the scheduling decisions surrounding it.

**Score persistence is mediated, never direct.** A Grader hands a produced Score back to the Execution Engine, which writes it durably through the same Application-Layer-mediated, Infrastructure-implemented path every other write in the platform uses, exactly as the Backend Architecture's Background Execution Flow already states — the Worker does not grant the Grader Layer direct database access, and this document treats that restriction as absolute: a Grader that somehow acquired the ability to write its own Score directly would be a second, uncontrolled persistence path into a table whose uniqueness and idempotency guarantees, per Schema Design and Database Design, depend entirely on every write flowing through the one path the platform's architecture actually enforces.

**Grader failure is surfaced to the Execution Engine as a classified fact, never absorbed silently.** Per this document's Failure Model below, a Grader that cannot reach a judgment reports that inability clearly enough for the Execution Engine to record the failure against that specific Grader and proceed with collecting results from the others, exactly as the Grading Pipeline's Partial grading failures treatment already establishes from the orchestrating side.

## Interaction with the Domain Model

A Grader's entire relationship to platform data is mediated through the Domain Layer, and this document treats that mediation as the specific mechanism that makes every other guarantee in this document enforceable rather than merely aspirational.

**Read contracts, not raw persistence access.** A Grader reads a Run's Execution Events and Artifacts through interfaces the Domain Layer defines and Infrastructure implements, per the Backend Architecture's dependency rules placing the Grader Layer's only permitted dependency on the Domain Layer. A Grader never issues a database query, never touches object storage directly, and never knows or cares whether a given Artifact's payload happens to live in PostgreSQL, an object store, or somewhere this corpus has not yet anticipated — it knows only the domain-level shape of what it is reading, exactly as the Domain Model defines that shape, insulated entirely from how that shape happens to be physically stored.

**The contracts a Grader is given expose reading, never writing, of anything belonging to a Run.** This is the structural mechanism, referenced in this document's Grader Contract section, that makes non-mutation an enforced property rather than a convention a Grader author must simply remember to honor — there is no method on the interfaces a Grader is handed that would let it alter a Run's status, insert an Execution Event, or modify an Artifact, because the Domain Layer's own contract surface for the Grader Layer was never given one.

**A Grader knows a Run only as the Domain Model describes it, never as any specific Agent or Adapter's native reality.** Because the Normalized Domain Model shape is what every Execution Event's content actually takes, per the Domain Model's own clarification of that term, a Grader reading a Run's Execution Events is reading exactly the same agent-agnostic representation the Execution Engine itself operates on — a Grader has no need to know, and this document's contract gives it no way to discover, which Agent or Adapter Version actually produced the Run it is grading, unless that fact is itself exposed as ordinary, ordinary-to-read domain data on the Run (which Grader Version pinning and comparison, addressed in this document's Versioning section, may sometimes require, but which is read as data, never inferred by importing or invoking the Adapter that produced it, per the Backend Architecture's explicit prohibition on exactly that shortcut).

**Domain invariants a Grader must never violate are enforced by the same Domain Layer that enforces them for every other component.** A Score's uniqueness per Run-and-Grader-Version pairing, a Grader Version's immutability once written, a Run's closure to further change once terminal — none of these are rules a Grader is trusted to honor voluntarily. They are enforced the same way every other domain invariant in this corpus is enforced: by the Domain Layer's own construction, independent of whether any specific Grader's authored logic is well-behaved.

## Versioning

**A Grader Version is an immutable record of one specific revision of a Grader's rubric wording, scoring thresholds, or objective-check logic**, per Schema Design's Grader Version specification, and this document treats every one of those three kinds of change — rubric wording, thresholds, logic — as equally version-triggering, without distinguishing a "minor" rubric wording tweak from a "major" logic rewrite. This is deliberate: the Versioning Model's stated reason for treating Grader as one of the six independently versioned axes is that scores from different Grader Versions are not comparable, and that reasoning applies with equal force to a subtle wording change (which can shift a rubric-based Grader's judgment meaningfully) and an obvious logic rewrite — this document does not create a lesser category of change that escapes versioning, because doing so would reintroduce exactly the ambiguity ("did the score change because the agent regressed, or because we tweaked the rubric") the Versioning Model exists to eliminate.

**Case Grader Declaration references a stable Grader identity, not a specific Grader Version**, per Schema Design's own specification of that association — a Case Version declares which Graders (plural, by their enduring identity) apply to it, and which specific Grader Version actually executes against a given Run is resolved separately, at the moment that Run is created, and pinned permanently from that point forward, exactly as every other one of the Run's six versioned inputs is pinned per the Domain Model's Versioning Model. This document treats that resolution-and-pinning step as happening entirely outside the Grader's own lifecycle — a Grader Version does not select itself for a Run; it is selected on its behalf, once, at Run creation, and simply executes when the Execution Engine later invokes it.

**A Score is permanently attributed to exactly the Grader Version that produced it**, never to the Grader's stable identity alone, which is what makes it possible to tell, per the Domain Model, whether an apparent score regression reflects a real change in Agent behavior or simply a change in how the Grader scores. This document treats this attribution as the single most important fact this section establishes, because it is the mechanism that makes rubric-based grading's calibrated non-determinism (this document's Determinism Requirements section) tolerable at the platform level: any variance a rubric-based Grader Version introduces is fully contained within comparisons across that one Grader Version, and never silently blended into a comparison across Grader Versions that a viewer might mistake for a comparison across Agent behavior alone.

**Grader Versions accumulate; they are never edited in place**, per Database Design's Immutable versions principle, applied here exactly as it is applied to every other versioned axis — a revision to a rubric's wording produces a new Grader Version row, referenced by every Score produced from that point forward, while every historical Score produced under the prior Grader Version remains permanently, correctly attributed to it. A Grader with many superseded Grader Versions behind it is not a Grader accumulating technical debt; it is a Grader whose full evaluative history is exactly as reconstructable as the Domain Model's reproducibility guarantee requires.

## Compatibility

**A Grader Version's compatibility obligation runs toward the Normalized Domain Model shape as it existed when that Grader Version was authored, not toward whatever shape the Domain Model has since evolved into.** Exactly as the Adapter Architecture establishes for Adapters reading the Domain Model's evolving action-type vocabulary, a Grader Version is authored against a specific understanding of what an Execution Event or Artifact can contain, and this document does not require every existing Grader Version to be rewritten every time the Domain Model's Extensibility Model accommodates a new event or action type elsewhere in the platform. A Grader Version that predates a given extension continues to interpret the record it knows how to interpret, correctly, for every Run whose Execution Events fall within that Grader Version's original understanding.

**A Grader Version that encounters content its own logic does not recognize must fail explicitly, never silently.** This document treats an unrecognized Execution Event type, an unexpected Artifact shape, or any other content a Grader Version was not authored to interpret as a signal worth surfacing precisely — per this document's Failure Model below — rather than a condition a Grader is permitted to skip past quietly while still producing a Score as if nothing were amiss. A Score produced by silently ignoring content the Grader did not know how to handle would be exactly the kind of incomplete, misleadingly confident measurement this document's Grader Contract's Completeness term exists to prevent.

**Cross-Grader-Version comparability is bounded, deliberately, to what this document's Versioning section already establishes.** Two Scores from two different Grader Versions of the same Grader are not directly comparable as if they measured the identical thing, exactly as two Scores from two entirely different Graders are not — this document does not introduce, and this corpus does not anticipate, any mechanism for automatically normalizing scores across Grader Versions, because doing so would require exactly the kind of judgment (how much did the rubric actually change in effect, not merely in wording) that this document's Rubric Interpretation section already establishes the platform does not attempt to make mechanically.

## Failure Model

**Judgment failure.** A Grader's own logic raises an exception, times out, or otherwise fails to reach a Score while attempting to interpret a Run's record — an unrecognized content shape (per Compatibility above), an internal defect in the Grader's own authored logic, or an external dependency (a judge-model API, for a rubric-based Grader) that failed or timed out mid-invocation. This is classified as a failure specific to that Grader, attributed to the specific Grader Version involved, and never conflated with a failure of the Run's own execution, which by the time grading begins is already complete and immutable regardless of what happens during grading itself, exactly as the Execution Engine Architecture's own Failure Model already states for Grader failure generally.

**Infrastructure failure.** The channel through which a Grader reads a Run's Execution Events and Artifacts, or through which a rubric-based Grader reaches an external judge-model service, is disrupted transiently — a network interruption, a temporary service outage unrelated to anything the Grader's own logic did wrong. This document classifies this the same way the Execution Engine Architecture's Failure Model classifies network interruptions generally: a transient, typically retryable condition, distinguished from a judgment failure precisely because the Grader's own logic never had the opportunity to actually reach or fail to reach a verdict.

**Containment is total, in both directions.** A Grader's failure, of either kind, is contained to that Grader alone — it never affects another Grader's ability to produce its own Score, per this document's Isolation Between Graders section, and it never affects the Run's own execution record, which grading can only read, never write. This bidirectional containment is what makes a Grader's failure classifiable purely as information about that Grader's own reliability, never as ambiguous evidence about the Run, the Agent, or any other Grader.

**Partial grading is the honest, expected shape of a failure this architecture does not attempt to hide.** A Run can, and legitimately does, reach its terminal state with some declared Graders having produced Scores and others having conclusively failed, per the Domain Model's thirteenth invariant treating partial grading as a property of a Completed Run rather than a distinct outcome. This document does not treat a Grader's failure as something the platform must eventually resolve into full success before a Run can be considered done — a grading window that never closed, waiting indefinitely for every Grader to eventually succeed, would mean the platform could never present a Run's results with the confidence this platform's entire comparative purpose depends on.

## Retry Philosophy

**Infrastructure-classified Grader failures are retried, bounded and idempotent, exactly as every other transient failure in this pipeline is.** Per the Execution Engine Architecture's own Retry Philosophy, a network interruption or a transient external-service failure encountered while invoking a Grader is safely retryable because retrying it does not change what is being measured — the Run's record a Grader reads is fixed and immutable, so re-invoking a Grader against it after a transient failure produces a judgment against the identical input, not a different measurement of a moving target. Score's uniqueness constraint on the Run-and-Grader-Version pairing, per Schema Design, is what makes this safe mechanically: a retried Grader invocation that eventually succeeds produces a Score that either inserts cleanly or is recognized as already durably recorded, never a silent duplicate.

**Judgment failures are not retried automatically, because retrying does not make a broken judgment correct.** A Grader whose own logic raised an exception on an unrecognized content shape, or whose own defect prevented it from reaching a verdict, will encounter the identical obstacle on an immediate retry against the identical, immutable Run record — this document treats blind retrying of this category exactly as the Execution Engine Architecture's Retry Philosophy treats domain-level rejections generally: retrying a defect does not make it valid, and a failure of this kind is surfaced, attributed to the specific Grader Version, and left for that Grader Version's own author to address in a future, newly versioned revision, per this document's Versioning section.

**Rubric-based Graders warrant a narrower, more deliberate retry posture than objective Graders, specifically because of their calibrated non-determinism.** An objective Grader retried after a transient infrastructure failure is expected to produce the identical Score on retry, since its judgment is strictly deterministic per this document's Determinism Requirements. A rubric-based Grader retried under the same circumstances may not, and this document treats that as an acceptable consequence of retrying an infrastructure failure specifically — never a reason to retry a rubric-based Grader's judgment failure in the hope that a different attempt produces a more favorable verdict, which would corrupt the very reproducibility-through-attribution guarantee this document's Versioning section establishes.

**Where retries deliberately do not happen** mirrors the Execution Engine Architecture's own stance exactly: a Grader is never retried past whatever bounded attempt policy the platform applies, because a grading phase that retries indefinitely is architecturally identical to the "grading window that never closes" this document's Failure Model already rules out. Where a Grader genuinely needs to be attempted again after exhausting retry budget, that is a new grading attempt against the same immutable Run, governed by whatever grading-window policy the Execution Engine's own Grading Pipeline applies, never a silent, unbounded extension of the original invocation.

## Resource Ownership

**A Grader owns no persistent storage of its own**, mirroring the Adapter's identical restriction from the opposite side of a Run's lifecycle — every fact a Grader produces (a Score, an explanatory Artifact) flows immediately back across the boundary for the Execution Engine to record durably through the platform's own persistence path, and a Grader that accumulated its own record, even transiently across invocations, would be creating a second, uncontrolled copy of facts this platform's architecture depends on having exactly one authoritative copy of.

**A Grader's compute and memory footprint during a single invocation is its own to consume, but is not drawn from the Sandbox's resource envelope**, because, per this document's Responsibilities section, a Grader never executes anything inside a Sandbox and has no relationship to one at all — an objective Grader's resource needs are typically minimal (reading and pattern-matching against an already-recorded record); a rubric-based Grader's resource needs may be substantially larger (invoking a large judge model), and this document treats both as consuming the platform's grading-capacity resource pool specifically, a distinct accounting surface from execution-time Sandbox resources, addressed further under this document's Scalability section.

**External-service credentials a rubric-based Grader requires — an API key for a judge-model service, most commonly — are scoped as narrowly as that specific Grader Version's own requirements demand, and owned by the platform on the Grader's behalf, never by the Grader itself as durable state it manages.** This document treats such a credential the same way the Adapter Architecture treats an Adapter's own vendor credentials: platform-held, used on the platform's behalf, injected at invocation time, and never something a Grader accumulates, caches indefinitely, or exposes as part of its own output.

**Cost incurred by a Grader's own invocation — most concretely, the cost of a rubric-based Grader's external judge-model calls — is a cost the platform accounts for as part of its own operating cost, distinct from the per-Run execution cost (token usage, wall-clock time, compute) the Domain Model already treats as intrinsic to the Run itself.** This document draws this distinction because a Run's execution cost measures what the Agent under evaluation consumed, while a Grader's own invocation cost measures what the platform itself spent to produce a judgment — conflating the two would misattribute platform-side grading expense to the Agent being evaluated, corrupting exactly the kind of cost comparison the Domain Model's cost-as-first-class-metric treatment exists to support accurately.

## Security

A Grader operates downstream of the platform's most sensitive trust boundary, not at it — by the time any Grader is invoked, the Sandbox has already been torn down, per the Execution Engine Architecture's Sandbox Lifecycle, and a Grader has no path back into it whatsoever. This document does not treat a Grader as facing the same live, adversarial-execution risk an Adapter faces; it treats a Grader as facing a narrower, but still real, risk: the content it reads, while no longer live or executable, still originated from an untrusted Sandbox running an Agent's autonomously generated behavior against a potentially adversarial repository, per the System Overview's own Threat Model, and that provenance does not stop mattering once execution has concluded.

**Content read by a Grader is never trusted implicitly, even though it is no longer live.** An Execution Event's payload, a diff, a transcript, or any other Artifact a Grader reads may contain content an Agent produced, deliberately or accidentally, that was never intended to be executed but was crafted, or happens, to disrupt or manipulate whatever process reads it next. A Grader's own logic is written defensively against malformed, unexpectedly large, or adversarially structured content in exactly the sense the Adapter Architecture already establishes for content an Adapter observes live — the fact that a Grader's input arrives through a durable, already-recorded channel rather than a live one does not make that input any more trustworthy in its content.

**Rubric-based Graders face a security consideration specific to their family: instruction injection embedded in the content being graded.** Because a rubric-based Grader's judgment mechanism typically involves handing a Run's recorded content — including content an Agent itself wrote, such as code comments, commit messages, or output text — to an external judge-model invocation, this document treats that content as a channel through which an adversarial instruction could attempt to influence the judge model's own behavior (for instance, text embedded in a diff attempting to instruct a judge model to disregard its rubric and assign a favorable score). A rubric-based Grader Version's own design is responsible for treating every part of a Run's recorded content as untrusted input to the judgment mechanism, never as a channel through which the content being graded can redirect how it is graded — this document does not specify the defensive mechanism (structured prompting, content isolation, or any other technique), consistent with this document's Non-Goals, but establishes that the obligation to defend against it belongs to the Grader Version's own authored logic, informed by the platform's own stated posture that content originating from a Run should never be treated as instructions to the platform's own components.

**A Grader's inability to modify a Run is itself a security property, not only a correctness one.** Because the read contracts this document's Interaction with the Domain Model section describes expose no mutating operation to the Grader Layer at all, a Grader — however compromised, buggy, or adversarially manipulated its own judgment mechanism becomes — has no structural path to altering the Run's execution record, corrupting another Grader's Score, or affecting the Run's own lifecycle state. This is the same principle the Execution Engine Architecture applies to Sandbox isolation, applied here to a different, later boundary: the blast radius of a Grader's worst possible failure is bounded, by construction, to that Grader's own Score.

**A Grader's own credentials, where it holds any, are never exposed to anything upstream of it.** Because a Grader is invoked only after a Run's Sandbox has already been torn down, there is no live Agent for a Grader's credentials to leak toward even in principle — but this document states the boundary explicitly regardless, consistent with the System Overview's structural, not merely disciplinary, treatment of secret handling: a Grader's own external-service credentials are provisioned to it narrowly, per this document's Resource Ownership section, and are never written into a Score, an Execution Event, or any other durably recorded, externally visible fact the platform produces.

## Observability

Every Grader invocation is correlated to the same correlation identifier established at Run creation and threaded through every component this document's Position in the Architecture describes, per the System Overview's Observability treatment — a Grader's own logging, wherever it exists, carries that identifier so that an engineer reconstructing a Run's full operational history can see each Grader's contribution to the grading phase alongside everything the Execution Engine, Sandbox, and Adapter separately produced upstream of it.

**Per-Grader-Version latency and outcome rates** are worth measuring as their own category, distinct from general execution-timing metrics, because grader latency is one of the specific numbers the System Overview's Observability section already names as answering "is the platform itself healthy" — a rubric-based Grader Version whose latency has drifted upward, or whose judgment-failure rate has climbed, is a signal worth attributing to that specific Grader Version, not blended into a platform-wide grading average that could mask a regression in one particular grading capability.

**Score distribution monitoring** is a category of observability specific to grading that this document calls out because nothing upstream of the Grader Layer has an equivalent need: because a rubric-based Grader Version's judgment carries the calibrated non-determinism this document's Determinism Requirements section acknowledges, watching how that Grader Version's Score distribution shifts over time — even while its rubric wording remains fixed — is a leading indicator of drift in whatever underlying judgment mechanism it depends on (an upstream judge-model provider silently updating its own model, for instance), distinguishable, through this monitoring, from a genuine shift in Agent behavior across the Runs being scored.

**Failure-classification observability**, tracking how often each of this document's Failure Model categories (judgment failure, infrastructure failure) actually occurs, per Grader Version, is what lets the platform's operators distinguish a genuinely unreliable Grader Version from a Grader that is functioning correctly but happens to be scoring a batch of Runs whose Agent behavior was poor — exactly the distinction this document's Failure Model exists to make possible, made concrete here as something worth actually measuring.

This document does not specify the mechanisms — logging framework, metrics backend, tracing system — through which any of this observability is delivered, consistent with the Execution Engine Architecture's and the Adapter Architecture's own restraint on this exact question; it establishes only what is worth observing about a Grader's behavior specifically, leaving how to a future, dedicated Observability Architecture document.

## Scalability

**Parallel grading, already established from the Execution Engine's side as the default posture, is what makes grading capacity scale the same way execution capacity does.** Because every declared Grader is architecturally independent of every other one, per this document's Isolation Between Graders section, grading throughput scales by adding more concurrent grading capability, without any correctness concern about Graders interfering with each other regardless of how many run concurrently — the only bound is whatever resource limits the platform's grading capacity imposes at a given time, a scheduling concern the Execution Engine's own Scheduling Philosophy owns, not a correctness concern this document needs to resolve.

**Heterogeneous resource profiles across Grader families are a scheduling reality this document surfaces but does not resolve.** An objective Grader's near-instantaneous, low-cost evaluation and a rubric-based Grader's substantially heavier, externally-dependent invocation impose very different demands on the platform's grading capacity, and treating every Grader as an interchangeable unit of scheduling work would either starve rubric-based Graders of the time and external-call budget they genuinely need, or over-provision capacity for objective Graders that never need it. This document establishes that a Grader Version's resource profile is a fact worth exposing to the Execution Engine's own resource-aware scheduling, exactly as the Execution Engine Architecture's Scheduling Philosophy already anticipates for GPU-routing and resource-aware routing generally — this document does not specify how that routing decision is made, only that it is, architecturally, the same scheduling-policy layer's responsibility to own, not something a Grader itself should ever need to negotiate on its own behalf.

**GPU-backed or otherwise specialized compute, should some future Grader require it**, is accommodated the same way any other Grader resource requirement is — as a property of the specific Grader invocation for a given Run, routed through the resource-aware scheduling and GPU-routing policy the Execution Engine Architecture's Scheduling Philosophy already anticipates, not as a structural change to this document's contract. A Grader's own logic does not need to know or care what kind of compute it actually runs on, only that the boundary invoking it fulfills the contract this document establishes.

**High-volume grading, at the scale Database Design and Schema Design anticipate (tens of millions of Scores over the platform's lifetime, a modest multiple of Run volume), is handled primarily through this document's statelessness and idempotency properties**, inherited directly from the Execution Engine Architecture's own: because a Grader holds no durable state between invocations and every Score it produces is written through an idempotent, uniqueness-constrained path, nothing in this document's design depends on grading volume staying below any particular threshold — scaling grading capacity is a matter of provisioning more concurrent grading capability, never a matter of redesigning this document's contract.

## Extensibility

Every principle in this document converges on the same extensibility claim this document's Grading Philosophy opened with: adding a new grading capability means authoring a new Grader that satisfies this document's Grader Contract, and nothing else in the platform changes as a result. This section makes that claim concrete against the specific extensibility scenarios this corpus has already anticipated.

**A new Grader, of either existing family, is purely additive**, per the Domain Model's own Extensibility Model treatment: because Graders are independently deployable and never modify Runs, adding one never risks destabilizing any existing Grader or the Run lifecycle itself. A Case's declared applicable Graders (per Schema Design's Case Grader Declaration) simply grows to include the new Grader, and every Run created against that Case Version from that point forward resolves and pins the new Grader's initial Grader Version exactly as it does for every other declared Grader — no existing Grader, existing Score, or existing Run is touched.

**A future Grader SDK**, anticipated by Schema Design's Future Extensions and the Domain Model's Extensibility Model, formalizes this document's Grader Contract into a versioned, externally documented interface — but it does not change the contract's shape, only its degree of formality and, potentially, who is capable of authoring a conforming Grader. Everything this document establishes about reading, judgment, Score production, versioning, and failure classification remains exactly as true of an SDK-authored Grader as of a platform-team-authored one, because the SDK's entire purpose is to make satisfying this document's existing contract easier, not to introduce a different one.

**Grader capability metadata** — a declared statement of whether a given Grader Version is objective or rubric-based, along with descriptive facts such as its typical cost, typical latency, or its dependence on an external service — is anticipated by this document as a natural extension of the Grader Contract, formalized alongside a future Grader SDK rather than specified here. This document does not treat such metadata as part of a Grader Version's judgment logic; it is a declared, descriptive fact about a Grader Version, not an implementation detail this document would otherwise leave unspecified. Its architectural purpose is to let the Execution Engine's own resource-aware scheduling, per this document's Scalability section, make better-informed routing and concurrency decisions as the platform's population of Graders grows more heterogeneous, without requiring this document's contract itself to change to accommodate it.

**A new grading family entirely unlike objective or rubric-based grading** — should the platform's needs ever produce one — is accommodated by the same observation the Domain Model's Grader treatment already makes: both existing families are modeled identically as "something that reads a Run's record and emits a Score," and this document's contract is drawn at exactly that level of generality specifically so that a third family, whatever it turns out to measure, satisfies the identical contract without requiring this document, the Domain Model, or the Execution Engine's Grading Pipeline to be revised.

**Additional grading engines** — a new invocation mechanism for how Graders execute, distinct from how Graders run today — are accommodated by the same isolation and scheduling boundary the Execution Engine Architecture's Grading Pipeline already establishes for exactly this scenario: a new Grader, running under a new mechanism, is simply one more independent, isolated participant the Execution Engine schedules and collects a Score from, following the identical contract every existing Grader already follows.

## Non-Goals

This document defines the architecture governing the Grader Layer; it does not define how any specific Grader is actually implemented. It does not specify rubric authoring formats, rubric-wording best practices, or scoring-scale design, all of which remain entirely a Grader Version author's own concern, referenced here only insofar as this document establishes that whatever a Grader Version's rubric says, it says immutably once versioned. It does not specify which judge-model provider or model a rubric-based Grader uses, how that provider is invoked, authenticated against, or rate-limited, or how prompt engineering for a judge-model invocation is approached — those are per-Grader-Version implementation decisions made against this document's contract, not part of it. It does not provide interfaces, type signatures, or any code-level specification of the Domain-defined read contracts a Grader consumes, which remain entirely the Domain Layer's own responsibility, referenced here by name and never redefined. It does not specify SDK design for a future Grader SDK beyond the Extensibility section's architectural anticipation of one. It does not specify the defensive technique a rubric-based Grader Version uses to resist instruction injection embedded in graded content, beyond establishing, in this document's Security section, that the obligation to resist it exists. It does not specify logging, metrics, or tracing implementation, beyond naming what is worth observing in this document's Observability section. It does not define Execution Engine internals, Sandbox or Adapter mechanics, or persistence mechanics, all of which remain exactly as the Execution Engine Architecture, the Adapter Architecture, Database Design, and Schema Design already establish them, referenced here only at the boundary where a Grader touches them. And it does not include diagrams, pseudocode, or implementation examples of any kind, consistent with every architecture document in this corpus treating those as artifacts of a later, separate implementation effort, not of the architecture itself.
