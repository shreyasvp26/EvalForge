# REST API Design

## Purpose

Every document that precedes this one describes EvalForge from the inside: what the platform is (Domain Model), how its codebase is organized (Backend Architecture), and how its data is stored (Database Design, Schema Design). None of them describe what the platform looks like from outside its own process boundary. That is a different question, and it deserves its own document for the same reason ADR-0001 already established as a system-wide principle: the frontend consumes the same API any external caller would use, and there is no private, undocumented internal API. If that principle is true, then the API is not an implementation detail of the backend — it is the platform's actual product surface, the one artifact every consumer of EvalForge, human or automated, ever directly touches. A surface with that much leverage over the platform's future needs its own architectural contract, considered independently of whatever internal module happens to implement it on a given day.

This document is also, concretely, the bridge between the frontend and the backend the Backend Architecture describes. The Presentation Plane, per the System Overview, is a pure consumer of the REST API and SSE stream, holding no independent business logic — every capability the frontend offers a user exists because this API exposes it. That framing sets the standard this document is held to: an omission here is not a documentation gap, it is a capability the frontend (and every other client) cannot have.

Finally, this document exists because an API, unlike an internal module boundary, cannot be casually refactored once real clients depend on it. The Backend Architecture's internal layers can be reorganized behind the scenes as long as their external contracts hold; the API *is* the external contract, for every client that will ever be written against it, for as long as that client exists. A document governing this much inertia has to be written with backward compatibility and long-term evolution as first-order concerns from the outset, not appended later once the cost of getting it wrong has already been paid by real integrations.

This document specifies the architecture governing the API — its philosophy, its resource model, its request and response shape, its versioning and evolution rules. It is deliberately not an endpoint reference, an OpenAPI specification, or FastAPI implementation code; those are downstream artifacts that must conform to the rules established here, produced once this architecture is settled, not before.

## API Philosophy

**REST over RPC.** ADR-0001 already settled REST over GraphQL for the platform as a whole; this document extends that decision by ruling out RPC-style APIs as well, for a related but distinct reason. EvalForge's domain is a well-defined set of resources — Projects, Suites, Cases, Runs, and so on — with lifecycle transitions that map naturally onto resource state (a Run moves from queued to running to a terminal outcome) rather than onto an open-ended set of remote procedures. An RPC-style API tends to accumulate one endpoint per business operation, which grows unboundedly as the platform's capabilities grow and offers no structural way for a client to infer what it can do with a resource it has not yet been told about explicitly. A resource-oriented REST API, by contrast, lets a client reason about a new resource largely by analogy to resources it already understands — if it knows how to list, fetch, and create a Suite, it already knows most of what it needs to do the same for a Case, because both are resources following the same conventions this document establishes.

**Resource-oriented design.** Every noun in the Domain Model that has independent identity, a lifecycle, and a reason to be addressed directly by a client is modeled as an API resource, and every operation on it is expressed as a standard HTTP verb applied to that resource, rather than as a bespoke action endpoint. This is not a stylistic preference; it is what makes the API's shape predictable enough that a client integrating against Runs already understands, without being told, roughly how it would integrate against Scores. Where an operation genuinely does not map onto a create, read, update, or delete of some resource — a use case the Domain Model does not model as a persistent entity in its own right — this document still prefers expressing it as an action on an existing resource's state (a status transition) over introducing a verb-shaped endpoint that breaks the resource-oriented pattern.

**Statelessness.** Every request carries everything the API needs to authenticate, authorize, and fulfill it; no request depends on server-held session state left over from a previous request by the same client. This mirrors the Backend Architecture's own statement that the API layer is stateless by construction, and it is what allows the API layer to scale horizontally behind a load balancer with no coordination overhead, and what allows any client — a browser tab, a CI job, a long-lived integration — to make a request without first establishing or resuming some server-side conversation.

**Predictability.** A client should be able to correctly guess the shape of an API interaction it has not yet tried, based on interactions with the API it has already seen. This is the practical payoff of resource-oriented, convention-governed design: predictability is not an aesthetic goal, it is what reduces the cost of every future integration against the platform, including EvalForge's own frontend.

**Consistency.** Every resource in the API is represented, paginated, filtered, and reported on error using the same conventions, defined once in this document and applied everywhere, rather than negotiated independently each time a new resource is added. An API where Runs paginate one way and Suites paginate another is not two small inconsistencies; it is a tax paid by every client on every integration, permanently, and this document treats consistency as non-negotiable specifically because its cost compounds while its benefit is invisible until it is violated.

**Long-term evolution and backward compatibility.** Because the API is the one artifact real, independent clients build against and cannot be forced to update in lockstep with the backend, every architectural decision in this document is made with an explicit eye toward what it will cost to evolve later. This is elaborated fully in Versioning Strategy and API Evolution below, but it is named here as a philosophy, not only a set of later rules: the API is designed, from its first version, as something that will need to grow for years without breaking clients that integrated against it on day one.

## Resource Model

Not every entity in the Schema Design is a first-class API resource, and the distinction matters: a first-class resource is directly addressable by its own identifier, independently listable, and independently fetchable; everything else is either a nested representation of a first-class resource or is intentionally not exposed as its own addressable surface at all.

**Projects, Suites, Cases, Runs, Agents, and Graders** are first-class resources in the fullest sense — each is independently listable, independently fetchable by identifier, and the natural entry point a client reaches for when working with the platform. This mirrors the Domain Model's own treatment of these as the entities with genuinely independent identity and lifecycle within their respective bounded contexts.

**Suite Versions, Case Versions, and Prompt Versions** are first-class resources as well, but ones a client typically reaches through their stable parent (listing the versions of a given Suite, or fetching one specific Case Version by its own identifier) rather than browsing independently of any parent context. They are addressable in their own right — because a Run's pinned references point to specific versions, and a client debugging a historical Run needs to fetch exactly the version it pinned — but the API's navigational structure treats them as scoped beneath their stable parent, consistent with Schema Design's ownership model.

**Agent Versions and Adapters** follow the identical pattern: independently addressable, but reached in practice through their owning Agent, since a client's typical entry point is "which versions of this Agent exist," not "browse all Agent Versions across every Agent in the platform."

**Execution Events and Artifacts** are first-class resources scoped entirely to their owning Run — the API never exposes a way to list Execution Events independent of a specific Run, because that access pattern has no meaning in the domain: an Execution Event's entire relevance is as part of one Run's ordered history. They are addressable by identifier for direct fetches (a client that already knows which event or artifact it wants), but the primary access pattern, and the one this document treats as canonical, is always nested beneath the Run.

**Scores** are first-class resources scoped to their owning Run for the same reason, though, because Scores are also compared across many Runs for a given Grader in dashboard and trend workflows, the API additionally supports fetching Scores filtered by Grader across Runs — a read pattern, not a change to Score's fundamental ownership by its Run.

**Audit Logs** are first-class, read-only resources, scoped by Project and by actor rather than nested beneath any single other resource, consistent with Schema Design's treatment of Audit Log as standing apart from the execution-time and definitional-entity ownership graph.

**Grader Versions** are addressable, primarily so that a Score's response representation can reference exactly which version produced it, but are not a resource most clients browse independently — the typical client cares which Grader Version produced a given Score, reached from the Score, far more often than it browses a Grader's version history for its own sake, though that latter access pattern remains supported.

## URL Design

**Resource hierarchy expressed through nesting.** Where one resource is genuinely owned by another, per Schema Design's ownership model, the URL structure reflects that ownership through nesting: a Run's Execution Events, Artifacts, and Scores are addressed beneath that Run, a Suite's Suite Versions are addressed beneath that Suite, a Case's Case Versions beneath that Case. Where a relationship is reference-only rather than ownership — a Run's pinned Case Version, for instance — the URL structure does not nest one beneath the other, because nesting in the URL implies an ownership relationship that reference-only relationships do not have; instead, the reference is expressed as an identifier within the Run's own representation, resolvable independently through the referenced resource's own top-level or appropriately-nested address.

**Plural naming, consistently.** Every resource collection is named with a plural noun, and every individual resource is addressed as a member of that plural collection by its identifier. This is not a stylistic flourish; it is what keeps the URL structure predictable across every resource in the platform, current and future, without a client needing to memorize which resources happen to be singular.

**Stable identifiers, never mutable attributes, in the URL path.** A resource's URL is built from its stable identifier — the same identifier Schema Design assigns as that resource's primary identity — never from a name, a slug, or any other attribute that could change over the resource's lifetime. This matters specifically because of this platform's versioning model: a Suite's name is not part of any Suite Version's identity, and building URLs around names would create exactly the kind of implicit, time-dependent addressing Schema Design's Version Tables section already rejected at the storage layer. A URL, once given to a client, must keep working for as long as the resource it addresses exists, and only an immutable identifier can guarantee that.

**Versioned endpoints refer to the API's own version, not the domain's versioned entities.** This is a deliberate terminology distinction this document insists on precisely because the platform's domain already uses "version" heavily for a different concept: a Case Version or Suite Version is a domain concept addressed through the resource hierarchy described above, while an API version (see Versioning Strategy) is a property of the API surface itself, expressed once, at the root of the URL structure, and never conflated with a domain entity's own version identifier appearing later in the same path.

**Nested resources are bounded to one level of true ownership at a time.** A Run's Execution Events are nested beneath that Run; an Execution Event's referenced Artifacts are not further nested beneath the Execution Event's own URL, because that relationship is reference-only, not ownership, per Schema Design. Deeply nested URLs (a resource nested three or four levels beneath its ultimate ancestor) are avoided by design — nesting reflects direct ownership only, one level at a time, with reference-only relationships always resolved as identifiers within a representation rather than as further path segments.

**Filtering, searching, and sorting are expressed uniformly as query parameters against a collection endpoint**, never as separate endpoints or path segments — listing a Project's Runs filtered by Case, Agent, and time range is the same collection endpoint as listing all of a Project's Runs, with query parameters narrowing the result, because introducing a separate endpoint per filter combination would immediately break the predictability this document's philosophy insists on.

**Pagination is a property of every collection endpoint, without exception**, expressed through a consistent, platform-wide convention (detailed in Filtering below) rather than negotiated per resource — a client that has learned to paginate through Runs already knows how to paginate through Suites, Cases, or Audit Logs, because the mechanism never varies by resource.

## HTTP Method Philosophy

**GET** retrieves a resource or a collection and never causes a side effect a client should be concerned about — it is safe to call repeatedly, safe to cache where appropriate, and safe for any automated tooling to issue without special caution. Every first-class and nested resource in the Resource Model supports GET, both for a single resource by identifier and, where the resource is meaningfully listable, for its collection.

**POST** creates a new resource, and, by extension, is the method used to trigger a Run — creating a Run is, architecturally, creating a new resource whose subsequent lifecycle is then observed through GET and, for live progress, SSE, never through a distinct "trigger" verb. POST is also, more narrowly, used to express an explicit state transition on an existing resource where that transition cannot be expressed as a field-level update — cancelling a Run is the clearest example, since cancellation is a deliberate action with its own validity rules (a Run can only be cancelled from specific states, per the Domain Model's lifecycle), not a generic field the caller sets to an arbitrary value.

**PATCH** updates a mutable subset of an existing resource's fields, and is used only where the underlying entity genuinely supports partial mutation — a Project's settings, a Suite's or Case's administrative status (active, deprecated), an Agent's registered metadata. PATCH is never used against any resource this platform's schema defines as immutable after creation: no Suite Version, Case Version, Prompt Version, Agent Version, Adapter Version, or Grader Version ever accepts a PATCH, and neither does any Execution Event, Artifact, or Score, because none of these has a mutable field for PATCH to legitimately target. This is not an API-layer restriction bolted onto an otherwise-mutable resource; it is the API surface faithfully reflecting a storage-layer invariant that Schema Design already establishes, and the absence of a working PATCH endpoint for these resources is itself part of how this document expresses immutability architecturally.

**DELETE** exists only where Database Design's deletion philosophy permits actual removal — administrative, deliberate expiration of a resource under an explicit retention policy — and is never available as a routine operation against any resource that the platform's core value proposition depends on retaining, which in practice means DELETE is largely absent from the historical and execution-time surface of this API (no client can DELETE a Run, an Execution Event, a Score, or any version row) and present only where genuine, deliberate removal is a legitimate operation (a draft Suite or Case that was never published, for instance, prior to ever being referenced by a Run).

**PUT is not used anywhere in this API.** PUT's semantic — full replacement of a resource's representation — does not fit any resource this platform models: mutable resources (Project settings, administrative status fields) are more precisely and safely updated through PATCH's partial-update semantic, and immutable resources accept no update at all. Introducing PUT would offer a second way to express updates that PATCH already covers, at the cost of the predictability this document's philosophy insists on; it is omitted deliberately rather than by oversight.

**Immutable resources as a first-class API concept.** Because so much of this platform's domain is immutable by design, this document treats "does this resource accept mutation at all" as a property every resource's API surface makes structurally obvious — a resource that has no PATCH and no DELETE affordance available to it communicates its immutability through the shape of the API itself, not merely through documentation prose a client might not read.

## Request Lifecycle

A request's path through the platform is already fully specified by the Backend Architecture; this document's contribution is describing that path from the perspective of what the API contract obligates at each stage, not re-describing the internal layering itself.

**Client to API Layer.** The client issues an HTTP request against a resource URL, per URL Design, carrying whatever authentication credential the request requires (see Authentication) and, for a write, a representation of the resource being created or the fields being updated. The API Layer's obligation at this stage is to validate the request's shape — is this well-formed, does it match the expected representation for this resource, are required fields present — and to reject anything malformed before it consumes any further processing.

**API Layer to Application Layer.** Once shape-validated, the request is translated into a call against the Application Layer's use-case interface, exactly as the Backend Architecture describes. The API's obligation here is translation, not decision-making: the API Layer does not itself decide whether a Run can be created against a deprecated Case Version, for instance — it passes the request through to the layer whose job that decision is.

**Application Layer authorization and orchestration.** The Application Layer authorizes the request — is this caller permitted to perform this operation against this Project-scoped resource, per Authorization below — and orchestrates whatever Domain and Infrastructure calls the use case requires, within the transaction boundary appropriate to the operation, per Database Design's Database Transactions section.

**Domain Layer validation.** Domain invariants — is this Case Version eligible to be run against, does this Suite composition satisfy its own rules — are enforced here, independent of whether the caller was the API or, for asynchronous operations, a Background Worker. The API contract's obligation is to surface whatever the Domain Layer determines, faithfully and without reinterpretation, in the response.

**Infrastructure and response.** Once the Application and Domain layers have determined the outcome, Infrastructure persists or retrieves data accordingly, and the API Layer translates the result back into an HTTP response — a resource representation for success, or a structured error for failure, per Response Philosophy and Error Model below.

**Validation flow, summarized.** Shape-level validation happens once, at the API boundary, cheaply, and rejects malformed requests before they reach business logic. Semantic validation happens in the Domain Layer, invoked through Application, and is never skipped on the assumption the API Layer's shape validation already covered it — this is the identical split the Backend Architecture already establishes, restated here as an API-contract obligation: a client should expect a fast, cheap rejection for a malformed request, and a slower, more specific rejection (see Error Model) for a well-formed request that violates a business rule.

**Authorization flow, summarized.** Authentication — who is making this request — is verified at the API Layer. Authorization — is this identity permitted to perform this specific operation against this specific, Project-scoped resource — is enforced at the Application Layer, per the Backend Architecture's explicit split, and every resource's API contract assumes this split without exception: a client should never observe a request succeed past authentication only to be authorized inconsistently depending on which endpoint happened to handle it.

## Response Philosophy

**Consistency across every resource.** A resource's representation follows the same structural conventions — how its identifier is expressed, how its timestamps are expressed, how its relationships to other resources are expressed — regardless of which resource it is. A client that has learned how a Suite's representation is shaped should not need to relearn that shape for a Case or a Run; the fields differ, the structure does not.

**Resource representations reflect the domain's ownership and reference distinctions.** A representation of a Run includes its owning Project's identifier and its pinned version identifiers as references — not embedded copies of those resources' full representations — consistent with Schema Design's insistence that a Run stores a reference to a Case Version, never a copy of its content. This is not merely a storage-layer decision inherited passively; it is a deliberate API-response decision, because embedding full nested representations by default would mean every fetch of a Run silently grows in size and cost as the resources it references grow in size and cost, breaking the predictability this document's philosophy insists on.

**Expansion is opt-in, never default.** Where a client genuinely needs a referenced resource's full representation alongside the resource that references it — the Case Version's content alongside the Run that pins it, for a debugging view — the API supports this through an explicit, opt-in expansion mechanism rather than by silently including it in every response. This keeps the default response shape for every resource small, predictable, and inexpensive regardless of how the resource is used, while still serving the legitimate cases where a client wants to avoid a second round trip.

**Relationships are always addressable, never only embedded.** Every reference a resource's representation carries — a Run's pinned Case Version, a Score's Grader Version — is expressed as an identifier a client can independently resolve through that resource's own URL, never as an opaque or embedded-only reference that only makes sense in the context of the response that happened to include it. This is what keeps the API's resource graph navigable in any direction a client needs, not only the direction a specific endpoint's designer anticipated.

**Metadata accompanies collections, not individual resources.** A collection response carries pagination metadata (see Filtering) describing the collection itself — how many results, how to fetch the next page — while an individual resource's representation carries only that resource's own fields and relationships, never collection-level metadata that would only make sense in a list context.

**Errors follow one consistent shape across the entire API**, detailed fully in Error Model, precisely because a client's error-handling logic should not need to special-case which resource or which endpoint produced a given failure.

**Pagination metadata is never ambiguous about completeness.** A collection response always makes explicit whether more results exist and how to fetch them, never leaving a client to infer completeness from an empty-seeming page or a suspiciously round result count — this is a direct consequence of Consistency, applied specifically to the one piece of response metadata every list-consuming client depends on getting right.

## Long Running Operations

**Run creation returns immediately, never blocks on execution.** Consistent with ADR-0001's decision that evaluation execution never happens inside an API request, creating a Run is a fast, synchronous operation from the client's perspective: the API validates the request, creates the Run resource in its initial (queued) state, and returns a representation of that resource — not a representation of its eventual outcome. The client receives, in effect, a durable handle to a resource whose state will continue to evolve after the response has already been returned.

**Asynchronous execution is observed, not driven, by the client.** Once a Run has been created, the client has no further obligation to keep any connection open or take any further action to make execution happen — the Background Workers described in the Backend Architecture drive the Run forward independently. The client's only remaining concern is how it learns about the Run's progress and eventual outcome, which this API supports through two complementary mechanisms.

**Polling** is always available and requires nothing beyond the standard GET semantics already described: a client fetches the Run resource by identifier at whatever interval suits it, and observes its status field advancing through the lifecycle the Domain Model defines. This is the simplest possible mechanism, appropriate for clients (a CI integration, a script) that do not need live, sub-polling-interval visibility into a Run's progress.

**Server-Sent Events** provide live, low-latency progress for clients that need it — most notably the frontend's own dashboard — without requiring the client to poll aggressively. This is elaborated fully in the next section.

**Status resources make "how is this going" always answerable synchronously.** A Run's own resource representation is always the authoritative, immediately fetchable answer to its current status, whether or not a client happens to be connected to its SSE stream at that moment — the SSE stream is a convenience for live visibility, never the only way to learn a Run's state, because a client that was disconnected during a Run's entire execution must still be able to learn its outcome with a single GET once it reconnects.

**No API request, of any kind, is ever held open pending an asynchronous outcome.** This is a hard architectural rule, not a default subject to exception per endpoint: every request this API accepts is expected to complete within the low-hundreds-of-milliseconds range the System Overview establishes as the Control Plane's performance goal, and any operation whose true completion depends on execution, grading, or any other asynchronous process is modeled as a resource creation or a resource-state read, never as a held-open request awaiting that process's outcome.

## Server-Sent Events

**Connection lifecycle.** A client opens an SSE connection scoped to a specific Run, over standard HTTP, and the connection remains open for as long as the client wants live updates or until the Run reaches a terminal state, whichever comes first — the server does not hold the connection open indefinitely once nothing further will ever be published to it, since a terminal Run's history is permanently closed and no further event will ever arrive on that stream.

**What is streamed.** The SSE stream publishes the same status transitions and Execution Events that are being durably persisted through the Backend Architecture's execution flow, as they occur — a client watching the stream observes, live, the same facts a later GET against the Run's Execution Events collection would return, never a different or richer view than the persisted record.

**Reconnection.** Because SSE connections can and do drop — network interruption, a client tab backgrounded and resumed — a client must be able to reconnect and resume from where it left off without re-fetching a Run's entire history over the stream. This is supported through the same explicit sequence position that Schema Design already assigns to every Execution Event: a reconnecting client indicates the last sequence position it observed, and the server resumes the stream from there, rather than requiring the client to either lose events that occurred during the disconnection or fall back to a full re-fetch every time.

**Ordering.** The stream delivers events in the same strict sequence order the underlying Execution Event table already guarantees, per Schema Design — the SSE stream introduces no independent notion of ordering, because doing so would create the possibility of the live view and the persisted record disagreeing about what happened in what order, which is precisely the kind of discrepancy this platform's trustworthiness cannot tolerate even transiently.

**Delivery guarantees.** The SSE stream is a best-effort, at-most-once live convenience layered on top of a durable, authoritative record — it does not itself provide delivery guarantees a client should depend on for correctness. A client that needs a guaranteed-complete view of a Run's history, for any reason more rigorous than live dashboard display, reads the persisted Execution Events collection directly rather than relying on having received every event over a live stream that may have dropped a connection at an inopportune moment. This is a deliberate, named tradeoff, not an oversight: guaranteeing exactly-once delivery over a live push channel would add real complexity for a use case (live progress display) that does not actually require it, given that the durable record is always available as the correctness backstop.

**Relationship with persisted Execution Events.** The SSE stream is never the source of truth for anything — it is a live projection of Execution Events that are, independently and durably, being written to the system of record via the exact flow the Backend Architecture's Background Execution Flow describes. This relationship is the API-surface expression of Database Design's principle that Redis (which backs the SSE progress mechanism, per the System Overview) is deliberately excluded from the durable path: an SSE outage affects only live visibility, never the underlying truth of what happened during a Run, which remains fully intact and fully queryable through ordinary GET requests regardless of what happened to any client's live connection.

## Filtering

**Filtering philosophy.** Every collection endpoint supports filtering by the attributes a client would naturally narrow a list by, expressed as query parameters against the collection URL, never as separate endpoints per filter — a Project's Runs filtered by Case, by Agent, by status, or by a time range are all the same collection endpoint, narrowed. This is a direct extension of URL Design's stance that filtering belongs in query parameters, restated here because filtering, more than any other collection concern, is where an API's design is tempted to proliferate special-purpose endpoints, and this document rules that temptation out categorically.

**Search** is treated as a specific, named kind of filter — a text-matching narrowing of a collection, most relevant for definitional entities a human browses by name (Suites, Cases) rather than for execution-time resources a client typically reaches by more structured filters (Case, Agent, time range, status). Search is expressed the same way any other filter is: as a query parameter against the relevant collection endpoint, never as its own distinct endpoint.

**Sorting** is a client-specified ordering applied to a filtered collection, defaulting to the ordering most useful for that resource absent any client preference (most recently created first, for Runs) but always overridable, expressed consistently across every sortable collection rather than negotiated per resource.

**Pagination: cursor over offset, deliberately.** Every collection in this platform is paginated using a cursor-based mechanism, not an offset-based one, and this choice is made for reasons specific to this platform's data shape, not as a generic best practice adopted without justification. Offset-based pagination degrades in both correctness and performance on a table that grows continuously while being paginated — a client paginating through Runs while new Runs are simultaneously being created will, under offset pagination, either see the same Run twice or miss one entirely, because "the twentieth row" shifts meaning as rows are inserted ahead of it. Cursor-based pagination, anchored to a stable position (this platform's cursor is built from the same insertion-ordered, immutable identity every append-only resource already has), does not have this failure mode: a cursor obtained from one page remains valid and correctly anchored regardless of how much data has been inserted since, which matters enormously for a platform whose highest-volume resource — Execution Events, and Runs themselves at scale — is exactly the kind of continuously-growing collection offset pagination handles worst. Cursor pagination also avoids the performance cliff offset pagination hits on large tables, where "skip the first million rows" becomes genuinely expensive at the storage layer as an offset grows — a concern directly connected to Database Design's Partitioning Strategy for exactly these tables.

## Versioning Strategy

**API versioning is explicit and coarse-grained.** The API exposes a version identifier, once, at the root of its URL structure, and every resource and endpoint in a given API version is guaranteed to remain stable within that version for as long as the version is supported. This is a deliberate choice of granularity: versioning individual endpoints or individual resources independently would let different parts of the API drift out of sync with each other in ways a client would have to track individually, while a single, platform-wide version number gives every client one clear answer to "which contract am I integrated against."

**Compatibility within a version is an absolute guarantee.** Once an API version is published, every change made within it must be backward compatible by the rules in API Evolution below — a client correctly integrated against a given API version on the day it launched must continue to work, unmodified, for as long as that version is supported, no matter how much the platform's internal implementation has changed underneath it in the meantime. This guarantee is what makes the version number meaningful; a version number that could still break clients within itself would not actually be providing the stability the concept of versioning exists to promise.

**Deprecation is a long, explicit, observable process, never a silent removal.** When a new API version is introduced, the prior version is not immediately withdrawn — it enters a clearly communicated deprecation period, with a defined, generous timeline, during which it continues to function exactly as before while clients are given the opportunity to migrate. Removal of a deprecated version happens only at the end of that communicated timeline, never as a surprise, and the platform's own frontend is expected to migrate to a new version through the same deprecation window as any external client, not through some privileged, unannounced fast path — a direct consequence of ADR-0001's insistence that there is no private, undocumented internal API distinct from what external callers use.

**Evolution and breaking changes are handled by versioning, not by ambiguity within a version.** Where a genuinely breaking change to a resource's shape or behavior is required — not merely an addition, but a redefinition of what an existing field or endpoint means — that change is only ever introduced in a new API version, never retrofitted into an existing one under the theory that "most clients probably don't rely on the old behavior." This is a hard rule specifically because "probably" is not a guarantee this document is willing to accept on behalf of every client the API will ever have, many of which the platform's own team will never have visibility into.

## Error Model

**One consistent error shape across the entire API.** Regardless of which resource, which endpoint, or which layer of the Backend Architecture ultimately produced a failure, the API surfaces it in the same structural shape — the same fields identify what kind of error occurred, what it means, and, where applicable, which part of the request was responsible. A client's error-handling logic is written once, against this one shape, and applies correctly to every failure the API can ever produce.

**Validation errors** correspond to the API Layer's shape-validation rejections described in Request Lifecycle — a malformed request, a missing required field, a value of the wrong type. These are the cheapest failures to detect and are surfaced with enough specificity that a client can identify and correct exactly what was wrong with its request without needing to guess.

**Authorization errors** correspond to the Application Layer's enforcement of Project-scoped access — a request that is well-formed and would otherwise be valid, but which the authenticated caller is not permitted to perform against the specific resource in question. Consistent with the Backend Architecture's split between authentication and authorization, this API distinguishes, in its error responses, between "you are not who you claim to be" and "you are who you claim to be, but you may not do this" — collapsing the two into a single generic failure would deny a legitimate, well-behaved client the information it needs to determine whether the problem is its credentials or its permissions.

**Domain errors** correspond to the Domain Layer's invariant violations, per the Backend Architecture's Error Handling Philosophy — an attempt to create a Run against a deprecated Case Version, an attempt to score a Run that is not in a gradable state. These are surfaced as specific, well-formed failures distinct from validation errors, because a domain error represents a request that was perfectly well-formed but violates a business rule, which is a meaningfully different situation for a client to understand and react to than a malformed request.

**Infrastructure failures** — a transient database or queue unavailability underneath the request — are surfaced distinctly from domain errors, consistent with the Backend Architecture's insistence that these two categories are never conflated internally, because a client's correct response to each differs: a domain error should never be retried as-is, while an infrastructure failure often should be, and an API that blurred the two into one generic failure category would deny clients the information needed to make that distinction correctly.

**Unexpected failures** are surfaced as a generic, non-leaking failure response, per the Backend Architecture's Error Handling Philosophy — the client learns that something went wrong on the platform's side without being exposed to internal implementation detail that could either leak sensitive information or create an accidental, unsupported dependency on an internal error's specific shape.

## Idempotency

**POST retries are a normal, expected client behavior, not an edge case.** A client that issues a POST and does not receive a response — because of a network timeout, a dropped connection, or any other ambiguous failure — cannot know whether the operation succeeded on the server before the response was lost, and the only safe client behavior in that situation is to retry. This API is designed around that reality rather than around the fiction that a client will only ever issue a POST exactly once per intended operation.

**Run creation is the case this matters most for**, since an unintended duplicate Run is not a harmless no-op — it means an Agent is evaluated twice against the same Case when the client only intended once, consuming real execution cost and, worse, polluting the exact historical record this platform exists to keep trustworthy. Idempotency for Run creation is not an optional convenience; it is a correctness requirement given the stakes of getting it wrong.

**Idempotency keys** are the mechanism: a client that wants a POST — most importantly, Run creation — to be safely retryable supplies a client-generated idempotency key alongside the request, and the API guarantees that multiple requests carrying the same key, within an appropriate retention window, produce or return the same resulting resource rather than creating a duplicate. This mirrors, at the API layer, the same idempotent-insert principle Database Design's Concurrency section already establishes for task redelivery at the Infrastructure layer — the API-level idempotency key and the storage-level uniqueness constraint are two expressions of the identical underlying discipline, applied at the two different points in the request's lifecycle where a duplicate could otherwise be introduced.

**Duplicate requests without an idempotency key** are not silently deduplicated by guesswork — the API does not attempt to infer that two structurally similar requests were "probably" the same client's retry, because that inference is exactly the kind of unreliable heuristic that would sometimes wrongly collapse two genuinely distinct client intentions into one. Safe retries are something the API makes possible for clients who opt into the idempotency-key mechanism deliberately, not something the API attempts to guarantee unconditionally for every request regardless of whether the client participated in making it safe.

**Safe retries beyond POST.** GET is naturally safe to retry without any special mechanism, since it has no side effect. PATCH, applied to the narrow set of genuinely mutable resources this API supports, is designed to be safely retryable by nature — reapplying the same field update twice produces the same end state as applying it once — without requiring an idempotency key, since PATCH's semantics are idempotent by construction in a way POST's resource-creation semantics are not.

## Authentication

**Every request is authenticated; there is no anonymous access.** This restates, at the API-contract level, the System Overview's Security Considerations: no endpoint in this API, including read-only ones, is reachable without an authenticated identity attached to the request. This is a deliberate, absolute rule rather than a default with exceptions carved out for "harmless" read endpoints, because what counts as harmless to expose is itself a judgment call this document does not trust any individual endpoint's implementation to make consistently over the platform's lifetime.

**Identity is established once, at the API boundary.** Consistent with the Backend Architecture, session or token validation happens at the API Layer, and every layer downstream of it — Application, Domain, Infrastructure, Background Workers — trusts that an authenticated identity has already been established rather than re-verifying it independently. This is an architectural efficiency (verification happens exactly once per request, not redundantly at every layer) and a security property (there is exactly one place in the codebase responsible for getting authentication right, rather than several places that could each independently get it slightly wrong).

**Bearer tokens are the credential mechanism this document commits to at the architectural level**, without specifying their issuance, refresh, or storage mechanics — those are implementation decisions for a dedicated authentication design document, not this one. What this document does commit to is the shape of the interaction: a request carries a credential proving its caller's identity, the API Layer verifies that credential, and every request is independently, statelessly verifiable without the API needing to consult any server-held session left over from a prior request, consistent with this document's Statelessness principle.

**Session ownership belongs to whichever actor's credential is presented**, human or automated — a CI integration's credential and a human user's credential are treated identically by this API's authentication architecture, verified the same way, and distinguished only by which actor they resolve to, never by a structurally different authentication path for "real users" versus "automated callers." This is a direct consequence of API-First: the frontend is one caller among many, not a privileged one, and its users' credentials are verified through the same mechanism any other caller's would be.

This document does not design OAuth flows, token issuance, refresh mechanics, or credential storage — those belong to a dedicated authentication and identity design document, informed by the architectural commitments made here but not specified by them.

## Authorization

**Project-scoped authorization is the API's primary access-control dimension**, directly inheriting the Domain Model's treatment of Project as the unit of authorization boundary. Nearly every resource this API exposes belongs, directly or transitively, to exactly one Project, and a caller's ability to read or act on that resource is bound to whether they belong to that Project, checked on every request, never assumed from a prior request or cached client-side.

**Ownership determines visibility, not merely mutability.** A caller who is not a member of a Project cannot see that Project's Suites, Cases, or Runs at all — not merely denied write access to them, but denied their existence in the API's responses entirely, consistent with the System Overview's statement that there is no anonymous access to run data, even read-only. A list endpoint never reveals the existence of resources a caller is not authorized to see, even indirectly through a count or an identifier appearing in an otherwise-filtered result.

**Enforcement happens at the Application Layer, on every request, without exception.** Per the Backend Architecture's explicit split, authorization is never left to the API Layer to informally check, never left to the frontend to hide-and-hope, and never assumed to have already been checked by an earlier request in the same session — because this API is stateless, per API Philosophy, there is no "earlier in the session" for authorization to lean on in the first place. Every single request re-establishes, from its own credential and its own target resource, whether it is authorized, independent of anything that happened on any prior request.

**Resource visibility composes correctly across nested and referenced resources.** A caller authorized to view a Run is, by the nature of Run's ownership model, authorized to view the Execution Events, Artifacts, and Scores that Run owns, since those are not independently Project-scoped resources with their own separate authorization check — their visibility is entirely a function of their owning Run's visibility, exactly mirroring Schema Design's ownership model. A caller is not, however, automatically authorized to view the full representation of a Case Version a Run merely references, if that Case Version belongs to a different Project than the caller has access to — reference-only relationships do not extend visibility the way ownership relationships do, and this API's authorization enforcement is deliberately precise about that distinction.

## API Evolution

**Adding fields is always safe, within a version, when done correctly.** A new, optional field added to an existing resource's representation, or a new, optional parameter accepted by an existing endpoint, is a backward-compatible change: a client written before the field existed continues to function identically, simply ignoring a field it does not know about. This is the primary mechanism by which the API grows in place within a given version, and it is treated as the default, preferred path for evolution wherever it is sufficient.

**Adding resources is always safe.** A new, entirely new resource type introduced to the API — anticipating, for instance, a future Grader SDK's registration surface, per Schema Design's Future Extensions — is backward compatible by construction, since no existing client's behavior depends on a resource it never knew existed. This is the second primary mechanism for growth, and it is preferred over reshaping an existing resource whenever the new capability is genuinely a new kind of thing rather than a new facet of an existing one.

**Deprecation of a field or a resource is signaled explicitly and honored for a defined period before removal**, mirroring the same discipline Versioning Strategy establishes for whole API versions, applied at finer grain: a field the platform intends to stop returning is marked deprecated, continues to be returned exactly as before throughout the deprecation window, and is only actually removed once that window elapses — and even then, in practice, removal of a field is treated as consequential enough that it typically waits for the next API version rather than happening within the version a client is currently relying on.

**Never breaking old clients is the test every proposed change is held against**, more so than any specific rule above — a change that technically fits the letter of "just adding a field" but happens to alter existing behavior in a way an old client would observe differently (a field whose meaning subtly shifts, a default that changes) is treated as a breaking change regardless of its superficial shape, and is routed through Versioning Strategy's process rather than being smuggled into an existing version under the appearance of an additive change.

## Non-Goals

This document defines architecture, not specification. It does not include an OpenAPI document, JSON Schema definitions for any resource representation, FastAPI route or dependency code, endpoint-by-endpoint implementation, or serialization logic mapping resource representations onto the Schema Design's logical tables. It also does not enumerate a complete endpoint list — every resource named in Resource Model implies a set of endpoints following the conventions established here, but naming each one explicitly is downstream work that applies this architecture, not part of the architecture itself. Those artifacts are produced against this document, by engineers implementing the API, and are expected to be fully derivable from the rules established here without requiring any architectural decision this document left unmade.
